1. Opaque Type Aliases & ADTs

One of the cornerstones of software engineering is the Abstract Data Type (ADT): define a type solely by its name, its constructors, and its operations — while hiding the concrete implementation. In Scala 3 the opaque type construct makes this possible with zero runtime overhead.

Key idea

opaque type T = TImpl creates a brand-new type that, outside its defining module, is completely distinct from TImpl. No boxing, no wrapping — the compiler treats them as different types, but at runtime they are the same representation.

An opaque type inside an object gives you a self-contained ADT module: the object defines the type, the constructors, and the operations. Clients see only the public API: they perceive ways of constructing elements and operations to manipulate them, but have no real way to inspect how the type is implemented. This is an alternative to algebraic data types (enum / case class) that promotes information hiding from the start — at the price that hiding the implementation may hamper extending the set of operations outside the module. Any datatype (sequences, streams, optionals) can be defined this way, and new types can transparently reuse existing ones (e.g. sets by algebraic sequences). Use ADTs to cure the primitive obsession: using primitives instead of specifically designed types (strings to represent concepts, booleans for 2-valued types, ints for n-valued types), which is a DIP violation.

The lesson's motivating question: can we build a whole application with pure FP? The mechanisms, in order: opaque alias types / type members (modules providing the type of a data structure), module types / inclusive polymorphism (modules as strategies with a type and many implementations), given instances / contextual abstraction (modules as contextual parameters, possibly implicitly passed), context bounds / ad-hoc polymorphism (type classes), and for-comprehension / monads.

Oral prep

Be ready to compare opaque-type ADTs with Scala’s enum algebraic data types. ADTs are the more standard software-engineering approach: they promote abstraction and modularity, treat operations and constructors uniformly, and from there one more naturally evolves to type classes. Exposed algebraic data types reflect more the Scala approach in libraries, are handier to flexibly add algorithms outside the definition, and from there one more naturally evolves to the OOP approach. In the rest of the lesson sequences and streams are assumed in their algebraic (exposed) version, while the discussion keeps starting from ADTs.

2. ADTs by Example: Euro, Sequence, Set

Euro ADT

Here is a classic “primitive obsession” cure: an opaque type for Euro amounts.

Oral prep

Why is val e3: Euro = 100 forbidden? Because Euro is opaque — outside the EuroADT object, the compiler treats it as unrelated to Int. This forces all construction through the provided factory functions, preserving invariants.

Sequence ADT

The same pattern works for recursive data structures. A linked-list Sequence is defined as an opaque alias to a private enum inside the module. Operations can be given either as extension methods (map) or as standard methods (concat).

object SequenceADT:
  // implementation of the data structure: fully hidden
  private enum SequenceImpl[E]:
    case Cons(head: E, tail: Sequence[E])
    case Nil()
  import SequenceImpl.*

  // the type Sequence is an opaque alias to SequenceImpl
  opaque type Sequence[A] = SequenceImpl[A]

  // constructors
  def cons[E](head: E, tail: Sequence[E]): Sequence[E] = Cons(head, tail)
  def nil[E](): Sequence[E] = Nil[E]()

  // operations as extension methods
  extension [A](seq: Sequence[A])
    def map[B](mapper: A => B): Sequence[B] = seq match
      case Cons(h, t) => Cons(mapper(h), t.map(mapper))
      case Nil()      => Nil()

  // operations as standard methods
  def concat[A](seq1: Sequence[A], seq2: Sequence[A]): Sequence[A] = seq1 match
    case Cons(h, t) => Cons(h, concat(t, seq2))
    case Nil()      => seq2

@main def trySequenceADT =
  import SequenceADT.*   // note: a single import
  val seq = cons(10, cons(20, cons(30, nil())))
  println(concat(seq, seq.map(_ + 1)))
Editor’s note

The private enum is the “real” data type. The opaque type Sequence[A] = SequenceImpl[A] hides this from clients, who cannot pattern-match on Cons/Nil nor build a sequence except through cons/nil. Compare with the encapsulated sequences of lesson 2 (private enum cases, no opaque type): here the very identity of the implementation type is hidden.

Set ADT (backed by algebraic Sequences)

Because Set is just an opaque alias for Sequence, we can build set operations on top of the sequence operations — all while hiding that fact from users. Here Sequence is the algebraic (exposed) enum of lesson 2, with filter as an extension method: this is what allows SetADT to pattern-match on Cons and Nil and to call s.filter.

object SetADT:
  opaque type Set[A] = Sequence[A]

  def fromSequence[A](s: Sequence[A]): Set[A] = s match
    case Cons(h, t) => Cons(h, fromSequence(t.remove(h)))
    case Nil()      => Nil()

  def union[A](s1: Set[A], s2: Set[A]): Set[A] = s2 match
    case Cons(h, t) => Cons(h, union(s1.remove(h), t))
    case Nil()      => s1

  def intersection[A](s1: Set[A], s2: Set[A]): Set[A] = s1 match
    case Cons(h, t) if s2.contains(h) => Cons(h, intersection(t, s2.remove(h)))
    case Cons(_, t)                   => intersection(t, s2)
    case Nil()                        => Nil()

  extension [A](s: Set[A])
    def contains(a: A): Boolean = s match
      case Cons(h, t) if h == a => true
      case Cons(_, t)           => t.contains(a)
      case Nil()                => false
    def remove(a: A): Set[A] = s.filter(_ != a)
    def toSequence(): Sequence[A] = s
Key insight

Notice remove delegates to filter from the Sequence module. Since Set[A] is just Sequence[A] at runtime, all sequence operations are available inside the module. Clients, however, cannot accidentally misuse a Set as a Sequence: val s3: Set[Int] = Cons(10, Nil()) does not compile.

@main def trySetADT =
  import SetADT.*
  val s1: Set[Int] = fromSequence(Cons(10, Cons(20, Cons(10, Cons(30, Nil())))))
  val s2: Set[Int] = fromSequence(Cons(10, Cons(11, Nil())))
  println(s1.toSequence())                     // (10, 20, 30): duplicates removed
  println(s2.toSequence())                     // (10, 11)
  println(union(s1, s2).toSequence())          // (10, 20, 30, 11)
  println(intersection(s1, s2).toSequence())   // (10)

Note how fromSequence removes duplicates: it keeps the head and recurs on the tail with all copies of the head removed. union walks s2, adding each element after removing it from s1, hence (10, 20, 30, 11) and not (10, 11, 20, 30).

3. Module Types by Traits

Just as we gave data types an abstract interface via opaque types, we can give modules an abstract interface via traits. A trait declaring method signatures becomes a module type; any object implementing it is a module that conforms to that type.

Key idea

trait ModuleType { def meth(...): ... } defines a module interface. object Impl extends ModuleType { ... } provides an implementation. Functions can then accept ModuleType as a parameter, enabling strategy-like polymorphism in a purely functional setting.

Implications: many implementations of a module can be provided, trading off various aspects; module implementations can be passed to functions to make them more abstract; an application decides which implementation to use each time. This is very useful in ADTs, and lets us deal with the Open/Closed Principle (extend behaviour by providing new implementations) and the Dependency Inversion Principle (depend on abstractions, not concretions) in a pure FP setting, without any OOP inheritance machinery.

4. Logger & Math Module Types

LoggerModuleType

Two implementations of a simple logger trait demonstrate how module types enable pluggable behaviour:

object LoggerModules:
  trait LoggerModuleType:
    def log(s: String): Unit

  object BasicLoggerModule extends LoggerModuleType:
    def log(s: String): Unit = println(s)

  object EmptyLoggerModule extends LoggerModuleType:
    def log(s: String): Unit = {}

  def loggedCall[A, B](name: String, f: A => B, a: A)(LoggerModule: LoggerModuleType): B =
    LoggerModule.log(s"calling function $name with input $a")
    f(a)

@main def tryLoggers =
  import LoggerModules.*
  println(loggedCall("sin", Math.sin(_), 0.5)(BasicLoggerModule))
  println(loggedCall("sin", Math.sin(_), 0.5)(EmptyLoggerModule))   // no log line
Oral prep

How does loggedCall achieve OCP-compliant behaviour? You can add a new logger (e.g. a file-logger) without modifying loggedCall at all — just pass a new object that extends LoggerModuleType.

MathModuleType with Multiple Implementations

A more realistic example: a math module providing factorial and exponentiation, with two distinct implementations (simple recursive without input checks vs. tail-recursive with input checks; note the if-then-else expression syntax of Scala 3).

object MathModules:
  trait MathModuleType:
    def factorial(n: Int): Int
    def exp(base: Double, power: Int): Double
object BasicMathModule extends MathModuleType:
  def factorial(n: Int): Int =
    if n == 0 then 1 else n * factorial(n - 1)

  def exp(base: Double, power: Int): Double =
    if power == 0 then 1 else base * exp(base, power - 1)
object ProductionMathModule extends MathModuleType:
  def factorial(n: Int): Int =
    @scala.annotation.tailrec
    def _fact(n: Int, temp: Int): Int =
      if n == 0 then temp else _fact(n - 1, temp * n)
    n match
      case _ if n >= 0 => _fact(n, 1)

  def exp(base: Double, power: Int): Double =
    @scala.annotation.tailrec
    def _exp(p: Int, temp: Double): Double =
      if p == 0 then temp else _exp(p - 1, temp * base)
    power match
      case _ if base >= 0 => _exp(power, 1)

A binomial probability function uses whichever module is passed, proving the abstraction:

def binomialProbability(mm: MathModuleType)(n: Int, x: Int, p: Double): Double =
  mm.factorial(n) / mm.factorial(x) / mm.factorial(n - x) *
  mm.exp(p, x) * mm.exp(1 - p, n - x)

// Prob. of 6 heads on 10 coin tosses, same result from both modules:
binomialProbability(BasicMathModule)(10, 6, 0.5)
binomialProbability(ProductionMathModule)(10, 6, 0.5)

Module types with type members: SetADT as a module type

A module type can also declare an abstract type member: the trait states that a type Set[A] exists, with constructors and operations, and each implementation decides what it is (here, an opaque alias to Sequence[A]). Clients depend only on the trait, and can even import the type from a value of that type:

trait SetADT:
  type Set[A]
  def fromSequence[A](s: Sequence[A]): Set[A]
  def union[A](s1: Set[A], s2: Set[A]): Set[A]
  def intersection[A](s1: Set[A], s2: Set[A]): Set[A]
  extension [A](s: Set[A])
    def contains(a: A): Boolean
    def remove(a: A): Set[A]
    def toSequence(): Sequence[A]

object BasicSetADT extends SetADT:
  opaque type Set[A] = Sequence[A]
  // ... same implementation as the SetADT object above ...

@main def trySetADTModule =
  import Sets.*
  val setADT: SetADT = BasicSetADT
  import setADT.*          // brings the type Set and the operations of that implementation
  val s1: Set[Int] = fromSequence(Cons(10, Cons(20, Cons(10, Cons(30, Nil())))))
  // val s3: Set[Int] = Cons(10, Nil())   // still not allowed: Set is abstract/opaque
  println(s1.toSequence())   // (10, 20, 30)

5. Contextual Abstraction: given/using

Contextual abstraction is the idea that certain function inputs are really just “context” — configuration, strategies, dependencies that the caller should not have to pass explicitly every time. Scala 3’s given/using mechanism provides first-class support for this pattern.

Key idea

def meth(arg: Type)(using ctx: CtxType) declares a contextual parameter; meth(actualArg)(using actualCtx) passes it explicitly; given givenName: CtxType = actualCtx defines a canonical term for that type, so that meth(actualArg) can be called with the context passed implicitly by the compiler. A using clause applies to a whole (curried) parameter list, typically the last one; the given name can be omitted (given CtxType = ...). Contextual abstraction easily captures additional arguments/strategies of methods, and is the basis of type classes.

Here is the simplest case: a max function over a sequence that needs a “default” value when the sequence is empty:

object ContextualParameters:
  def max(seq: Sequence[Int])(using orElse: Int): Int = seq match
    case Cons(h1, Cons(h2, t)) => max(Cons(if h1 > h2 then h1 else h2, t))
    case Cons(h1, Nil())       => h1
    case _                     => orElse

  given standardDefault: Int = -1

@main def tryContextualParameters() =
  import ContextualParameters.*
  println(max(Cons(10, Cons(30, Cons(20, Nil()))))(using -1))  // explicit
  println(max(Nil())(using -1))

  import ContextualParameters.given
  println(max(Cons(10, Cons(30, Cons(20, Nil())))))             // implicit via given
  println(max(Nil()))                                           // -1, implicit via given

Note that the using clause is not needed in the recursive call max(Cons(...)): inside the body orElse is itself a given, so the context is propagated automatically. The import import ContextualParameters.given (or ContextualParameters.standardDefault) is necessary: a plain import ContextualParameters.* does not import given instances. Plain contextual parameters like this one are not very common; strategies and modules are the typical use.

6. Contextual Strategies & Modules

Contextual Strategies

The same mechanism can inject a comparison strategy into max:

object ContextualStrategies:
  def max(seq: Sequence[Int])(using ordering: (Int, Int) => Boolean): Int = seq match
    case Cons(h1, Cons(h2, t)) =>
      max(Cons(if ordering(h1, h2) then h1 else h2, t))
    case Cons(h1, Nil()) => h1

@main def tryContextualStrategies() =
  println(max(Cons(10, Cons(30, Cons(20, Nil()))))(using _ > _))   // 30
  println(max(Cons(10, Cons(30, Cons(20, Nil()))))(using _ < _))   // 10: "greater" means "smaller"

  // an anonymous given (the name would not be helpful); defined here, no import needed
  given ((Int, Int) => Boolean) = _ > _
  println(max(Cons(10, Cons(30, Cons(20, Nil())))))                // 30

Contextual Modules (Dependency Injection, FP-style)

The full power emerges when we combine module types with given/using: a module is “injected” into a function as a contextual parameter.

object ContextualModules:
  trait IntOrderingModuleType:
    def greater(t1: Int, t2: Int): Boolean

  def max(seq: Sequence[Int])(using ordering: IntOrderingModuleType): Int = seq match
    case Cons(h1, Cons(h2, t)) =>
      max(Cons(if ordering.greater(h1, h2) then h1 else h2, t))
    case Cons(h1, Nil()) => h1

  object MyIntOrderingModule extends IntOrderingModuleType:
    def greater(t1: Int, t2: Int): Boolean = t1 > t2

  given iom: IntOrderingModuleType = MyIntOrderingModule

@main def tryContextualModules =
  import ContextualModules.*
  import ContextualModules.given                      // import all givens (or: import ContextualModules.iom)
  println(max(Cons(10, Cons(30, Cons(20, Nil())))))
  val ord = summon[IntOrderingModuleType]             // recovers the given: ContextualModules.iom

Applying this to the MathModuleType from earlier: we can declare a given MathModuleType = ProductionMathModule and then call binomialProbability without explicitly passing the module.

def binomialProbability(n: Int, x: Int, p: Double)(using mm: MathModuleType): Double =
  mm.factorial(n) / mm.factorial(x) / mm.factorial(n - x) *
  mm.exp(p, x) * mm.exp(1 - p, n - x)

given MathModuleType = ProductionMathModule

// Usage: no module argument needed!
binomialProbability(10, 6, 0.5)
Oral prep

This is pure-FP dependency injection. How is it different from the OOP approach (DI frameworks like Spring)? There is no reflection, no container, no runtime wiring — the compiler resolves everything at compile time based on scoped given definitions.

7. Type Classes & Context Bounds

When a module type is generic — parameterised by a type T — and used as a contextual parameter, it becomes a type class. A context bound [T: TypeClass] says: “this function works for any T for which a TypeClass[T] witness is available in scope.”

Key idea

def f[T: TypeClass](x: T): ... is syntactic sugar for def f[T](x: T)(using TypeClass[T]): .... Inside the method body, call summon[TypeClass[T]] to recover the witness.

This is ad-hoc polymorphism: different types can have completely different implementations of the same interface, chosen not by inheritance but by which given instance is in scope. The context GenericModuleType[T] can be interpreted as an a posteriori extension of type T — a “type class” — and the instance in scope is its witness. Ultimately this calls for defining concise data types, extensible later where and if needed. The two styles are equivalent:

// using-oriented style
def maxWithUsing[T](seq: Sequence[T])(using ordered: Ordered[T]): T = max(seq)
// context-bound style: callable on T only if an Ordered[T] is available in scope
def max[T: Ordered](seq: Sequence[T]): T = ...

8. The Ordered & Showable Type Classes

Ordered type class

trait Ordered[T]:
  def greater(t1: T, t2: T): Boolean

// Context-bound style
def max[T: Ordered](seq: Sequence[T]): T = seq match
  case Cons(h1, Cons(h2, t)) =>
    max(Cons(if summon[Ordered[T]].greater(h1, h2) then h1 else h2, t))
  case Cons(h1, Nil()) => h1

// Given instances
given Ordered[Int] with
  def greater(t1: Int, t2: Int): Boolean = t1 > t2

object MyOrderedString extends Ordered[String]:
  def greater(t1: String, t2: String): Boolean = t1 > t2
given Ordered[String] = MyOrderedString

@main def tryContextBound =
  println(max(Cons(10, Cons(30, Cons(20, Nil())))))           // Int: works
  println(max(Cons("a", Cons("c", Cons("d", Nil())))))       // String: works
  // println(max(Cons(1.0, Cons(3.0, Cons(5.0, Nil())))))    // Double: no given!

Showable type class

The Showable type class provides a show method for any type we choose to support. It mimics what .toString does, but in a principled, extensible way. In the slides the type class lives in object Showables with its algorithms in a companion object Showable, and the given instances in a separate object ShowableGivenInstances, imported with import ShowableGivenInstances.{*, given}.

trait Showable[T]:
  def show(t: T): String

// Extension method for all Showable types
extension [A: Showable](a: A)
  def show(): String = summon[Showable[A]].show(a)

def showPair[A: Showable, B: Showable](t: (A, B)): String = t match
  case (a, b) => "(" + a.show() + ", " + b.show() + ")"

def showSequence[A: Showable](seq: Sequence[A]): String = seq match
  case Cons(h, t) => "| " + h + showSequence(t)
  case Nil()      => ":"

// Given instances
given Showable[Int] with
  def show(i: Int): String = "" + i

given Showable[String] with
  def show(s: String): String = s

case class Student(name: String, id: Int)
given Showable[Student] with
  def show(s: Student): String = s match
    case Student(n, i) => "stud(" + n.show() + ", " + i.show() + ")"

@main def tryShowable =
  println(10.show())                    // "10"
  println("hello!".show())             // "hello!"
  println(Student("mario", 201).show()) // "stud(mario, 201)"
Oral prep

Notice that 10.show() looks like we dynamically extended Int with a new method. This is the power of type classes combined with extension methods: you can add behaviour to existing types without modifying them.

9. Higher-Kinded Types

Scala’s type system supports higher-kinded types — types that abstract over type constructors (i.e., types that themselves take type parameters). This is essential for generalising over container-like types.

Kind hierarchy

Types have kinds, which describe how many type parameters they take:

  • 0-kinded: Int, String, Euro — fully applied types
  • 1-kinded: Showable[T], Sequence[A] — one type parameter
  • 2-kinded: Monad[M[_]], Filterable[T[_]] — accepts a 1-kinded type
// 0-kinded
trait FactorialModuleType:
  def factorial(n: Int): Int

// 1-kinded
trait Showable[T]:
  def show(t: T): String

// 2-kinded
trait Filterable[T[_]]:
  def filter[A](t: T[A])(f: A => Boolean): T[A]

object FilterableOptional extends Filterable[Optional]:
  def filter[A](t: Optional[A])(f: A => Boolean): Optional[A] = t match
    case Just(a) if f(a) => Just(a)
    case _               => Empty()

val opt = FilterableOptional.filter(Just(11))(_ > 10)   // Just(11)

(The slide writes the empty case as None(), following the naming of the u03.extensionmethods.Optionals module it imports; here we use the Empty() of this lesson's Optional.)

Higher-kinded types are what make the Monad type class possible: a monad works for any type constructor F[_] that satisfies the monadic laws. Libraries such as Cats are organised as a hierarchy of such type classes (Functor, Applicative, Monad, ...).

10. For-Comprehension & the Monad Type Class

Everybody talks about monads: “the one-for-all recipe”, “the single design pattern for FP”, “a way of programming the semicolon in for-comprehensions”, “a variable binding mechanism”, “a tool for packing imperative aspects as pure FP”. History: in category theory a monad is an endofunctor with two natural transformations and certain laws; Eugenio Moggi (1991) described their use in programming; Haskell introduced them to handle I/O with lazy evaluation; they are used for sequences, optionals, streams, stateful evaluation, futures, I/O, parsers. Scala collections are monadic, and this is what for-comprehension relies on; libraries like scalaz and cats provide full support.

A monad is a computational “package” for elements of a type A — optionality, multiple results, I/O, state — providing two operations:

  • unit[A](a: => A): F[A] — wraps a value into the monadic context
  • flatMap[A, B](ma: F[A])(f: A => F[B]): F[B] — sequences computations

flatMap (or bind) takes a package of A and a function from A to a package of B: it takes the values out of the input monad, applies the function to them, and ultimately returns one package of B. It is a functional, programmable composition mechanism: for x <- m; ... becomes m.flatMap(x => ...), so by flatMap we implement “our” meaning of “;” in for-comprehensions involving m's type — we program what to extract from the monad and how to pass it to the next stages. In Scala, flatMap and map are all that is needed for for-comprehension syntax (a preview with the standard Option and List):

def getRandom(): Option[Double] =
  if Math.random() < 0.9 then Some(Math.random) else None

// For-comprehension desugars into flatMap/map
val sum: Option[Double] =
  for
    x <- getRandom()
    y <- getRandom()
    z <- getRandom()
  yield x + y + z
println(sum)   // Some(x + y + z) or None, probabilistically

// Equivalent desugared form: the last generator becomes a map
val sum2 = getRandom().flatMap(x =>
           getRandom().flatMap(y =>
           getRandom().map(z => x + y + z)))

val list: List[String] =
  for
    x <- List(10, 20, 30)
    y <- List("A", "B", "C")
  yield x + y
println(list)   // List(10A, 10B, 10C, 20A, 20B, 20C, 30A, 30B, 30C)
// equivalent to List(10,20,30).flatMap(x => List("A","B","C").map(y => x + y))

Two implementation strategies in Scala: just implement extension methods flatMap/map for your data type and use it in for-comprehensions; or use a type class approach, getting additional operations for free.

The general Monad type class captures this pattern generically:

With the type class in place, we can derive generic operations like map2 (combine two monadic values) and seqN (sequence a stream of monadic values):

object Monad:
  def map2[M[_]: Monad, A, B, C](m: M[A], m2: => M[B])(f: (A, B) => C): M[C] =
    m.flatMap(a => m2.map(b => f(a, b)))

  def seq[M[_]: Monad, A, B](m: M[A], m2: => M[B]): M[B] =
    map2(m, m2)((a, b) => b)

  def seqN[M[_]: Monad, A](stream: Stream[M[A]]): M[A] = stream match
    case Cons(h, t) => (h(), t()) match
      case (m, Empty()) => m
      case (m, s)       => seq(m, seqN(s))

11. Monadic Laws

Three laws define what it means to be a monad. Every Monad[F] implementation must satisfy these for the abstraction to be well-behaved:

LawExpressionMeaning
Left identity flatMap(unit(a), f) === f(a) Wrapping then flatMapping is the same as applying f directly
Right identity flatMap(m, unit) === m FlatMapping with unit leaves the monad unchanged
Associativity flatMap(flatMap(m, f), g) === flatMap(m, x => flatMap(f(x), g)) Sequencing of operations is associative; the grouping does not matter
Oral prep

These laws correspond to the category-theoretic monad laws. Left/right identity says that unit is a neutral element; associativity says that flatMap behaves like composition. You should be able to verify these for a concrete monad (e.g., manually verify for Optional).

12. The Optional & Sequence Monads

Optional as a Monad

The Optional monad models computations that may fail to produce a value. unit wraps a value in Just; flatMap unwraps only if the optional is Just, otherwise propagates Empty:

object Optionals:
  enum Optional[A]:
    case Just(a: A)
    case Empty()

  object Optional:   // minimal set of algorithms
    extension [A](m: Optional[A])
      def filter(p: A => Boolean): Optional[A] = m match
        case Just(a) if p(a) => m
        case _               => Empty()

  // extending Optional to be a Monad!
  given Monad[Optional] with
    import Optional.{Just, Empty}

    def unit[A](a: A): Optional[A] = Just(a)   // just boxing the value

    extension [A](m: Optional[A])              // opens the box if possible, gives the new box
      def flatMap[B](f: A => Optional[B]): Optional[B] = m match
        case Just(a) => f(a)
        case Empty() => Empty()

@main def tryOptionals =
  import Optionals.{*, given}, Optional.*   // importing also the given terms

  def optionalRandom(): Optional[Double] =
    Just(java.lang.Math.random()).filter(_ < 0.9)

  // <- just unboxes the Optional if possible; one Empty makes the whole result Empty
  val m: Optional[Double] = for
    x <- optionalRandom()
    y <- optionalRandom()
    z <- optionalRandom()
  yield x + y + z

  // equivalent formulation by flatMap/map
  val m2 = optionalRandom().flatMap(x =>
             optionalRandom().flatMap(y =>
               optionalRandom().map(z => x + y + z)))

  // a general-purpose monadic operator from object Monad
  println(map2(Just("rand: "), optionalRandom())(_ + _))   // Just(rand: 0.223..) or Empty()

Sequence as a Monad

The Sequence monad models non-deterministic / multi-valued computations. flatMap applies the function to every element and concatenates the results, producing the cartesian product:

object Sequences:
  enum Sequence[A]:
    case Cons(h: A, t: Sequence[A])
    case Nil()

  object Sequence:
    extension [A](s1: Sequence[A])
      def append(s2: Sequence[A]): Sequence[A] = s1 match
        case Cons(h, t) => Cons(h, t.append(s2))
        case Nil()      => s2

  given Monad[Sequence] with
    import Sequence.*
    def unit[A](a: A) = Cons(a, Nil())

    extension [A](m: Sequence[A])
      def flatMap[B](f: A => Sequence[B]): Sequence[B] = m match
        case Cons(h, t) => f(h).append(t.flatMap(f))
        case Nil()      => Nil()

@main def trySequences =
  import Sequences.{*, given}, Sequence.*
  // <- iterates all elements, using each to create a new box
  val s: Sequence[(Int, String)] = for
    x <- Cons(10, Cons(20, Nil()))
    y <- Cons("a", Cons("b", Nil()))
    z <- Cons(true, Cons(false, Nil()))
  yield if z then (x, y) else (0, y)
  println(s)
  // Cons((10,a), Cons((0,a), Cons((10,b), Cons((0,b),
  //   Cons((20,a), Cons((0,a), Cons((20,b), Cons((0,b), Nil()))))))))
  // 8 elements: every combination of (10|20) x (a|b) x (true|false), outer generator slowest

13. The IO Monad

In a purely functional language, I/O operations (reading input, printing to console) are side effects that violate referential transparency. The IO monad encapsulates these effects as first-class values: an IO[A] is a description of a computation that, when executed, performs I/O and produces an A.

object IOs:
  // data structure for a computation with input/output
  case class IO[A](exec: () => A)

  object IO:   // minimal set of operations
    def read(): IO[String]         = IO(() => scala.io.StdIn.readLine)
    def write[A](a: A): IO[A]      = IO(() => { println(a); a })
    def compute[A](a: => A): IO[A] = IO(() => a)
    def nop(): IO[Unit]            = compute(())

  given Monad[IO] with
    def unit[A](a: A): IO[A] = IO(() => a)   // an IO that just returns the boxed value

    extension [A](m: IO[A])   // opens the box, executes, and creates a new box with the result
      def flatMap[B](f: A => IO[B]): IO[B] =
        m match
          case IO(e) => f(e())
Editor’s note

With this minimal flatMap, m's effect runs as soon as the composition is built (f(e()) executes e immediately), so the slides' IO is a way of packaging side-effects behind a pure interface rather than a fully deferred description. A fully lazy variant would be IO(() => f(m.exec()).exec()), which runs nothing until someone calls exec() on the final value. The for-comprehension code is identical in both cases.

Now we can write an interactive program purely functionally, composing I/O actions with for-comprehension:

val simpleInteractiveComputation: IO[Int] = for
  s <- read()
  _ <- write("Thanks for providing: " + s)
  i <- compute(s.toInt)
  j <- compute(i * 2)
  _ <- write("Result is: " + j)
yield j

DrawNumber Game

A complete functional game with stateful logic, all inside the IO monad:

@main def tryDrawGameApp =
  enum Result:
    case Won, Lost

  def drawNumberGame(attempts: Int, draw: Int): IO[Result] =
    if attempts == 0
    then compute(Result.Lost)
    else
      for
        _ <- write("give your number: ")
        d <- read()
        i <- compute(d.toInt)
        res <-
          if i == draw
          then
            for
              _ <- write("won")
              r <- compute(Result.Won)
            yield r
          else
            for
              _ <- write(if i > draw then "too high!" else "too low!")
              r <- drawNumberGame(attempts - 1, draw)
            yield r
      yield res

  // starts one run of the game
  drawNumberGame(10, scala.util.Random.nextInt(100))

Note the shape: the “loop” is recursion inside the monad, and the generator res <- if ... then (for ...) else (for ...) binds the result of whichever nested IO computation is selected.

14. The State Monad

The State monad models computations that carry evolving state through a sequence of steps, all in a purely functional way. A State[S, A] is a function from an initial state S to a pair (S, A) of the new state and the result.

object States:
  // a state is/has a function evolving S and producing a result A
  case class State[S, A](run: S => (S, A))

  object State:
    // a facility to run the state on an initial s
    extension [S, A](m: State[S, A])
      def apply(s: S): (S, A) = m match
        case State(run) => run(s)

  // a given instance that works for all S: needs a "type lambda"
  given stateMonad[S]: Monad[[A] =>> State[S, A]] with
    // unit: a state with no evolution, just the result
    def unit[A](a: A): State[S, A] = State(s => (s, a))

    // flatMap: runs the state, uses the result to create (and run) the next state
    extension [A](m: State[S, A])
      override def flatMap[B](f: A => State[S, B]): State[S, B] =
        State(s => m.apply(s) match
          case (s2, a) => f(a).apply(s2))
Key insight

The type lambda [A] =>> State[S, A] is needed because Monad expects a 1-kinded type constructor, but State[S, A] has two type parameters. The lambda “bakes in” a fixed S, yielding a 1-kinded type.

A CounterState ADT and a session

A counter is an ADT whose operations are state transitions: each returns a State[Counter, A], i.e. a function from the current counter to (new counter, result). get() returns the counter as result without changing it; nop() changes nothing.

trait CounterState:
  type Counter
  def initialCounter(): Counter
  def inc(): State[Counter, Unit]
  def dec(): State[Counter, Unit]
  def reset(): State[Counter, Unit]
  def get(): State[Counter, Int]
  def nop(): State[Counter, Unit]

object CounterStateImpl extends CounterState:
  opaque type Counter = Int
  def initialCounter(): Counter = 0
  // each operation gives (new_counter, result)
  def inc(): State[Counter, Unit]   = State(i => (i + 1, ()))
  def dec(): State[Counter, Unit]   = State(i => (i - 1, ()))
  def reset(): State[Counter, Unit] = State(i => (0, ()))
  def get(): State[Counter, Int]    = State(i => (i, i))
  def nop(): State[Counter, Unit]   = State(i => (i, ()))

@main def tryCounterState =
  import Monads.*, Monad.*, States.{*, given}, State.*
  val counterState: CounterState = CounterStateImpl
  import counterState.*

  println(inc().run(initialCounter()))              // (1,())
  println(seq(inc(), inc()).run(initialCounter()))  // (2,())

  def increment(n: Int): State[Counter, Unit] =     // a loop as monadic recursion
    if n == 0
    then nop()
    else
      for
        _ <- increment(n - 1)
        _ <- inc()
      yield ()

  val session: State[Counter, Int] =
    for
      _ <- inc()
      _ <- reset()
      _ <- increment(5)
      v <- get()
      _ <- reset()
    yield v

  println(session.run(initialCounter()))   // (0,5): final counter 0, result 5
Editor’s note

Since run: S => (S, A), the pair is (state, result): inc().run(0) is (1,()) and the session gives (0,5). The slide comments print the two components in the opposite order (((),1) and (5,0)); the code is what counts. Notice also that session is a value: nothing runs until run is applied to an initial counter, and running it twice gives the same result — no mutation anywhere.

15. A State-Monadic Little “MVC”

The capstone example combines everything: opaque types for the window and counter states, module types for the WindowState and CounterState abstractions, and the State monad to wire a complete GUI application — all in pure FP.

WindowState type (abstract)

trait WindowState:
  type Window
  def initialWindow: Window
  def setSize(width: Int, height: Int): State[Window, Unit]
  def addButton(text: String, name: String): State[Window, Unit]
  def addLabel(text: String, name: String): State[Window, Unit]
  def toLabel(text: String, name: String): State[Window, Unit]
  def show(): State[Window, Unit]
  def exec(cmd: => Unit): State[Window, Unit]
  def eventStream(): State[Window, Stream[String]]

CounterState type (abstract)

trait CounterState:
  type Counter
  def initialCounter(): Counter
  def inc(): State[Counter, Unit]
  def dec(): State[Counter, Unit]
  def reset(): State[Counter, Unit]
  def get(): State[Counter, Int]
  def nop(): State[Counter, Unit]

object CounterStateImpl extends CounterState:
  opaque type Counter = Int
  def initialCounter(): Counter = 0
  def inc(): State[Counter, Unit]   = State(i => (i + 1, ()))
  def dec(): State[Counter, Unit]   = State(i => (i - 1, ()))
  def reset(): State[Counter, Unit] = State(i => (0, ()))
  def get(): State[Counter, Int]    = State(i => (i, i))
  def nop(): State[Counter, Unit]   = State(i => (i, ()))

The MVC wiring

The view side is implemented over a Java SwingFunctionalFacade exposing a fluent Frame (setSize, addButton, addLabel, showToLabel, show, and events(): Supplier[String], a blocking queue of button names). WindowStateImpl makes type Window = Frame, wraps each facade call into a State (e.g. def show() = State(w => (w.show, {})), def exec(cmd: => Unit) = State(w => (w, cmd))), and eventStream() returns State(w => (w, Stream.generate(() => w.events().get))): an infinite, lazy stream of events.

The mv combinator runs a model-state computation and then a view-state computation over a pair of states (SM, SV), feeding the model's result into the view:

def mv[SM, SV, AM, AV](
  m1: State[SM, AM],
  f: AM => State[SV, AV]
): State[(SM, SV), AV] =
  State: (sm, sv) =>
    val (sm2, am) = m1.run(sm)
    val (sv2, av) = f(am).run(sv)
    ((sm2, sv2), av)

The main controller creates the window, sets up buttons, then processes events infinitely:

@main def runMVC =
  def windowCreation(str: String): State[Window, Stream[String]] = for
    _ <- setSize(300, 300)
    _ <- addButton(text = "inc",    name = "IncButton")
    _ <- addButton(text = "dec",    name = "DecButton")
    _ <- addButton(text = "reset",  name = "ResetButton")
    _ <- addButton(text = "quit",   name = "QuitButton")
    _ <- addLabel(text = str,      name = "Label1")
    _ <- show()
    events <- eventStream()
  yield events

  val controller = for
    events <- mv(seq(reset(), get()), i => windowCreation(i.toString()))
    _     <- seqN(events.map(_ match
      case "IncButton"    => mv(seq(inc(), get()),   i => toLabel(i.toString, "Label1"))
      case "DecButton"    => mv(seq(dec(), get()),   i => toLabel(i.toString, "Label1"))
      case "ResetButton"  => mv(seq(reset(), get()), i => toLabel(i.toString, "Label1"))
      case "QuitButton"   => mv(nop(), _ => exec(sys.exit()))))
  yield ()

  controller.run((initialCounter(), initialWindow))
Oral prep

This is a complete application with no mutable variables in the Scala code: the imperative Swing machinery is hidden behind the facade, and the entire application state — both the counter and the window — flows through State computations. Be ready to explain how mv composes the two state threads (the pair (Counter, Window) is the state of the whole controller), how seq(reset(), get()) resets and reads the counter in one model step, and how seqN over the infinite lazy event stream is the event loop: each event is mapped to a State[(Counter, Window), Unit] and sequenced with the next, so the program never returns until QuitButton executes sys.exit().

The lesson shows that pure FP is not an academic exercise: it can build real, interactive applications. Libraries like Cats provide these abstractions in a battle-tested form, used in production systems world-wide.

Check Your Understanding

What is the difference between an opaque type alias and a regular type alias?

A regular type T = Int is just a synonym — clients can use T and Int interchangeably. An opaque type T = Int creates a distinct type that, outside the defining object, is not interchangeable with Int. This enforces abstraction: all construction and manipulation must go through the ADT’s public API.

How do module types support the Open/Closed Principle in FP?

A module type (trait) defines an interface. You can add new implementations (new objects extending the trait) without modifying any code that depends on the interface. Functions that accept the module type as a parameter can be used with any implementation — this is the OCP applied at the module level without OOP inheritance.

Explain the difference between given/using in Scala 3 and implicit in Scala 2.

Conceptually they serve the same purpose, but Scala 3 separates the two use cases of implicit: given for defining canonical terms, using for declaring contextual parameters. This eliminates the ambiguity that plagued Scala 2 implicits (was this implicit a conversion, a parameter, or a class?) and makes the intent explicit. The summon method replaces implicitly.

What is a context bound? Write an example.

A context bound [T: TypeClass] is syntactic sugar for a using parameter of type TypeClass[T]. It expresses ad-hoc polymorphism: the function works for any T that has a TypeClass[T] witness in scope. Example: def max[T: Ordered](seq: Sequence[T]): T = ... where Ordered[T] provides the comparison logic.

What is a higher-kinded type? Why is it needed for the Monad type class?

A higher-kinded type abstracts over type constructors. For example, Monad[F[_]] takes a 1-kinded type constructor F (like Optional, Sequence, or IO) as a parameter. This allows us to write generic monadic operations once, then instantiate them for any specific monad. Without higher-kinded types, we would need a separate MonadOptional, MonadSequence, etc.

State the three monadic laws. Why does each matter for programming?

Left identity: flatMap(unit(a), f) === f(a) — ensures unit does not introduce extra effects. Right identity: flatMap(m, unit) === m — ensures unit does not discard effects. Associativity: flatMap(flatMap(m, f), g) === flatMap(m, x => flatMap(f(x), g)) — ensures that sequencing is straightforward and refactorable. Together they let us reason about monadic code equationally.

How does the State monad make mutable state purely functional?

Instead of mutating a variable in place, the State monad threads state through a computation as an explicit parameter and return value. A State[S, A] is a function S => (S, A) that takes an incoming state and returns both a new state and a result. flatMap composes these functions, threading the state automatically. The run method executes the entire computation with an initial state, never mutating anything.

What is the meaning of <- in a for-comprehension over Optional, over Sequence, and over State?

It is always flatMap, but each monad programs it differently. Optional: <- unboxes the value if present, and a single Empty() makes the whole result Empty() (failure propagation). Sequence: <- iterates over all elements, using each to create a new sequence which is appended to the others, so nested generators give all combinations (the cartesian product, outer generator slowest). State: <- runs the transition on the current state, binds the produced result, and passes the new state to the next transition; the whole for-comprehension is itself a State value that runs nothing until applied to an initial state.

Why does the State given instance need a type lambda, and what does session.run(initialCounter()) return?

Monad abstracts over a 1-kinded type constructor M[_], but State[S, A] has two parameters: [A] =>> State[S, A] fixes S and yields a 1-kinded type, and given stateMonad[S] provides an instance for every S. For the session inc; reset; increment(5); v <- get; reset; yield v starting from counter 0: the counter goes 1, 0, 5, stays 5 while get yields 5, then 0; the result is the pair (final state, result) = (0, 5).

What does the mv combinator do in the MVC example?

mv (model-view) runs two independent state computations over a pair of states (SM, SV). The model computation m1: State[SM, AM] produces a value AM, which is then fed into a view computation f: AM => State[SV, AV]. The states evolve independently, but the computations are sequenced together through the pair. This lets us keep counter state and window state completely separate while composing them.
