1. Functional Data Structures

Scala blends OOP and FP naturally. When building a data structure such as a linked list, we aim for immutability, rely on Option instead of exceptions, and support declarative operations like map, filter, and foreach. The idiomatic Scala approach defines the type with its OO-style method signatures, uses enums for the algebraic data type, and places factories or FP-style operations in the companion object.

Key idea

Scala's approach to data structures is OO/FP mixed: a single enum defines the contract, constructors (cases), and methods in one place. The companion object hosts factories and utility operations.

2. Right-Associative Construction

Scala supports right-associative operators: any method whose name ends with : is right-associative. This is the secret behind the elegant 1 :: 2 :: 3 :: Nil syntax. Internally, a :: b is rewritten to b.::(a), so the list is built from right to left.

Oral exam

Be ready to explain: why does :: need right associativity? Because the receiver of a prepend is the list, which sits on the right: 10 :: 20 :: Nil() must parse as 10 :: (20 :: Nil()), i.e. Nil().::(20).::(10); with the usual left associativity 10 :: 20 would try to call a method on the Int 10. So the expression reads left-to-right while the list is built right-to-left, each step an O(1) prepend. The same name is used for the case constructor, because in a pattern the infix form p op q is equivalent to op(p, q): case h :: t matches a cons node.

3. Folding: foldLeft and foldRight

Folding is the quintessential functional pattern for reducing a collection to a single value. Scala supports both left-to-right and right-to-left folds. Understanding the difference is critical for both correctness and performance.

Key insight

foldLeft is tail-recursive and processes elements left-to-right, accumulating a result. foldRight processes right-to-left using the stack—it is not tail-recursive, but it is natural for reconstructing structures (like map via foldRight).

Worked example

Fold List(10, 20, 30) with + and initial value 0, both ways, by hand. foldLeft(0)(_ + _) looks at the head, combines it with the accumulator, and moves on: 0 + 10 = 10, then 10 + 20 = 30, then 30 + 30 = 60, then the list is empty and 60 is returned. Each step finished its arithmetic before making the next call, so the recursive call is the last thing the function does: this is what tail-recursive means, and it is why the compiler can turn it into a loop that uses no stack no matter how long the list is. Written out, the result is ((0 + 10) + 20) + 30: the parentheses nest on the left.

foldRight(0)(_ + _) cannot combine the head with anything yet, because the head must be combined with the fold of the rest, which does not exist until the recursion returns. So it descends first: 10 + foldRight(List(20, 30)), which needs 20 + foldRight(List(30)), which needs 30 + foldRight(Nil). Only at the end does foldRight(Nil) give 0, and the additions happen on the way back up: 30 + 0 = 30, 20 + 30 = 50, 10 + 50 = 60. Three pending frames were kept on the stack. Written out: 10 + (20 + (30 + 0)), parentheses nesting on the right.

For + the two answers coincide because addition is associative. Replace + with :: and they no longer do: foldRight(Nil)(_ :: _) rebuilds the list in the same order, because the last element is consed first, while foldLeft(Nil)((acc, h) => h :: acc) reverses it. That is why map, filter and concat are written with foldRight in the code above, and reverse with foldLeft: the choice of fold is the choice of which way the parentheses nest.

4. OO/FP Mixed Design

The mixed OO/FP approach in Scala gives you method chaining (like Java streams), foreach/map support for for-comprehensions, and a clear separation of contract, construction, and algorithms. Many algorithms share a common fold structure and can be refactored to use foldRight.

Editor's note

map can be expressed as foldRight(Nil())(f(_) :: _), and filter as foldRight(Nil())((a,b) => if p(a) then a::b else b). This is the essence of fold-based refactoring.

For mutable structures, algebraic data types cannot be used: we use a trait + private implementation in the companion object. The implementation holds an optional (head, tail) pair in a var; if the head is empty the tail is empty. Note that mutable operations may keep the same signature as their immutable counterparts, just returning this (fluent style), so in principle mutable and immutable collections can share an interface; the implementation, however, is trickier — immutability is easier:

Oral exam

The slides ask: what would happen with l.append(l)? The last node of l gets ht = Some((h, l)), i.e. it points back to l itself: the list becomes cyclic and toList (or any traversal) never terminates. This aliasing hazard simply cannot arise with the immutable version, where l.append(l) builds a new list and l.append(l) == l is false.

On performance: mutable structures win when frequently changed, but clever immutable structures (e.g. immutable red-black trees) offer logarithmic-time updates by sharing most of the original structure. Immutable collections are intrinsically thread-safe, can be freely shared, and suit information-extraction pipelines; side effects on mutable structures can be tricky.

5. Scala Collections Framework

Scala's collections framework is one of the richest in any language, declared goals: easy, concise, safe, fast, parallel, universal. The architecture is layered:

  • scala.collection — base traits (Iterable, Seq, Set, Map)
  • scala.collection.immutable — immutable implementations
  • scala.collection.mutable — mutable implementations

The root trait is IterableOnce, which only requires an iterator method. Iterable adds template methods like fold, flatMap, map, etc.

Architecture

Seq splits into LinearSeq (optimised head/tail: List, LazyList) and IndexedSeq (optimised apply/length: Vector, Array, ArrayBuffer).

Explore the collection hierarchy in the diagram below:

Any class can join the framework by extending Iterable and implementing just iterator; all template methods (map, toList, ...) come for free:

class Fibonacci(n: Int) extends Iterable[Int]:
  override def iterator: Iterator[Int] = new Iterator[Int]():
    var counter = 0
    var prev = (0, 1)
    override def next(): Int =
      prev = (prev._2, prev._1 + prev._2)
      counter = counter + 1
      prev._1
    override def hasNext: Boolean = counter <= n

val fibs = Fibonacci(20)
val fibsAsStrings = fibs.map(i => s"Next one is $i")
val list = fibs.toList

Aliases and constructors: without any import, Iterable, Seq, IndexedSeq, Set, Map and List refer to the immutable versions in scala.collection.immutable; mutable ones must be named explicitly (mutable.ListBuffer, mutable.ArrayBuffer, mutable.HashSet, mutable.HashMap). Each trait's companion has a varargs apply: immutable Iterable/Seq/LinearSeq create a List, IndexedSeq creates a Vector, Set a HashSet, Map a HashMap; mutable Iterable/Seq/IndexedSeq create an ArrayBuffer. scala.Option is somewhat part of the framework too (it has map, filter, flatMap, fold).

Guidelines

Use immutable collections unless you have severe, measured performance issues; encapsulate mutability (prefer a private immutable var over a private mutable val). In interfaces stick to abstract types: Iterable, Seq, Set, Map (occasionally LinearSeq/IndexedSeq); never expose mutable structures, expose views instead. Local variables need no explicit type.

8. Nesting Constructs

Scala's constructs — class, abstract class, object, trait, def (and packages, which are very similar to objects) — nest arbitrarily: classes inside classes (inner classes, see also family polymorphism), classes inside objects (Java's static nested classes), methods inside methods (frequent with recursion), anonymous classes inside methods (local helpers). Anonymous classes are written new D() {} / new D(): override def b = 2, and a trait with a single abstract method can be filled with a lambda, Java-style: val t2: T2 = () => 4.

Scalability

The ability to nest constructs arbitrarily is what makes Scala scalable: the language grows with your needs, from a simple script to a large system.

9. Packages, Imports, Visibility

Packages in Scala are fully compatible with Java's, but sources need not live in a directory matching the package, and packages can define namespaces directly in source files (package a: ... as in C#); in Scala 3 top-level vals and defs can be defined directly in a package. Imports can appear at any point (fine-grained, no long lists at the top), can import a whole package or single/multiple members, can "statically import" the content of an object/val, and can create aliases. Default imports are scala.*, java.lang.*, and scala.Predef.* (the object providing println, ???, ...). Being nested in a package or object means having its definitions "imported": at each point of the code the visible identifiers are those of all enclosing packages/objects, the explicit imports written so far, and the defaults — imports also control which givens and extensions are available.

Visibility modifiers in Scala:

ModifierMeaning
privateVisible only within the enclosing class/object — and its companion: class and companion object share private members
protectedVisible to subclasses

protected[package]Visible to subclasses or within the package

The qualifier may name a package or an enclosing object; the slides' example (in package u05.structure, subpackages pa1.pa2):

class C:
  private object pri               // visible only by C's instances (and object C)
  private[pa2] object pri_pa2      // visible only up to package pa2
  protected object pro             // visible to subclasses
  protected[pa2] object pro_pa2    // visible to subclasses, or up to pa2
  def f(c: C) = print(C.g())       // WORKS: can see the companion's private stuff

object C:
  print(new C().pri)               // WORKS: can see the class' private stuff
  private def g() = 1

class E(c: C):
  print(c.pri_pa2, c.pro_pa2)      // WORKS (same package pa2); c.pri, c.pro would be errors

class F extends pa2.C:             // outside pa2
  print(pro_pa2)                   // WORKS (subclass); pri_pa2 would be an error

// A private constructor: only the companion factory can create instances
class CounterImpl private[structure] () extends Counter: ...
object Counter:
  def apply(): Counter = new CounterImpl

Instead of many private helper methods, the slides suggest nesting them in a single private object ImplementationHelpers inside the class (with import ImplementationHelpers.* to ease the calls). Remember that the level of accessibility is a key design factor.

Oral question

Why is private less frequent in Scala than in Java? Because the pattern "private field + public getter" is unnecessary thanks to uniform access. Also, private helper methods can be nested inside the single public method that uses them.

10. Abstract Types and Modelling

Scala supports abstract type members: a trait or abstract class can declare type T (or a bounded type T <: R), and subclasses must concretise it with type T = R before objects can be created. It is a form of type parameterisation where the abstracted types are members rather than parameters in brackets; abstract types can themselves be generic (type MySeq[T] = List[T]). Three applications: (1) aliases, as in scala.Predef (type String = java.lang.String, type Map[A, +B] = collection.immutable.Map[A, B], type Function[-A, +B] = A => B) — similar to import renaming but usable with generics, typically paired with a same-named factory def MySeq[T](elems: T*); (2) abstract modelling of concepts, as in ADTs; (3) path-dependent types, supporting family polymorphism (end of the course).

The Exams case study

The quintessential abstract modelling technique: define a system as a trait of abstract concepts (Student, Teacher, Course, Evaluation), then refine it progressively with concrete implementations.

Why this matters

This approach cannot be easily achieved in other mainstream languages. It lays the foundation for family polymorphism and mixin-based system composition.

11. Traits, Mixins, Linearization

Abstract classes are as in Java (translated to JVM abstract classes, single extension, no overhead). Traits are richer than Java interfaces: they can carry fields and concrete methods, and are compiled to interfaces plus static methods that the extending class calls as needed; a class can mix in many of them, and linearization stacks them from left (up) to right (down) as a sequence of decorations. Typical uses of traits: abstract concepts (like interfaces), rich interfaces, interfaces for strategies and type classes (Ordered[T], any FunctionN), class templates (partial classes to be extended many times), and stackable modifications — the key mixin property. A mixin is a unit of code, possibly partially implemented, that is "included" or "stacked in" rather than inherited: it gives reuse, not necessarily substitutability. When a class mixes in traits with super calls, Scala creates a linear chain that determines which implementation is invoked.

The test in the slides: BasicParser(Set('a','b','c')).parseAll("aabc".toList) is true, "aabcdc" gives false, the empty string true; with NonEmptyBasicParser(Set('0','1')), "0101" is true, "0123" is false and List() is now false. Note that NonEmpty refers to an unknown super — nothing similar exists in Java — hence abstract override.

Rich interfaces define a few abstract methods and many template methods derived from them—Iterable is the canonical example; another is scala.Ordered[T], which derives <, >, <=, >= from the single abstract compareTo (Ordered plays the role of Java's Comparable, Ordering that of Comparator):

Self-types (trait T { name: Type => ... }) express that a trait can only be instantiated when mixed into a class/trait of the given type; name is a reference equal to this but typed Type. The trait is not a subtype of that type: it is inheritance without subtyping, achieved internally by delegation/decoration — the typical way to create mere "decorations" and to declare a dependency without inheriting:

If the type is omitted (self =>), the name is just an alias for this of the enclosing class, used inside inner or anonymous classes where this would refer to the inner object:

trait FunctionOption[-A, +B]:
  self =>
  def apply(a: A): Option[B]
  final def andThen[C](f: FunctionOption[B, C]): FunctionOption[A, C] =
    new FunctionOption[A, C]:
      override def apply(a: A): Option[C] =
        self.apply(a).flatMap(b => f.apply(b))   // this.apply(a) would not compile: this is the new object

Linearization is how Scala renders multiple inheritance on the JVM: by decoration (inheritance + delegation). For a class C extends Base with A with B, the linearization is C → B → A → Base (each trait's own parents are inserted after it, and no class ever appears twice). The super call in each trait refers to the next element in this chain: in NonEmptyBasicParser, NonEmpty uses the BasicParser part as super. When programming, "things just work".

12. Exports and Delegation

Scala 3 introduces export, which eliminates the boilerplate of delegation. Instead of manually writing forwarding methods, you export the members of a delegated object:

Principle

Prefer delegation over inheritance (least power principle). Inheritance opens a class to subclasses too much and hardly deals with multiple reuses; substitutability is better achieved by traits alone, focusing on the contract, and delegation combined with refined access modifiers is preferable. The problem with delegation was the boilerplate of forwarders: an export directly transfers the visibility of the "content" of a stable member to the outside, with almost the same syntax as imports. In the example, MultiCounter and FancyCounter are Counters by substitutability only, with no inheritance of implementation; c2.decrement() on a FancyCounter does not compile, while c2.creationTime() does.

13. Variance in Generics

Scala uses declaration-site variance (unlike Java's use-site wildcards). A type parameter can be:

  • Covariant (+A): Container[Cat] <: Container[Animal]
  • Contravariant (-A): Handler[Animal] <: Handler[Cat]
  • Invariant: the default

The compiler checks that a variance annotation makes sense with respect to Liskov's substitution principle: with List[+T] we get List[Int] <: List[AnyVal], but a setter taking T would be rejected because T occurs in contravariant position. Type parameters can also be constrained by bounds: [A <: Upper], [A >: Lower], or both. (Definition-site variance was studied in Igarashi & Viroli, ECOOP 2002.)

Oral question

Why can't Stack[T] be covariant? Because push(t: T) puts T in contravariant position: if Stack[Int] <: Stack[Any] were allowed, val s: Stack[Any] = Stack[Int](10, 20); s.push("a string") would corrupt an Int stack. The solution is def push[R >: T](r: R): CoStack[R]: pushing a String onto a CoStack[Int] is allowed but yields a CoStack[Any].

Covariance is also what allows a single empty-list object. The slides' CoList:

enum CoList[+T]:
  case Cons(head: T, tail: CoList[T])
  case Nil                               // a single object, of type CoList[Nothing] <: CoList[T] for every T

object CoList:
  def apply[T](elems: T*): CoList[T] = elems.foldRight[CoList[T]](Nil)(Cons(_, _))

// would not type-check with an invariant CoList[T]
val ll: CoList[CoList[Any]] = CoList(CoList(10, 20, 30), CoList("a", "b", "c"), CoList(10, new java.util.Date, "a string"))

14. Extension Methods

Languages are shifting towards less rigidity and more terseness (DSLs, scripting, agility over predictivity); Scala's remaining flexibility features, all FP-oriented, are extension methods, given instances and automatic conversions — to be used with care, capturing and documenting the abstraction. Extension methods let you add new methods to existing types after their definition, only in certain programming contexts: an application of the adapter pattern without writing the adapter class. An extension method is defined outside the class, translates to a method taking the receiver as first argument, and can be called with dot notation whenever it is in scope. Typical uses: adding operators to existing classes, separating data from operations and recombining flexibly, giving an OOP flavour on top of pure FP:

Pure FP with extensions

Extension methods enable a purely functional style where you define types via enums/case classes and add operations as extensions in companion objects. This separates data from operations and recombines flexibly.

Do we really need OOP? Surprisingly, many cases can be solved with just enums + extension methods + delegation. Use OOP where it naturally fits (controllers, stateful models).

15. Contextual Programming

Scala 3's given/using mechanism separates inputs from context. Context parameters can be inferred from the scope, avoiding verbose explicit passing—perfect for strategies, configurations, and type classes.

Term inference

A given instance is a canonical term of a type that the compiler can synthesise in a scope: a parameter declared with using can be passed explicitly (f(using context)(input)) or omitted (f(input)), in which case the compiler looks for a given of that type; summon[T] recovers it by hand, and import X.given imports only the givens of X. Scala 2 did this with the much-criticised implicit mechanism; Scala 3's given/using is more direct and intent-revealing.

Context bounds (def m[A: B]) enable ad-hoc polymorphism: the method can be invoked with a type A only if a given of type B[A] exists in scope, recovered inside with summon[B[A]]. This is not a trick: it paves the way to hierarchies of "contexts" as type classes, a method being applicable to few selected types (those with the context):

Given conversions automate the adapter pattern when legacy libraries must interoperate with new ones: provide a given instance of scala.Conversion[-I, +O] (a subtype of I => O) and the compiler inserts the conversion where an I is used as an O. The companion object of the target type is the proper place for it:

case class Point(n: Int, m: Int)
object Point:
  given Conversion[(Int, Int), Point] with
    def apply(t: (Int, Int)): Point = Point(t._1, t._2)
  given Conversion[List[Int], Point] = l => Point(l.head, l.tail.head)   // by a literal

def pointToRadius(p: Point) = Math.sqrt(p.n * p.n + p.m * p.m)
println(pointToRadius((3, 4)))         // 5.0: the tuple is converted
println(pointToRadius(List(3, 4)))     // 5.0
println(summon[((Int, Int)) => Point]((10, 20)))   // Point(10,20): checks a conversion is active

Check Your Understanding

Explain the difference between foldLeft and foldRight. Which one is tail-recursive?

foldLeft processes elements left-to-right and is tail-recursive: the accumulator is computed first, then passed to the next iteration. foldRight processes right-to-left: it pushes recursive calls onto the stack and combines on return. foldRight is not tail-recursive, but it expresses structure-preserving transformations naturally (e.g., map, filter, concat).

Desugar the expression for x <- List(1,2); y <- List(3,4) if x+y > 3 yield (x,y) into flatMap/map/filter calls.

List(1,2).flatMap(x => List(3,4).filter(y => x + y > 3).map(y => (x, y))), giving List((1,3), (1,4), (2,3), (2,4)). Rule: every generator but the last becomes a flatMap, the last a map (a foreach for for ... do), guards become filter (strictly withFilter, the lazy variant) and x = e definitions become a map to a tuple.

Why does :: need to be right-associative in Scala?

Because the receiver of a prepend is the list, on the right: a :: b :: Nil() must group as a :: (b :: Nil()), i.e. Nil().::(b).::(a) — prepend b to the empty list, then prepend a. With left associativity a :: b would call :: on the element a, which has no such method. Any method whose name ends in : gets this treatment, so the list reads left-to-right while being built right-to-left by O(1) prepends; and since a pattern h :: t means ::(h, t), the same name serves construction and extraction.

Compare the three immutability strategies. When would you use each?

Mutable val (e.g., val buf = ListBuffer()): for hot loops with verified performance need. Immutable var (e.g., var list = Seq()): for domain concepts that are naturally mutable (register state, counters). Immutable val (e.g., val list = List()): preferred FP style; the data never changes, new versions are created. Always push side-effects outward.

What is trait linearization? Give an example with NonEmpty and BasicParser.

Linearization resolves which super implementation is called when traits are stacked: the class and its parents are ordered from right to left of the extends ... with ... clause, each followed by its own parents, with no class listed twice; super in a trait means "the next one in the chain", which is unknown when the trait is written (hence abstract override). For NonEmptyBasicParser extends BasicParser with NonEmpty[Char], the linearization is NonEmptyBasicParser → NonEmpty → BasicParser → Parser (then AnyRef, Any). NonEmpty's super.parse(t) calls BasicParser's parse: on the JVM this is decoration, i.e. inheritance plus delegation.

How do you make Stack[T] covariant? What is the key change to the push method?

Declare trait CoStack[+T] and change push to use a lower type bound: def push[R >: T](r: R): CoStack[R]. This prevents inserting the wrong type by widening the result type.

What is the difference between import and export in Scala 3?

import brings names into the current scope for use. export re-exports stable members of a value to the enclosing scope, making them part of the public API—it is the inverse of import, and it enables zero-boilerplate delegation.

Explain how abstract types enable the Exams modelling approach.

The Exams trait declares abstract types (type Student, type Teacher, type Course, type Evaluation) that are concretised by subclasses (override type Student = String). This defines a whole “system” of concepts that can be refined progressively, keeping all mutual dependencies consistent without type parameters.

What is a self-type, and how does trait ProducerUtils { producer: Producer => ... } differ from trait ProducerUtils extends Producer?

A self-type declares that the trait can only be mixed into a class of the given type, and gives this (under the name producer) that type inside the trait. Unlike extends, it creates no subtyping: ProducerUtils is not a Producer, it merely requires one, so it works as a pure decoration attachable to any implementation (new ConstantProducer("a") with ProducerUtils). It is inheritance without subtyping, i.e. a declared dependency, achieved by delegation.

What do using parameters and context bounds add over ordinary parameters? What does def max[T: MyOrdering](...) mean?

A using parameter separates context (a strategy, a configuration) from inputs: it can be passed explicitly with using, or inferred by the compiler from the given instances in scope (term inference). [T: MyOrdering] is a context bound: the method can be called with a type T only if a given MyOrdering[T] exists in scope, retrievable inside with summon[MyOrdering[T]]. This is ad-hoc polymorphism: the method applies to exactly those types for which the context has been defined, the basis of type classes.

How is an extension method compiled, and when is p.length resolved to extension (p: Point2D) def length?

The extension translates to an ordinary method whose first parameter is the receiver (length(p)); the call p.length is rewritten to it by the compiler only when Point2D itself has no length member and the extension is in scope (defined or imported, e.g. import Point2DOperators.*). It is the adapter pattern without the adapter class, and it allows a pure-FP style: data as enums/case classes, operations as extensions in the companion object.
