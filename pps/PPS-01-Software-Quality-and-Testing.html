1. Good Design, Abstraction, and Process

Software accounts for a remarkably large share of the world economy — approximately 15 percent of global GDP indirectly, with estimates that the digital economy will reach 30 percent by 2030. Yet producing good software is costly: productivity is far below 100 lines of code per day per person when considering the whole lifecycle, from requirements through maintenance.

Key insight

Being able to write very high quality software means having a wide set of key skills — technical and organisational — the most important of which is a high ability in capturing and managing abstraction.

The need for a software process

Software development faces inherent challenges: software tends to be very complex, pieces of software are often easy to prototype but difficult to get right, and error-prone code can be extremely hard to debug. The time from prototype to correct, deployed software can be enormous. Without a disciplined process, software projects can and will simply fail.

Steps of software development

These steps are not strictly waterfall — modern processes iterate through them:

  • Requirement engineering — elicitation, analysis, and specification: understanding the problem, gathering and formalising requirements
  • Design — defining the key elements of the solution, by incremental refinement from architecture to details
  • Implementation — actual development: choosing technologies and coding
  • Post-implementation — testing, deployment, maintenance: the resource-demanding phase
Frequently forgotten facts (R. Glass)

A 10% increase in problem complexity leads to 100% increase in solution complexity. Good programmers are up to 30 times better than mediocre ones. The two causes of project runaway are instability of requirements and optimistic estimation. Error detection and removal accounts for 40% of development cost. Rigorous review removes 90% of errors. Maintenance consumes 40% to 80% of overall cost.

The abstraction principle

Abstraction is the single concept behind a variety of pragmatic concretions or individuals. In software engineering specifically, abstraction helps:

  • Mitigate opacity — code directly captures the idea, not bloated with unnecessary details
  • DRY principle — Don't Repeat Yourself, now or in the future
  • DIP principle — Dependency Inversion: depend on abstractions (interfaces), not on implementation details (classes)

2. Software Quality Criteria

Definitions of software quality

Classic definitions: "well translating future needs into measurable characteristics" (Deming) and "meeting the customer needs, with freedom from deficiencies" (Juran). There are multiple perspectives on what software quality means:

  • Transcendental — philosophical, promoting elegance and coherence
  • Product — quantifiable and measurable characteristics
  • Manufacturing — conforming to agreed requirements
  • User — satisfying the users of the produced software

Internal vs external quality

External quality determines the fulfilment of stakeholder requirements: correctness, usability, efficiency, reliability, integrity, adaptability, accuracy, and robustness. Internal quality determines your ability to move forward on a project: maintainability, flexibility, portability, reusability, readability, testability, and understandability.

Oral exam tip

People typically perceive external quality, but internal quality is the key means to achieve external quality. Modern approaches require internal features to be readily observable. Aiming at external quality while bypassing internal quality is often the root cause of project failure. Be ready to explain this distinction.

EfficiencyGood performance and scalability

MaintainabilityAdaptability, evolvability, control

3. Code Quality, Technical Debt, and Code Smells

Code quality as a precondition

Software quality is a combination of code, data, process, tools, platform, and library quality. Code quality is a necessary precondition to overall software quality. It focuses on the shape of code and how code can be evolved to achieve internal quality, which then impacts external quality.

Technical debt

Technical debt is the extra development work that arises when code that is easy to implement in the short run is used instead of applying the best overall solution. It is the "patch" problem: one quickly solves a problem sub-optimally, delaying improvement. Sooner or later, this costs more than fixing it immediately. Sometimes technical debt is necessary or unavoidable, but it must be managed consciously. Overall it is a measure of the distance to "complete quality" — almost impossible to measure, so one mostly proceeds empirically.

public class Configuration {
  private List<String> data;

  public void loadFromFile(final String fileName) {
    try {
      this.data = Files.readAllLines(Paths.get(fileName));
    } catch (IOException e) {
      System.out.println(e); // Technical debt here!
    }
  }

  public List<String> getData() {
    return Collections.unmodifiableList(this.data);
  }
}
Technical debt

The catch block above just prints the exception instead of properly handling it or propagating it. This is classic technical debt — quick to write now, but if the file is missing the program silently continues with data still null, and a later getData() fails with a NullPointerException far away from the real cause.

Code smells

Code smells are surface indications in source code that possibly indicate a deeper problem, violating fundamental design principles and negatively impacting quality. They are not necessarily bugs, but they typically create technical debt. Common examples include code duplication, bad names, abstraction jumps, partial implementations, and violation of simple OO principles.

Example 1: Neglecting code conventions

Every language has conventions beyond its syntax: style of names, spacing, formatting, obsolete constructs to avoid. In Java: never prefix interfaces with I, use camelCase, never declare two variables on the same line, do not abuse obscure operators.

Example 2: Not adhering to modern rules of effectiveness

Inspired by Effective Java by Joshua Bloch: know and use your libraries, minimise accessibility of class members, minimise mutability, favour composition over inheritance, prefer interfaces over abstract classes, program against interfaces not classes.

Example 3: Not using clean coding techniques

Code should be as readable as good prose, always reveal the intent, and be clear to all programmers regardless of skill level.

Meaningful names

  • Use intention-revealing names — elapsedTimeInDays is better than d
  • Use pronounceable names, not acronyms
  • Use searchable names — MAX_CLASSES_PER_STUDENT = 7 is wonderful
  • No prefixes in variables or interfaces
  • Class names are nouns or noun phrases (TransactionProcessor, not Processing)
  • Function names are typically verb phrases

Good functions and methods

  • Should be small (10 lines), simple, and quickly understandable — factor out what is needed in private methods
  • Do one thing and only one thing (SRP and DRY)
  • Work at one level of abstraction (DIP and ISP) — e.g. don't mix string manipulation with other stuff
  • Organise them top to down, like a story; a long name is better than a short obscure one
  • 0, 1, or 2 arguments — consider wrapping more in classes/builders
  • Have no side-effects unless that is the only purpose (as in setters)

Comments and formatting

Comments tend to compensate for bad code: better rewrite the code so it says what the comment would. Javadoc public APIs (interfaces above all), not private members; never comment code out, never "section" methods with comments. Formatting: adhere to the group's practice (which constrains, not opens, the community standard), use blank lines to separate concepts and keep close concepts close, put dependent functions below their callers, 100-120 characters per line.

Why good code matters

Bad code means more time in maintenance, and Leblanc's law says "later equals never". Good code is fully tested, integrated, reviewed, refactored and readable: elegant, simple, few dependencies, reads like prose. Adopt the boy-scout attitude: leave the campground cleaner than you found it.

Needless repetition example

private Enemy createEnemy() {
  int type = rand.nextInt(2);
  if (type == 0) {
    return new Cactus(800, cactus1.getWidth() - 10,
            cactus1.getHeight() - 10, cactus1);

Needless complexity example

public class StatValuesImpl implements StatValues {
  private static final int NO_MAX = -1;
  private int actual;
  private int max;

  public void updateActual(int value) {
    if (actual + value <= 0) {
      actual = 0;
    } else {
      if (max != NO_MAX && actual + value > max) {
        actual = max;
      } else {
        actual = actual + value;
      }
    }
  }
}
Why this matters

The updateActual method mixes three concerns: clamping to zero, capping at a maximum, and normal addition. A simpler design would separate these concerns into distinct methods or use a well-known clamp pattern. Needless complexity like this makes code harder to test, reason about, and modify.

6. Quality Framework: OO Paradigm

Object-orientation is the dominant paradigm in mainstream software engineering. In the Tiobe index all top programming languages except C are OO (the first is Python, around 23%). Big applications tend to use various languages, but the complex part is typically done in OO (Java, C#). Most software engineering books apply to OO languages, and patterns like GoF design patterns, modelling languages like UML, and quality principles are all rooted in the OO world. Paradigms, languages and IDEs might significantly affect quality issues.

Key elements of OO

  • Object — an entity with identity, state, and behaviour
  • Field — a piece of object state holding another object or value
  • Method — handler of a request-reply message received by objects
  • Interface — collection of public method signatures defining a contract (a type)
  • Class — code implementing an interface, a template to create objects

Key relationships in OO

  • Dependency (use-a) — class A uses class B
  • Association / Aggregation / Composition (has-a) — an instance of A holds a reference to an instance of B. Association: independent life of A and B, no ownership. Aggregation: independent life, but A owns B. Composition: "death" relationship — if A dies, B dies
  • Inheritance (is-a) — a class inherits properties of another, with subtyping and dynamic dispatch
  • Implementation (is-a, conforms-to) — a class implements all methods of an interface; critically, with a subtyping relation
Oral exam tip

Be able to explain the OO relationships with concrete examples. The Controller and Device example from the slides is the running case study throughout the quality and testing modules — make sure you understand how interfaces, implementations, and dependencies connect.

7. Software Methodologies and the Agile Manifesto

Critics of the waterfall model

The waterfall model (sequential phases: requirements, design, implementation, testing, maintenance) has three fundamental problems:

  1. Instability of requirements — requirements change, forcing a full cycle restart
  2. Difficulty in foreseen detailed design — many design choices emerge during coding and testing
  3. Problems with late testing — the longer you wait, the more code is built on top of buggy abstractions

The Agile Manifesto

The Agile Manifesto (2001), signed by the Agile Alliance, started from criticising the waterfall model and defined 12 principles. The key idea: do not refuse change, rather embrace it.

Principles that most affect coding

  • Highest priority: satisfy the customer through early and continuous delivery of valuable software
  • Welcome changing requirements, even late in development
  • Deliver working software frequently (weeks to months, preferring shorter timescales)
  • Working software is the primary measure of progress
  • Continuous attention to technical excellence and good design enhances agility
  • Simplicity — the art of maximising the amount of work not done — is essential

Agile programming as philosophy in this course

The course adopts an agile philosophy throughout: break development into short pieces and periods. In each period: (1) identify requirements, (2) identify architectural decisions, (3) write key interfaces, (4) write deep tests, (5) develop code until tests pass, (6) review/improve/refactor before merging. This promotes tools for continuous integration and emphasises people interactions over processes and tools.

8. Agile Unit Testing and Test-Driven Development

The Three Laws of TDD

  1. You may not write production code until you have written a failing unit test.
  2. You may not write more of a unit test than is sufficient to fail (and not compiling is failing).
  3. You may not write more production code than is sufficient to pass the currently failing test.

The TDD cycle: Red-Green-Refactor

The main methodology follows three steps in 10-20 minute cycles:

  1. Red — Write a test that fails
  2. Green — Get the test to pass (write the simplest production code)
  3. Refactor — Clean up any code added or changed in the prior two steps
Why be so strict?

Tests become a specification of intended behaviour, useful for understanding goals and documenting code. Tests dramatically reduce bug identification and resolution. The ability to quickly test gives freedom to refactor. Traditional cycle: Design, Code, Test. TDD cycle: Test, Code, Design/Refactor.

Kinds of tests

  • Unit test — isolating a single piece of code
  • Integration test — considering interaction between components
  • Functional test — examining code at the boundary of its public API
  • Stress test — considering actual workload and resource impact
  • Acceptance test — considering all aspects of user experience

Roles of unit tests

Unit tests serve multiple purposes: regression prevention, progress measurement, specification, implementation guidance (as in TDD), solidity enforcement (edge cases), and legacy restoration (refactoring old code).

Clean tests

Test code is a system in itself and should be very clean. Key recipes: readability is paramount (clarity, simplicity, density of expression), use consistent naming conventions (e.g. name the feature being tested), adhere to the build-operate-check pattern (also called Arrange-Act-Assert), strongly prefer one assert per test, single concept per test (not one test per method!). Tests should be fast, independent, repeatable, self-validating, and timely. The lab stresses that TDD formalises the "what" before the "how": tests should read as specifications or living documentation.

JUnit 5 recall (from the lab)

Annotations in org.junit.jupiter.api: @Test, @BeforeEach/@AfterEach (run before/after each test), @BeforeAll/@AfterAll (once per class), @Disabled, @Timeout. Assertions in Assertions: assertEquals(expected, actual), assertTrue, assertFalse, assertNull/assertNotNull, assertSame, assertThrows(Class<T>, Executable) (returns the exception), fail(). Tests live in the same package as the code but in a different source folder; they are often larger than the code they test.

Scala tests as "speakable specification"

Scala testing frameworks like ScalaTest allow tests to read like natural language specifications (a preview; the slide uses the older FlatSpec name, which in current ScalaTest is AnyFlatSpec):

class EmptySetSpecification extends FlatSpec {
  "An empty Set" should "have size 0" in {
    Set.empty should have size (0)
  }

  it should "raise NoSuchElementException when head is called" in {
    an [NoSuchElementException] should be thrownBy (Set.empty.head)
  }
}

9. TDD Walkthrough: The DeviceManager Example

This section walks through the complete TDD example from the course slides: a Device and DeviceManager system. The interfaces are defined first, then tests drive the implementation.

public interface Device {
  void on();
  void off();
  boolean isOn();
  boolean isWorking();
}

A device can be switched on and off. It can also become non-working, meaning it is off and cannot be switched on again.

public interface DeviceManager {
  void addDevice(Device device);
  List<Device> devices();
  void switchAllOn();
  void switchAllOff();
  boolean allOn();
  boolean allWorking();
}

A manager that keeps track of devices and provides bulk operations: switching all on/off, checking status.

public class DeviceImpl implements Device {
  private boolean on = false;
  private boolean works = true;

  public void on() {
    if (this.isWorking()) { this.on = true; }
  }

  public void off() { this.on = false; }

  public boolean isOn() { return this.on; }

  public boolean isWorking() { return this.works; }

  public void stopWorking() {
    this.works = false;
    this.on = false;
  }
}
public class DeviceImplTest {
  private DeviceImpl device;

  @BeforeEach
  public void setUp() { this.device = new DeviceImpl(); }

  @Test public void isInitiallyOff() { assertFalse(device.isOn()); }

  @Test public void canBeSwitchedOn() { device.on(); assertTrue(device.isOn()); }

  @Test public void canBeSwitchedOff() { device.on(); device.off(); assertFalse(device.isOn()); }

  @Test public void onIsIdempotent() { device.on(); device.on(); assertTrue(device.isOn()); }

  @Test public void canStopWorking() {
    device.stopWorking();
    assertFalse(device.isWorking());
    device.on();
    assertFalse(device.isOn());
  }
}
public class DeviceManagerImpl implements DeviceManager {
  private List<Device> devices = new ArrayList<>();

  public void addDevice(Device device) { this.devices.add(device); }

  public List<Device> devices() { return Collections.unmodifiableList(this.devices); }

  public void switchAllOn() { this.devices.forEach(Device::on); }

  public void switchAllOff() { this.devices.forEach(Device::off); }

  public boolean allOn() {
    for (final Device device : this.devices()) { if (!device.isOn()) return false; }
    return true;
  }

  public boolean allWorking() {
    for (final Device device : this.devices()) { if (!device.isWorking()) return false; }
    return true;
  }
}
public class DeviceManagerImplTest {
  private DeviceManager manager;
  private List<Device> devices;

  @BeforeEach
  public void init() {
    this.manager = new DeviceManagerImpl();
    this.devices = new ArrayList<>();
    for (int i = 0; i < 3; i++) {
      Device d = new DeviceImpl(); d.on();
      this.devices.add(d); this.manager.addDevice(d);
    }
  }

  @Test public void switchAllOn() {
    manager.devices().get(0).off();
    manager.devices().get(2).off();
    manager.switchAllOn();
    assertTrue(manager.allOn());
  }

  @Test public void someNotWorking() {
    DeviceImpl device = new DeviceImpl();
    device.stopWorking();
    manager.addDevice(device);
    assertFalse(manager.allWorking());
  }
}
Editor's note

The tests above follow the build-operate-check pattern: arrange (set up devices), act (call switchAllOn or add a broken device), assert (check allOn or allWorking). Each test focuses on a single concept. The slides' full test class also has canBeSwitchedOnTwice, canBeSwitchedOffTwice, canBeSwitchedMultipleTimes (a private helper loops on/off N_OF_ATTEMPTS = 10 times), initiallyWorks and typicallyWorks: many small tests naming one feature each. Note that devices() returns an unmodifiableList, enforcing immutability at the API boundary — a key quality practice from Effective Java. The slides' recipe: generate default implementations with the given names, generate one test class per class to implement, then complete the implementation; code and tests might not be perfect at first and should be refactored together.

10. Design Principles: DRY, KISS, and SOLID

DRY — Don't Repeat Yourself

Duplication is the quintessential code smell. When code similar to existing code is needed, the temptation is to cut, paste, and modify. This creates strong dependencies: errors propagate and evolve without control, and the system becomes extremely rigid. Duplication can be remedied by proper refactoring interventions; tools can detect syntactic duplications, and in some paradigms (e.g. FP) one is very aggressive in applying DRY.

// Before: repeated format logic
public class Logger {
  public static void logPrintString(final String s) {
    System.out.format("[Print] %s%n", s);
  }
  public static void logPrintStrings(final String[] array) {
    for (int i = 0; i < array.length; i++) {
      System.out.format("[Print] %s%n", array[i]);
    }
  }
}
// After: DRY applied, reusing the single-element version
public class LoggerDry {
  public static void logPrintString(final String s) {
    System.out.format("[Print] %s%n", s);
  }
  public static void logPrintStrings(final String[] array) {
    for (int i = 0; i < array.length; i++) {
      logPrintString(array[i]); // reused, no duplication
    }
  }
}

KISS — Keep It Simple, Stupid

"Most systems work best if they are kept simple rather than made complicated" (a design practice noted by the U.S. Navy in 1960). Never use complex solutions when easier ones are possible. When a complex solution emerges, think twice. Do not create problems that customers did not ask to be solved. Variants: Occam's razor, "less is more" (Mies van der Rohe), "make simple tasks simple" (Stroustrup), "everything should be made as simple as possible, but no simpler" (Einstein).

// KISS: avoiding a tricky API, using straightforward println
public class LoggerKiss {
  public static void logPrintString(final String s) {
    System.out.println("[Print] " + s); // simpler than format
  }
  public static void logPrintStrings(final String[] array) {
    for (final String s : array) { // for-each instead of indexed loop
      logPrintString(s);
    }
  }
}

The SOLID Principles

The five SOLID principles are cornerstones of good design and programming, generalising OO. In OO they mostly apply to classes (code) and interfaces (abstraction), but the course needs to stay general and reason in a multi-paradigm way. Click a card to flip it:

SRP in action: moving responsibility away

public class LoggerSrp {
  public static void logPrintString(final String s) {
    System.out.println(PrefixFormatter.printPrefix() + " " + s);
  }
}

class PrefixFormatter {
  static String printPrefix() { return "[Print]"; }
}

OCP in action: making logPrintString unmodifiable

public final class LoggerOcp {
  private final LogFormatter logFormatter;

  public LoggerOcp(LogFormatter logFormatter) { this.logFormatter = logFormatter; }

  // This method now won't likely be changed...
  public void logPrintString(final String s) {
    System.out.print(logFormatter.message(s));
  }
}

// ...can be changed by extension, instead of modification
class LogFormatter {
  protected String printPrefix() { return "[Print]"; }
  public final String message(String s) { return printPrefix() + " " + s; }
}

ISP in action: a generalised, client-specific interface

// Using a general Iterable: can now pass a List, a Set, or Arrays.asList(array)
public final void logPrintStrings(final Iterable<String> strings) {
  for (final String s : strings) { logPrintString(s); }
}

DIP in action: depending on abstractions

public class LoggerDip {
  interface Console { void print(String s); void println(String s); }
  interface Formatter { String message(String s); }

  private final Formatter formatter;
  private final Console console;

  public LoggerDip(Formatter formatter, Console console) {
    this.formatter = formatter;
    this.console = console;
  }

  public void logPrintString(final String s) {
    console.print(formatter.message(s));
  }
}

LSP in action: enforcing semantic substitutability

What if an implementor of Console messes with the relation between print and println? An abstract base class can fix the semantics with a template method, so that every subclass stays substitutable:

abstract class AbstractConsole implements LoggerLsp.Console {
  public final void println(String s) {
    this.print(s);
    this.lineFeed();
  }
  protected abstract void lineFeed();
}

class SystemOutConsole extends AbstractConsole {
  @Override public void print(String s) { System.out.print(s); }
  @Override protected void lineFeed() { System.out.println(); }
}

11. Refactoring and Design Patterns for Quality

Refactoring

Refactoring is the process by which code (or tests) is evolved without changing functionality: the goal is to improve quality, not to add features. Two objectives: enhance readability/generality, or prepare for change. Good tests are key to confidence in the outcome. Basic techniques, from fine to coarse grained: rename variables, arguments, fields, methods and classes; change signatures (removing or combining arguments); extract (private, then public) methods, static methods, constants; substitute inheritance with delegation; move code into new classes or base classes; change constructors into static factories; and finally, apply design patterns.

Design patterns

Design patterns capture experience on existing design to be reused as-is. They are not invented but extracted from analysing recurrent OO design solutions. The "Gang of Four" (GoF) book (Gamma, Helm, Johnson, Vlissides) describes 23 patterns across three categories: creational (Factory Method, Abstract Factory, Builder, Prototype, Singleton), structural (Adapter, Bridge, Composite, Decorator, Facade, Proxy), and behavioural (Interpreter, Template Method, Chain of Responsibility, Command, Iterator, Mediator, Memento, Observer, State, Strategy, Visitor, ...).

Why design patterns?

Patterns make your code more easily understandable by just recalling them by name. They make code more flexible and more open to change. They make your code much better organised. The course covers several key patterns in depth.

Strategy

A class includes an algorithm believed to easily change or come in different versions. The solution: capture the algorithm in an interface (Strategy), implemented by different classes. The main class takes a Strategy in its constructor or setter. This is a quintessential application of SRP and DIP; anonymous classes and lambdas simplify its adoption. Example: java.util.Comparator / java.util.TreeSet. In the device example, a devicesByName(String) method is generalised so that the manager is prepared for a variety of different searches:

// Strategy: filter devices by a predicate (functional strategy)
// replaces devicesByName(s), which hard-coded device.getName().equals(s)
public List<Device> filteredDevices(Predicate<Device> predicate) {
  List<Device> list = new ArrayList<>();
  for (Device device : devices) {
    if (predicate.test(device)) { list.add(device); }
  }
  return Collections.unmodifiableList(list);
}

Template Method

A class includes an algorithm whose parts are expected to change. The solution: capture the variable algorithm parts as abstract methods, called by concrete (template) methods. A concrete subclass implements the abstract methods. It is another natural application of SRP, with inheritance instead of delegation: the choice of algorithm happens at compile-time rather than run-time. Template method is almost mandatory in any class hierarchy; default methods in interfaces facilitate its adoption. Example: java.io.InputStream. In the device example, a BrokenDeviceImpl (which may break when switched off) initially duplicated all of DeviceImpl; a base class factors the common code:

public abstract class AbstractDevice implements Device {
  private boolean on = false;
  private boolean working = true;

  public void off() {
    this.doWhenOff();   // template method calls the abstract hook
    this.on = false;
  }

  protected abstract void doWhenOff(); // subclasses implement this

  public void on() { if (this.isWorking()) { this.on = true; } }
  public boolean isOn() { return this.on; }
  public boolean isWorking() { return this.working; }
  protected void stopWorking() { this.working = false; }
}

public class DeviceImpl extends AbstractDevice {
  protected void doWhenOff() { } // nothing special happens
}

public class BrokenDeviceImpl extends AbstractDevice {
  protected void doWhenOff() {
    if (this.isOn() && Math.random() > 0.95) {
      this.stopWorking(); // 5% chance of breaking when turned off
    }
  }
}

Decorator

An interface has many implementations to be flexibly mixed. The solution: a decorator class implements the interface and accepts an element of the same kind (as in strategy), to which most method calls are redirected, and which can be extended in different ways. A chain of decorations can be created, and the mix of behaviours is selected at run-time. This is a mixture of strategy and template method. Example: java.util.stream.Stream. In the device example, both the "broken" behaviour and a new "variable intensity" feature are turned into decorators wrapping a base Device, so features can be mixed freely:

// Decorator adds intensity control without modifying base Device
public class DeviceWithIntensityImpl implements Device {
  private final Device device;
  private int intensity;

  public DeviceWithIntensityImpl(Device device) {
    this.device = device;
  }

  public void increaseIntensity() { this.intensity++; }
  public int getIntensity() { return intensity; }

  // Delegating to the wrapped device
  public void on() { device.on(); }
  public void off() { device.off(); }
  public boolean isOn() { return device.isOn(); }
  public boolean isWorking() { return device.isWorking(); }
}

// Usage: compose decorators (BrokenDeviceImpl is now a decorator too)
Device d1 = new DeviceImpl("A");
Device d2 = new DeviceWithIntensityImpl(new DeviceImpl("A"));
Device d3 = new BrokenDeviceImpl(new DeviceImpl("A"));
Device d4 = new DeviceWithIntensityImpl(
            new BrokenDeviceImpl(
              new DeviceImpl("A")));

Proxy

Provide a surrogate (placeholder) for another object to control accesses to it: a wrapper with the same interface that delegates to the controlled object. This separates and encapsulates access logic, keeps the base class clean, can be made transparent to the client, and several stages of proxying can be cascaded. Principles safeguarded: SRP (core behaviour vs access control), DIP (client depends on interface, enabling transparent proxy use). Examples: optimising initialisation/use costs (lazy initialisation), transparent access to a remote object, limiting use or function (e.g. read-only collections).

Adapter

A class contains legacy behaviour that needs to be adapted to fit an interface someone expects. The solution: a thin adapter class implementing the target interface, delegating all needed work to the legacy class. It is needed when implementing the interface afterwards is not feasible, and often compensates a lack of design (e.g. in DIP you create an interface someone later has to adapt to; or you wrap bad legacy code). Example: java.util.Arrays.asList. In the device example a legacy Client was written against its own MyDeviceManager interface; following OCP we do not change the client, but fill the gap with an adapter:

// Adapter: connects a legacy Client expecting MyDeviceManager
// to the modern DeviceManager interface
public class MyDeviceManagerAdapter implements MyDeviceManager {
  final private DeviceManager manager;

  public MyDeviceManagerAdapter(DeviceManager manager) {
    this.manager = manager;
  }

  public void addSomeDevices(List<Device> list) {
    for (Device dev : list) { this.manager.addDevice(dev); }
  }

  public void switchOn(int position) {
    this.manager.devices().get(position).on();
  }

  public void switchOff(int position) {
    this.manager.devices().get(position).off();
  }
}

Abstract Factory

The decision on which versions of a group of classes to instantiate has to be taken dynamically. The solution: a factory interface with n factory methods (one per product interface); actual implementations define which concrete classes to use. Construction logic is thus separated from usage logic, and code becomes completely independent from the actual implementation. Factory Method (the factory is an actual class and n = 1) is a subcase, very used throughout libraries. Example: the static factories of java.util.stream.Stream.

public interface DeviceFactory {
  Device createStandardDevice(String name);
  Device createBrokenDevice(String name);
  Device createRandomDevice(String name);
}

public class DeviceFactoryImpl implements DeviceFactory {
  public Device createStandardDevice(String name) { return new DeviceImpl(name); }
  public Device createBrokenDevice(String name) { return new BrokenDeviceImpl(name); }
  public Device createRandomDevice(String name) {
    return Math.random() > 0.5 ? createStandardDevice(name) : createBrokenDevice(name);
  }
}

Builder

A class has too much construction logic with many/alternative inputs, default values, and sequential initialisation. The solution: a companion builder class whose objects have the sole responsibility of construction logic, eventually building one object. A fluent interface is typically used for one-statement construction, and the concrete class being built is often hidden (package-private or inner class). Recall that clean code tolerates very few constructors and arguments. Example: java.util.stream.Stream.Builder, java.lang.StringBuilder.

public class DeviceImplBuilder {
  private String name = "Device";
  private String description = "";

  public DeviceImplBuilder setName(String name) {
    this.name = name; return this;
  }

  public DeviceImplBuilder setDescription(String description) {
    this.description = description; return this;
  }

  public DeviceImpl createDeviceImpl() {
    return new DeviceImpl(name, description);
  }
}

// Fluent usage:
Device d1 = new DeviceImplBuilder()
    .setName("A")
    .setDescription("a nice device")
    .createDeviceImpl();

12. Quality and Language Paradigms

Software quality is typically considered a problem only in big projects, which are mostly developed in OO mainstream languages. In reality, quality must be achieved independently of the language used — but having the proper language or paradigm can be a powerful tool to achieve quality because the right abstraction might be better captured.

What a paradigm is

A programming paradigm is a fundamental style of computer programming, serving as a "school of thought". A language adheres to one of few paradigms (sometimes two); paradigms are rooted in a few concepts and computational mechanisms: primitive expressions (the simplest entities manipulated), means of combination (building compound elements out of simpler ones), and means of abstraction (naming and manipulating compound elements as units).

The four main paradigms

ParadigmMottoConceptsExamples
ImperativeFirst do this, then do thatStatements that change a program state, structured constructs (for, while), procedures, modules; inspired by hardware; the "most natural" for beginners and the starting point for OOFortran, Algol, Pascal, Basic, C
Object-OrientedSend a message to an object to simulate a real-world eventObjects exchanging messages, encapsulating data and behaviour; classes, methods, fields; method bodies typically imperative; the "most powerful" general-purpose approachC++, Java, C#
FunctionalEvaluate an expression and use the resulting value for somethingApplying functions without side effects, recursion instead of iteration; inspired by mathematics and the lambda-calculus; the "most elegant" approach for pros; later mixed with OO (Scala)Haskell, F#, Erlang, ML, Scheme, Lisp
LogicAnswer a computational question via search for a solutionChecking validity of a relationship among data; axioms, rules, matching and logic inference; inspired by first-order logic and theorem proving; works greatly in selected (AI-related) casesProlog, Datalog

Declarative languages and quality

Declarative languages (functional and logic) express the logic of computation abstracting away from specific control flow — focusing on what rather than how. The functional paradigm hides the order of evaluation; the logic paradigm hides the search strategy. Advantages for quality: much more concise and elegant code; gives a feeling of actual computational steps emerging "magically."

Multi-paradigm approaches: Scala

The idea is to identify languages or frameworks allowing different paradigms for different parts of a system, leveraging contamination between paradigms; historically this led to much more complex languages, but experience and improvements might create a breakthrough. Java and C# have primitive functional programming mechanisms (lambdas, streams). Scala is a full OO language with a very advanced type system and eye-candy mechanisms, and functions are first-class values as well. This course uses Scala specifically because it combines OO and FP, making it a perfect training tool for both paradigms and their integration. Another approach is the integration of Prolog and Java in tuProlog.

Domain-specific languages

DSLs are languages specifically tailored to particular domains, i.e. not general-purpose. They are often used in combination with mainstream languages, and have re-emerged thanks to frameworks to build them (e.g. Xtext). Turning an API into a DSL, when it succeeds, raises abstraction: "inside every system there's a small language struggling to get out." Examples include description languages (for games, configurations, meta-compilers, software engineering) and specific scripting languages (shell scripts).

Concurrency

Concurrency seems to badly fit all main paradigms: threads are too low-level, yet multi-core architectures made virtually any non-trivial application concurrent, often intertwined with distribution. The answer is high-level (typically functional-inspired) libraries and new paradigms on top of OO (actors, agents, streams). In this course the problem is delegated to the PCD side: we assume advanced libraries give us the abstractions we need.

Oral exam tip

The relationship between paradigm and quality is a common examination topic. Be ready to discuss how functional programming promotes immutability and referential transparency, how logic programming enables declarative specifications, and how Scala's multi-paradigm nature allows choosing the right abstraction for each subproblem.

13. Testing Deep Dive: Levels, Doubles, and Mockito

What is software testing?

Testing can be viewed from multiple angles: as an investigation providing stakeholders with information about quality (stakeholder view), as executing a system under specified conditions and evaluating the observed results (simulation view), or as the whole lifecycle process of planning, preparing and evaluating software products to detect defects (process view). There are different "schools" of testing: Analytic (formal methods: a test suite is a formal specification), Factory (planned and managed: a test suite is an engineering artifact like code and docs), Quality (a quality process for a quality product), Context-Driven (which testing is most valuable right now? a contract with stakeholders), and Agile (test automation and test-driven approaches: a test suite is what makes design flexible).

Levels and vocabulary (ISTQB)

Levels of testing: unit (individual units), integration (functionality provided by multiple interacting units), system (whole or part, functional requirements black-box and non-functional ones such as efficiency, reliability, usability, security), stress (performance in edge cases), acceptance (features against user expectations). Key terms: the SUT (system under test) is the item being tested; a test condition is a testable aspect of it; testability is the degree to which test conditions can be established and tests performed; a test case is a set of preconditions, inputs, actions, expected results and postconditions; the test oracle problem is determining the expected result; a test suite is a collection of test cases, and a test run its execution on a version of the SUT.

Test doubles

Unit tests target single components working in isolation — otherwise we would be testing a collaboration, and failures would be about the collaboration. To unit-test components that depend on others, we use test doubles (TD) — alternative implementations of the depended-on component (DOC), quickly set up for testing with predictable behaviour, like stunt doubles in movies. Test doubles must be free of errors "by construction" (or be much simpler to test than the real DOC). During fixture setup the real DOC is replaced by the TD, and the SUT is unaware of it. Reasons: the DOC may be unavailable, slow, costly, have undesirable side effects, or not return what the test needs (GUIs, random generation, databases, files, network, untested legacy code); or we want more control and visibility on how the SUT uses the DOC (does it call it properly? does it handle its errors and exceptions?).

Two families: stubs (dummy, stub, fake) emulate replies the DOC generates in response to calls; mocks (spy, mock) emulate and examine outgoing interactions from the SUT to the DOC.

TypePurposeHow it works
DummyReplace DOC with an untested reference"Empty object" passed to satisfy constructor parameters
StubPredefined responderEach method returns a fixed value

Mockito

Mockito is just a library for creating stubs and mocks (SBT dependency "org.mockito" % "mockito-core" % "3.+" % Test). The running example: a StandardDevice whose on() consults a FailingChecker strategy (attemptOn()) and throws IllegalStateException if it answers false; the constructor rejects a null checker with Objects.requireNonNull. Key constructs:

  • mock(C.class) — creates a dummy implementation
  • when(mock.meth()).thenReturn(res) — instructs a stubbed reply
  • spy(obj) — inserts a wrapper to detect events
  • verify(spy).meth() — checks if a method has been called (verify(obj, times(n)) for a count, verifyNoInteractions(obj) for none)
  • @Mock / @Spy fields, initialised by MockitoAnnotations.openMocks(this) in a @BeforeEach

14. Integration Testing

Unit tests are not enough. We can never be sure a system works as a whole if we rely exclusively on unit tests. Integration tests verify how different parts of a system collaborate with each other and with external systems.

Key distinction

A unit test verifies a single unit of behaviour, does it quickly, and does it in isolation from other units and tests. If a test fails to meet any of these three requirements, it falls into the category of integration tests. Integration tests are not system tests — they verify few collaborations, carefully isolating those strictly needed to verify a multi-component behaviour, often using mocking to limit the scope and to spy on resources that cannot be used during testing. When there is no more isolation or mocking and a whole system part is exercised, we have entered system tests (though the boundary is not clean). It is crucial to balance the number of unit and integration tests, and integration testing must be automated even when external resources seem to make it unfeasible.

Integration testing example

A manager handles devices, with commands to switch them all on or off; on start and on errors it files reports (e.g. for logging). We want to test the correct collaboration between manager and devices, mocking the checker and the reporter:

public interface DeviceManager {
  void start();
  void addDevice(String name, Device device);
  void switchOnAll();
  void switchOnOne(String name);
  boolean isSwitchedOn(String name);
}

public interface EventReporter {
  void reportStarted(String deviceName);
  void reportFailed(String deviceName, String reason);
}
public class IntegrationTest {
  private DeviceManager deviceManager;
  private Device device;
  @Mock FailingChecker checker;
  @Mock EventReporter reporter;

  @BeforeEach
  void init() {
    MockitoAnnotations.openMocks(this);
    this.deviceManager = Factory.createDeviceManager(reporter);
    this.device = spy(new StandardDevice(checker));
    this.deviceManager.addDevice("dev-0", this.device);
  }

  @Test
  void managerCorrectlyReportsADeviceFailure() {
    when(this.checker.attemptOn()).thenReturn(false);
    this.deviceManager.start();
    this.deviceManager.switchOnAll();

    assertFalse(this.deviceManager.isSwitchedOn("dev-0"));

    verify(this.device).on();
    verify(this.checker).attemptOn();
    verify(this.reporter).reportStarted("dev-0");
    verify(this.reporter).reportFailed(eq("dev-0"), anyString());
  }
}

  • Make domain model boundaries explicit
  • Reduce the number of layers
  • Eliminate circular dependencies
  • Use multiple act sections in a test
  • Writing integration tests earlier supports "design for testability"

15. Check Your Understanding

1. What are the seven software engineering principles of the quality framework? Give one example of each.

Rigour and formality (describe behaviour as precisely as mathematics: state machines, rule-like tests); separation of concerns (unit vs integration vs acceptance tests, functional vs non-functional requirements); modularity (high cohesion, low coupling: packages, nested classes, JARs); abstraction (an interface hiding a class, an API layer, a DSL); anticipation of change (constants instead of magic numbers, encapsulating implementation choices, hiding object creation behind APIs); generality (making implementation choices parameters, supporting more input cases than needed); incrementality (versioned releases, Scrum sprints, 10-20 minute TDD cycles). Abstraction is the most important: it mitigates opacity and underlies DRY and DIP.

2. Explain the difference between internal and external software quality. Why is internal quality important for achieving external quality?

External quality determines the fulfilment of stakeholder requirements — attributes like correctness, usability, efficiency, reliability. Internal quality determines your ability to move forward on a project — attributes like maintainability, flexibility, readability, testability. Internal quality is the key means to achieving external quality because you cannot sustainably produce correct, reliable software from a codebase that is rigid, fragile, opaque, or untestable. Modern approaches require internal features to be readily observable through clean code, tests, and documentation.

3. What is technical debt? Describe a concrete example from the slides.

Technical debt is the extra development work that arises when code easy to implement in the short run is used instead of the best overall solution. It is the "patch" problem: you solve something quickly and sub-optimally, delaying improvement until it costs more than fixing it immediately. In the slides, the Configuration class catches IOException and just prints it instead of properly handling or propagating it — classic technical debt that will cause silent failures later.

4. List the seven code defects described in the quality framework. Which one is considered the "quintessential code smell"?

The seven defects: (1) Needless repetition, (2) Needless complexity, (3) Rigidity, (4) Fragility, (5) Immobility, (6) Viscosity, (7) Opacity. Duplication (needless repetition) is the quintessential code smell — it creates strong dependencies where errors propagate without control and the system becomes extremely rigid.

5. What are the three laws of TDD? How does the TDD cycle differ from the traditional design-code-test sequence?

Law 1: No production code without a failing unit test. Law 2: No more of a unit test than is sufficient to fail. Law 3: No more production code than is sufficient to pass the failing test. Traditional: Design → Code → Test. TDD: Test (write a failing test) → Code (make it pass) → Design/Refactor (clean up). TDD inverts the order, making tests a specification tool and a safety net for refactoring.

6. Explain the five SOLID principles. Give a concrete code example for each.

SRP: One reason to change — separate PrefixFormatter from Logger. OCP: Open for extension, closed for modification — LoggerOcp uses a LogFormatter strategy. LSP: Subtypes must be substitutable — AbstractConsole enforces print/println semantics. ISP: Fine-grained client-specific interfaces — use Iterable<String> not String[]. DIP: Depend on abstractions, not concretions — LoggerDip depends on Console and Formatter interfaces, not System.out.

7. What is the difference between a Stub, a Spy, and a Mock in Mockito? When would you use each?

All are test doubles: replacements of a depended-on component (DOC) so that the SUT can be unit-tested in isolation. Stub: emulates the replies of the DOC with predefined answers (when(...).thenReturn(...)). Use when you need a predictable response from a dependency (a dummy is a stub nobody calls, a fake returns a realistic sequence of results). Spy: a proxy wrapping a real object to track the calls it receives (spy(new RandomChecker()), then verify(spy).attemptOn()). Use when you want to verify that methods were called but also keep the real behaviour. Mock: an object used to check that the SUT uses the DOC correctly overall (mock(FailingChecker.class) with verify(mock, times(n)).attemptOn()). Use when the point of the test is the interaction pattern (how many times, with which arguments) between SUT and DOC. Stubs, dummies and fakes emulate replies; spies and mocks examine outgoing interactions.

8. What is refactoring, and what is its relationship with tests and design patterns?

Refactoring is evolving code (and tests) without changing functionality, to improve quality — readability and generality, or preparation for change. It ranges from fine-grained techniques (renaming, changing signatures, extracting methods and constants, replacing inheritance with delegation, moving code into new or base classes, constructors into static factories) up to applying design patterns. Since behaviour must not change, a good test suite is what gives confidence in the outcome — which is why TDD's third step is precisely refactoring, protected by green tests.

9. How does the Decorator pattern differ from the Template Method pattern? When would you choose one over the other?

Template Method uses inheritance and abstract methods to let subclasses define variable parts of an algorithm — the variation point is decided at compile-time. Example: AbstractDevice.doWhenOff(). Decorator uses composition and delegation to wrap objects with additional behaviour — multiple decorators can be chained at run-time. Example: wrapping a DeviceImpl with BrokenDeviceImpl and DeviceWithIntensityImpl. Choose Template Method when the variation is fixed at subclasses; choose Decorator when you need to mix behaviours flexibly at run-time.

10. Describe the Agile Manifesto's key principles that most affect coding. How does agility address the problems of the waterfall model?

Key principles: satisfy customers through early/continuous delivery; welcome changing requirements; deliver working software frequently; working software is the primary measure of progress; continuous attention to technical excellence; simplicity is essential. Agile addresses waterfall's three problems: (1) requirements instability is embraced through iterative cycles, (2) detailed design emerges through coding and testing in short iterations, (3) testing is continuous, not deferred to the end — preventing late-discovered bugs.

11. What is the Abstraction principle and why is it considered the single most important concept in software engineering?

Abstraction is the process of identifying common features in individuals and forming a concept of those features, ignoring unnecessary details. In software engineering, it mitigates opacity (code directly captures the idea), enforces DRY (don't repeat yourself), and enables DIP (depend on abstractions, not details). It is considered most important because managing complexity in software — the single biggest challenge — fundamentally relies on creating the right abstractions at every level: classes, interfaces, packages, APIs, DSLs, and architectural layers.

12. Why is the Builder pattern useful? Provide a scenario from the course examples where it applies.

Builder is useful when a class has too much construction logic with many optional parameters, default values, or sequential initialisation steps — precisely the situation where telescoping constructors become unreadable and error-prone. In the course, DeviceImpl had multiple constructors for different combinations of name and description. The DeviceImplBuilder replaces those with a fluent API: new DeviceImplBuilder().setName("A").setDescription("nice device").createDeviceImpl(). This applies SRP by separating construction logic from the class itself.
