The lesson in one paragraph. Quality software keeps working while requirements change, and what makes that possible is internal quality: code that is readable, testable and easy to change. The course builds it in layers: the defects to avoid (repetition, rigidity, fragility, opacity…), the software-engineering principles that prevent them, the design principles that make them concrete (DRY, KISS, SOLID), and the design patterns that package them. 2. What is software quality?

Why software needs a process

Software is about 15% of world GDP (indirectly) and heading for 30% by 2030, yet over the whole life cycle productivity is far below 100 lines per person per day. Software is easy to “somewhat prototype” but hard to get right and to debug, and without discipline projects fail. Development iterates over four kinds of step (lesson 8 covers processes): requirement engineering (elicit, analyse, specify), design (from architecture to details), implementation, and post-implementation (testing, deployment, maintenance: the most expensive phase).

From the slides: Glass’s “frequently forgotten facts”

A 10% increase in problem complexity brings a 100% increase in solution complexity. Good programmers are up to 30 times better than mediocre ones. Projects run away because of unstable requirements and optimistic estimates. Finding and removing errors takes 40% of development effort; rigorous review removes 90% of errors. Maintenance takes 40–80% of the total cost.

Quality software adapts better to unstable requirements, lowers maintenance costs and helps remove errors. Getting there means knowing what quality is, using practices that lead to it, and organising the process well: the goals of the course. Behind all of them is one skill, managing abstraction: the single concept behind many concrete cases. In code it mitigates opacity and underlies DRY (don’t repeat yourself) and DIP (depend on interfaces, not on implementation classes).

Definitions and measures

Quality is “translating future needs into measurable characteristics” (Deming) or “meeting the customer needs, with freedom from deficiencies” (Juran), seen from a transcendental (elegance), product (measurable characteristics), manufacturing (conformance) or user (satisfaction) perspective. It is measured as reliability, efficiency, security, maintainability and size.

Internal and external quality

External quality decides whether stakeholder requirements are met: correctness, usability, efficiency, reliability, integrity, adaptability, accuracy, robustness. Internal quality decides whether the team can keep moving forward: maintainability, flexibility, portability, reusability, readability, testability, understandability. People notice external quality, but internal quality is the means to it, and skipping it is a common cause of failure; modern approaches make it observable through tests, reviews and clean code. Code quality, the shape of the code and how it can evolve, is a precondition of both.

Technical debt

Technical debt is the extra work caused by choosing code that is easy now over the best overall solution: the “patch” you mean to improve later, which ends up costing more than fixing it at once. It is sometimes unavoidable, and it can only be managed empirically, since the distance from “complete quality” is almost impossible to measure.

public class Configuration {

3. How does bad code show itself?

The course organises quality in five layers, and this lesson follows them: code defects to avoid (this section), software-engineering principles (section 4), design principles DRY, KISS and SOLID (section 5), design patterns (section 7), and methodology: waterfall and agility, with TDD (section 6, lesson 8).

Code smells

A code smell is a surface sign that may point to a deeper problem: duplicated code, bad names, abstraction “jumps”, partial implementations, violated OO principles. Smells are not necessarily bugs, but they create technical debt. Three families are common: neglected conventions (in Java: no I prefixes, camel case, one declaration per line, no obscure operators); ignored rules of effectiveness from Bloch’s Effective Java (know your libraries, minimise mutability and accessibility, favour composition over inheritance, program against interfaces…); and unclean code in Martin’s sense: code should read like good prose and always reveal its intent. Names come first: intention-revealing (elapsedTimeInDays, not d), pronounceable, searchable (MAX_CLASSES_PER_STUDENT), nouns for classes and verbs for functions.

From the slides: the full convention, Effective Java and naming rules

Conventions. Every language has conventions beyond its syntax (naming, spacing, formatting, obsolete constructs, program structure); they differ between languages (C# vs Java), and groups may add constraints but never remove them. In Java: never prefix interfaces or variables, use camel case for all identifiers, never declare two variables on one line, don’t abuse obscure operators.

Effective Java rules. Know and use your libraries; minimise the accessibility of class members; minimise mutability; favour composition over inheritance; design and document for inheritance, or else prohibit it; prefer interfaces to abstract classes; check the validity of parameters in public APIs; document all public APIs; make defensive copies when needed; minimise the scope of local variables; prefer for-each loops; avoid floating point when exact values are needed; avoid strings where other types fit better; program against interfaces, not classes.

Names.

  • Intention-revealing: elapsedTimeInDays is better than d, even for a local variable.
  • Pronounceable, not acronyms or pseudo-acronyms (no class DtaRcrd102).
  • Searchable: a constant MAX_CLASSES_PER_STUDENT = 7 beats a magic number.
  • No prefixes on variables or interfaces: interface IScheduler is ugly, and interfaces are the key abstractions.
  • Class names are nouns or noun phrases (TransactionProcessor, not Processing); plurals are sometimes used for helper classes (Objects, Collections).
  • Function names are usually verb phrases; prefer named factories to constructors; functions that just read an element are sometimes nouns, and mathematical functions keep their one-letter names.

Spot what is wrong with this interface:

// A modelling abstraction for a DVCS
public interface Model {

  void setCmd();

  void doCopy(String path2);

  void setRepository(String repo);

  boolean check_Existence();

  void doCommit(String commento);

  String[] Log();

Answers: seven problems
  • Model says nothing about a version-control system. The comment has to compensate, where a name such as Repository would not need it.
  • setCmd() is a setter with no argument, so its name contradicts its signature, and Cmd is an abbreviation.
  • doCopy(String path2): the “do” prefix is noise, and path2 reveals nothing (the path of what?).
  • check_Existence() breaks camel case. A boolean query reads better as exists().
  • commento mixes Italian into English identifiers.
  • Log() starts with a capital letter like a class, and returns a raw array rather than a List.
  • The methods sit at different levels of abstraction. User commands (doCommit) are mixed with configuration (setRepository) and plumbing (setCmd).

Functions, comments, formatting

A function should be small (about 10 lines), do one thing at one level of abstraction, read top-down like a story, take 0–2 arguments (wrap more into classes or builders), and have no side effects unless that is its purpose. The course’s example is a 38-line Clean Code function that repeats a lookup–render–append sequence four times; refactored, it becomes a class of small methods whose top level reads as a sentence:

private void includeSetupAndTeardownPages() throws Exception {
  includeSetupPages();
  includePageContent();
  includeTeardownPages();
  updatePageContent();
}

From the slides: symptoms and typical causes of each defect
  • Needless repetition. Code is cut, pasted and modified. Bugs and changes multiply from a single cause until fixing becomes impractical. Examples at large scale: many similar GUI forms, database-access logic, large models of slightly different entities, software product lines. Small scale: any resemblance between two parts of the code.
  • Needless complexity. The solution is more involved than needed, so the code is harder to understand, change and test. Typical causes: reinventing a library, picking the trickiest of several solutions, extra cyclomatic complexity from lack of skill, optimising where it is not needed, supporting requirements nobody asked for.
  • Rigidity. The design is hard to change: small changes cascade. The result is reluctance to change and underestimated costs. Typical causes: repetition without factorisation, poor information hiding, too tight a dependency on lower-level implementations: in general, unneeded dependencies between modules.
  • Fragility. The design is easy to break: a change in one module causes errors elsewhere, and fragile modules fill the bug list. Typical causes: undocumented assumptions about other modules, partial implementations that miss cases, indirect coupling, solutions too complicated to be understood.
  • Immobility. The design is hard to reuse: code looks general but cannot be extracted without high cost and risk. Typical causes: configurable details hidden in the implementation, badly structured interfaces of complex components, commonalities not revealed, direct use of implementation details.
  • Viscosity. Doing things right costs more than hacking, which leads to accepting low quality and to pervasive debt. Typical causes: a slow IDE or build, automated tests that are impossible or ineffective, deployment too complex for acceptance tests, a design that resists extension, old hacks that invite new ones.
  • Opacity. Modules are hard to understand, and keeping their intent clear takes effort (so inline comments get abused). Typical causes: bad module organisation, bad names, types and structure that hide intent, obscure formatting of control flow.

4. Which principles lead to good design?

The seven software-engineering principles

Everyone agrees with these principles and then believes there is no time for them; the real skill is knowing when to apply each. Lesson 8 uses them from the methodology side (its deck abbreviates them RF, SOC, M, A, AOC, G, I).

From the slides: each principle in full, with all its examples
  • RF — rigour and formality. Describe or enact behaviour as precisely as mathematics would. This is key where errors would cause heavy debt later. It is realistic only for small or critical parts, is more common among developers with a scientific background, and can live in tests or in documentation. Examples: finite-state machines, Petri nets and other automata; advanced algorithms where needed; DSLs or DSL-like APIs to configure complex aspects; rule-like specifications in tests.
  • SOC — separation of concerns. Master complexity by grouping issues and considering each in isolation, since people can only work within a limited context. Concerns can be separated in time, by quality (efficiency vs correctness) or by view (problem vs solution). It is so general that several other principles are instances of it. Examples: divide a project into increments; split developers into teams and the work within a team; divide tests into unit, integration, acceptance and stress tests; divide requirements into functional and non-functional; consider correctness independently of performance.
  • MOD — modularity. Divide software into modules (groups of classes, sources or other modules), with high cohesion inside a module and low coupling between modules. Allocate concerns to modules, at several levels, top-down or bottom-up, so that modules can be reused and composed. Examples: package and namespace structure; nested classes; deployment units (object files, DLLs, JARs, ZIPs).
  • ABS — abstraction. Identify the key aspects and ignore the rest as unnecessary detail, at every granularity (classes, packages…). It can be seen as another instance of SOC. Examples: choose the paradigm best suited to a context; give a class an interface and let others use only that; put an API layer over complex machinery; use a DSL instead of an API.
  • AOC — anticipation of change. Software, unlike other engineering products, always evolves, and requirements are unstable. Prepare the ground to react flexibly, sometimes implementing “ahead” of need. Examples: move the content of a class into an abstract class; turn numbers and strings into constants; encapsulate specific implementation choices; hide object creation behind public APIs.
  • GEN — generality. Solve a more general problem than the one at hand, which makes reuse in new situations possible. It adds a burden that not everyone accepts, and it is close to AOC. Examples: make implementation choices into parameters; support more inputs or configurations than currently needed; merge two apparently unrelated functions into one.
  • INC — incrementality. A quality of processes, at every granularity. It reduces the risk of building on wrong code or assumptions, lets you start from the known requirements only, and lets you postpone choices that could not yet be made precisely. Examples: incremental version numbers; week-long Scrum Sprints; TDD with 20-minute red–green–refactor cycles.

The OO paradigm as the starting point

Paradigms and languages affect quality, and OO is the mainstream: every top TIOBE language except C is OO, the complex part of large systems is usually written in Java or C#, and GoF patterns and UML assume OO. Its elements: an object has identity, state (its fields) and behaviour; a method handles a request–reply message; an interface is a contract, i.e. a type; a class implements an interface and is a template for objects. Its relationships: dependency (use-a); association, aggregation, composition (has-a: independent lives without ownership, independent lives with ownership, or B dies with A); inheritance (is-a, with subtyping and dynamic dispatch); implementation (conforms-to, also a subtype relation).

The course’s first example, a controller of devices, uses all of these:

public interface Device {
  void on();
  void off();
  boolean isOn();
}

public interface Controller {
  void addDevice(Device device);
  void setAllOn();
  void setAllOff();
  boolean allOn();
}

public class TV implements Device {                 // implementation
  private boolean flag = true;
  @Override public void on() { flag = true; }
  @Override public void off() { flag = false; }
  @Override public boolean isOn() { return flag; }
  @Override public String toString() { return "TV{" + flag + "}"; }
}

public class EternalTV extends TV {                 // inheritance
  @Override public void off() {}                    // refuses to switch off
  @Override public String toString() { return "eTV{on}"; }
}

public class ControllerImpl implements Controller {
  private final List<Device> devices = new LinkedList<>();   // association

  @Override public void addDevice(final Device device) { devices.add(device); }
  @Override public void setAllOn() { for (final Device d : devices) { d.on(); } }
  @Override public void setAllOff() { for (final Device d : devices) { d.off(); } }
  @Override public boolean allOn() {
    for (final Device d : devices) {
      if (!d.isOn()) { return false; }
    }
    return true;
  }
  @Override public String toString() { return "ControllerImpl{devices=" + devices + '}'; }
}

final Controller controller = new ControllerImpl();
controller.addDevice(new TV());
controller.addDevice(new EternalTV());
controller.addDevice(new TV());
controller.setAllOff();
System.out.println(controller);        // ControllerImpl{devices=[TV{false}, eTV{on}, TV{false}]}
System.out.println(controller.allOn()); // false

Dynamic dispatch picks EternalTV.off(), so after setAllOff() one device is still on and the controller, which only sees the interface, cannot tell. Whether that is an acceptable Device is the question the Liskov principle answers.

5. What do DRY, KISS and SOLID look like in code?

DRY (don’t repeat yourself): cut-paste-modify creates hidden dependencies through which errors propagate, and makes the system rigid; duplication is the quintessential code smell. KISS (keep it simple, stupid; U.S. Navy, 1960): never use a complex solution when a simpler one exists, and don’t solve problems nobody asked about.

From the slides: DRY and KISS in more detail

Refactoring removes duplication, tools can detect syntactic duplication, and some paradigms such as FP apply DRY very aggressively. KISS in other words: Occam’s razor (the simpler solution tends to be right), Leonardo (“simplicity is the ultimate sophistication”), Mies van der Rohe (“less is more”), Stroustrup (“make simple tasks simple”), Saint-Exupéry (“perfection is reached when there’s nothing left to take away”), Einstein (“as simple as possible, but no simpler”). When a complex solution emerges, think twice.

6. How does test-driven development work?

The course is agile throughout (the Agile Manifesto and the course’s six-step method are in lesson 8), and TDD is where agility meets code.

The rules

The three laws of TDD:

  1. You may not write production code until you have written a failing unit test.
  2. You may not write more of a unit test than is sufficient to fail, and not compiling is failing.
  3. You may not write more production code than is sufficient to pass the currently failing test.

Each cycle lasts 10–20 minutes: write a failing test (red), make it pass (green), clean up what the two steps added (refactor).

Why so strict? Tests written first are a specification that documents the code; they cut the cost of finding bugs; and fast tests give the freedom to refactor. The traditional cycle is design → code → test; TDD’s is test → code → refactor, and in practice everybody sits somewhere in between. The lab’s point: TDD fixes the what before the how, and the same JUnit code serves as specification, then implementation guide, then regression check.

Kinds of tests and clean tests

Tests come as unit (one piece of code in isolation), integration (interacting components), functional (the public API, use cases), stress (realistic workload, resources) and acceptance (the whole user experience). Unit tests serve regression, progress measurement, specification, implementation guidance (TDD), solidity (edge cases) and legacy recovery. Test code must be as clean as production code: one naming convention, the build–operate–check (Arrange–Act–Assert) structure, preferably one assert and always a single concept per test (not one test per method), and tests that are fast, independent, repeatable, self-validating and timely.

JUnit 5 in brief

Tests are methods annotated @Test; @BeforeEach builds the fixture; assertions such as assertEquals(expected, actual), assertTrue and assertThrows check the outcome. The lab slide writes assertEqual and assertNotEqual; the methods are assertEquals and assertNotEquals.

7. How do refactoring and design patterns improve code?

Refactoring

Refactoring evolves code or tests without changing functionality, to make them more readable and general or to prepare them for change; good tests are what make it safe. The techniques go from fine to coarse: renaming; changing signatures; extracting methods, static methods and constants; replacing inheritance with delegation; moving code into new or base classes; turning constructors into static factories; and finally applying design patterns.

Design patterns

A design pattern packages a recurring design solution, extracted from experience rather than invented. The 23 “Gang of Four” patterns (Gamma, Helm, Johnson, Vlissides) are the classics. A pattern makes code easier to understand (its name explains the structure), more open to change and better organised.

From the slides: the 23 GoF patterns

Creational: Factory Method (class level); Abstract Factory, Builder, Prototype, Singleton (object level). Structural: Adapter (class and object level); Bridge, Composite, Decorator, Facade, Flyweight, Proxy (object level). Behavioural: Interpreter, Template Method (class level); Chain of Responsibility, Command, Iterator, Mediator, Memento, Observer, State, Strategy, Visitor (object level). The slide lists Flyweight among the behavioural patterns; the GoF book classifies it as structural.

The course works through seven of them; in each, the device example meets a new requirement and the pattern absorbs it.

Proxy

A proxy is a surrogate with the same interface that controls access to another object: to create it lazily, to reach a remote object transparently, or to restrict its use (as read-only collections do). It keeps access logic out of the base class (SRP), and clients depending on the interface cannot tell it is there (DIP); proxies can be chained.

From the course code: a proxy that forbids overdrafts on a bank account 
public interface BankAccount {
  int balance();
  void deposit(int amount);
  void withdraw(int amount);
}

class SimpleBankAccount implements BankAccount {
  private int balance;

  @Override public int balance() { return this.balance; }

  private void checkNegativeAmount(int amount) {
    if (amount < 0) {
      throw new IllegalArgumentException();
    }
  }
  @Override public void deposit(int amount) {
    checkNegativeAmount(amount);
    this.balance = this.balance + amount;
  }
  @Override public void withdraw(int amount) {
    checkNegativeAmount(amount);
    this.balance = this.balance - amount - 1;       // fee of 1
  }
}

class CheckedBankAccount implements BankAccount {    // the proxy
  private final BankAccount baseBankAccount = new SimpleBankAccount();

  public int balance() { return baseBankAccount.balance(); }
  public void deposit(int amount) { baseBankAccount.deposit(amount); }
  public void withdraw(int amount) {
    if (amount > this.balance()) {                  // access control
      throw new IllegalStateException();
    }
    baseBankAccount.withdraw(amount);
  }
}

Template Method

Template Method solves the same problem by inheritance: the varying steps are abstract methods called by a concrete template method, so the choice is made at compile time (e.g. InputStream). A breakable device would duplicate all of DeviceImpl; a base class factors the common code:

public abstract class AbstractDevice implements Device {
  private boolean on;
  private boolean working;
  private final String name;

  public AbstractDevice(String name) {
    this.on = false;
    this.working = true;
    this.name = name;
  }

  @Override public void on() {
    if (this.isWorking()) {
      this.on = true;
    }
  }

  @Override public void off() {       // the template method
    this.doWhenOff();                  // the variable step
    this.on = false;
  }

  protected abstract void doWhenOff();

  @Override public boolean isOn() { return this.on; }
  @Override public boolean isWorking() { return this.working; }
  @Override public String getName() { return this.name; }

  void stopWorking() { this.working = false; }   // package-private
}

public class DeviceImpl extends AbstractDevice {
  public DeviceImpl(String name) { super(name); }

  @Override protected void doWhenOff() { }       // nothing special
}

public class BrokenDeviceImpl extends AbstractDevice {
  public BrokenDeviceImpl(String name) { super(name); }

  @Override protected void doWhenOff() {         // 5% chance of breaking
    if (this.isOn() && Math.random() > 0.95) {
      this.stopWorking();
    }
  }
}

  }
  @Override public void switchOn(int position) { this.manager.devices().get(position).on(); }
  @Override public void switchOff(int position) { this.manager.devices().get(position).off(); }
}

Abstract Factory

Abstract Factory: when which classes to instantiate is decided dynamically, a factory interface has one method per product and each implementation picks the concrete classes, separating construction from use. Factory Method is the one-method special case.

public interface DeviceFactory {
  Device createStandardDevice(String name);
  Device createBrokenDevice(String name);
  Device createRandomDevice(String name);
}

public final class DeviceFactoryImpl implements DeviceFactory {
  @Override public Device createStandardDevice(String name) { return new DeviceImpl(name); }
  @Override public Device createBrokenDevice(String name) { return new BrokenDeviceImpl(name); }
  @Override public Device createRandomDevice(String name) {
    return Math.random() > 0.5 ? createStandardDevice(name) : createBrokenDevice(name);
  }
}

DeviceFactory factory = new DeviceFactoryImpl();
Device d1 = factory.createStandardDevice("A");
Device d2 = factory.createBrokenDevice("A");

8. Does the programming paradigm matter for quality?

Quality must be achieved in any language, but the right paradigm can capture the right abstraction and so becomes a tool for quality. A paradigm is a fundamental style of programming, resting on three mechanisms: primitive expressions, means of combination and means of abstraction. There are many languages, but few paradigms.

ParadigmMottoComputing as…Languages
ImperativeFirst do this, then do thatexecuting statements that change a state, organised by structured constructs (for, while), procedures and modules. Inspired by the hardware, considered the most “natural” for beginners, and the starting point of OO.Fortran, Algol, Pascal, Basic, C

Multi-paradigm languages use different paradigms for different parts of a system, historically at the price of complexity. Java and C# have basic FP (lambdas, streams); Scala is a full OO language with an advanced type system and first-class functions; tuProlog integrates Prolog with Java (lesson 11).

DSLs, tailored to one domain and often embedded in a mainstream language, raise the level of abstraction when an API becomes a language: “inside every system there’s a small language struggling to get out” (configuration and game description languages, shell scripts).

Concurrency fits no paradigm well and threads are too low-level; the answers are FP-inspired libraries and abstractions such as actors and streams, which in SSS belong to PCD.

9. How do you test a component that depends on others?

Testing: what, why and who

Testing is an investigation that informs stakeholders about quality, the execution of a system under specified conditions followed by an evaluation, and a whole life-cycle process of planning, preparing and evaluating. A test strategy answers why, what (the system under test), who, when (before, after or together with the code) and how.

From the slides: the five “schools” of testing
  • Analytic: testing as a rigorous task using formal methods (“programs are logical artefacts subject to math-like laws”). A test suite is a formal specification of the system’s behaviour.
  • Factory: testing to measure progress, so it must be planned, scheduled and managed. A test suite is an engineering artefact, like code, documentation and data.
  • Quality: “a quality process for a quality product”. A test suite is a means to enact and control quality, internal and external.
  • Context-driven: which testing is most valuable right now? A test suite is a contract with the stakeholders that follows a sequence of milestones.
  • Agile: testing to make change easy, through automation and test-driven approaches. A test suite is the code that keeps the design flexible throughout the process.

The levels are unit, integration, system (functional requirements black-box, non-functional ones such as efficiency and security), stress, and acceptance. In ISTQB vocabulary, you run a suite of test cases, using tools and oracles, to verify test conditions on testable test items (the SUT).

Test doubles

A unit test targets one component in isolation; if the component depends on others, a failure would be about the collaboration. So the depended-on component (DOC) is replaced by a test double (TD): a simple, predictable implementation set up just for the test, like a stunt double in a film. It must be correct “by construction”, or much simpler to test than the real DOC.

Doubles are needed when the DOC cannot be used in a test (unavailable, slow, costly, with side effects, or breaking automation: GUIs, randomness, databases, files, network, untested code) and when the test needs visibility into how the SUT uses it (does it call it properly? does it handle its errors?).

Mockito

Mockito creates doubles on the fly (the slides give "org.mockito" % "mockito-core" % "3.+" % Test; the seminar repository uses 5.23.0):

  • mock(C.class) creates an implementation of C whose methods do nothing and return defaults (false, 0, null);
  • when(mock.meth()).thenReturn(res) programs a reply. The slide writes thenResult, but the method is thenReturn. thenReturn(a, b, c) returns the values in sequence;
  • spy(obj) wraps a real object and records the calls it receives;
  • verify(spy).meth() checks that meth was called once. verify(x, times(n)) checks the number of calls, and verifyNoInteractions(x) checks that there were none.

The running example is a device that asks a FailingChecker strategy whether switching on succeeds:

public interface Device {
  void on() throws IllegalStateException;
  void off();
  boolean isOn();
  void reset();
}

public interface FailingChecker {
  boolean attemptOn();
  void reset();
  String checkerName();
}

public class StandardDevice implements Device {
  private FailingChecker failingChecker;
  private boolean on = false;

  public StandardDevice(FailingChecker failingChecker) {
    this.failingChecker = Objects.requireNonNull(failingChecker);
  }
  @Override public void on() throws IllegalStateException {
    if (!this.failingChecker.attemptOn()) {
      throw new IllegalStateException();
    }
    this.on = true;
  }
  @Override public void off() { this.on = false; }
  @Override public boolean isOn() { return this.on; }
  @Override public void reset() {
    this.off();
    this.failingChecker.reset();
  }
  @Override public String toString() {
    return "StandardDevice{" + "policy=" + failingChecker.checkerName() + ", on=" + on + '}';
  }
}

public class RandomChecker implements FailingChecker {   // the real DOC
  private final Random random = new Random();
  private boolean failed = false;

  @Override public boolean attemptOn() {
    this.failed = this.failed || random.nextBoolean();   // once failed, always failed
    return !this.failed;
  }
  @Override public void reset() { this.failed = false; }
  @Override public String checkerName() { return "random"; }
}

Integration tests

Unit tests check business logic well but cannot show that the system works as a whole. A unit test checks one unit of behaviour, quickly, in isolation; a test missing any of the three is an integration test.

An integration test is not a system test: it isolates the few collaborations needed for one multi-component behaviour, still mocking what cannot be used in testing. Once nothing is mocked and a whole part of the system runs, it is a system test. Integration tests must be automated too, and balanced against unit tests.

The example: a manager switches named devices on and reports starts and failures. The test uses the real manager and a real StandardDevice, mocking the checker and the reporter:

public interface DeviceManager {
  void start();
  void addDevice(String name, Device device);
  void switchOnAll();
  void switchOnOne(String name);
  boolean isSwitchedOn(String name);
}

public interface EventReporter {
  void reportStarted(String deviceName);
  void reportFailed(String deviceName, String reason);
}

public class Factory {
  static DeviceManager createDeviceManager(EventReporter reporter) {
    return new DeviceManager() {
      private Map<String, Device> map = new HashMap<>();

      @Override public void start() {
        this.map.forEach((name, device) -> reporter.reportStarted(name));
      }
      @Override public void addDevice(String name, Device device) {
        this.map.put(name, device);
      }
      @Override public void switchOnAll() {
        this.map.forEach((name, device) -> {
          try {
            device.on();
          } catch (IllegalStateException e) {
            reporter.reportFailed(name, "unknown");
          }
        });
      }
      @Override public void switchOnOne(String name) {
        try {
          this.map.get(name).on();
        } catch (IllegalStateException e) {
          reporter.reportFailed(name, "unknown");
        }
      }
      @Override public boolean isSwitchedOn(String name) {
        return this.map.get(name).isOn();
      }
    };
  }
}
public class IntegrationTest {

  private DeviceManager deviceManager;
  private Device device;
  @Mock FailingChecker checker;
  @Mock EventReporter reporter;

  @BeforeEach
  void init() {
    MockitoAnnotations.openMocks(this);
    this.deviceManager = Factory.createDeviceManager(reporter);
    this.device = spy(new StandardDevice(checker));        // real device, observed
    this.deviceManager.addDevice("dev-0", this.device);
  }

  @Test
  void managerCorrectlyReportsADeviceFailure() {
    when(this.checker.attemptOn()).thenReturn(false);
    this.deviceManager.start();
    this.deviceManager.switchOnAll();
    assertFalse(this.deviceManager.isSwitchedOn("dev-0"));

    verify(this.device).on();
    verify(this.checker).attemptOn();
    verify(this.reporter).reportStarted("dev-0");
    verify(this.reporter).reportFailed(eq("dev-0"), anyString());
  }
}

The test has two act steps and checks the whole chain: manager → device → checker → reporter. eq and anyString are argument matchers. All 13 tests of the seminar repository pass. Good practice: explicit domain boundaries, few layers, no circular dependencies, several act sections when needed; writing integration tests early supports design for testability.

10. How do you keep your work under version control?

A version control system manages the history of a repository of files. In a centralised VCS developers hold working copies of one remote repository; in a distributed VCS such as Git, everyone holds the entire repository.

Git stores snapshots rather than per-file changes (with deltas underneath). Its vocabulary:

  • the git directory (.git) holds the metadata and the object database: commits, branches…;
  • the working tree is a checkout of one version of the project, plus your local changes;
  • the staging area (or index) records what will go into the next commit;
  • files in the working tree are untracked or tracked, and tracked files are unmodified, modified and/or staged;
  • a branch is an independent line of development, and new commits go into the history of the current branch;
  • HEAD points to the current snapshot (a branch or a commit).
CommandEffect
init / clonecreate a new repository / download a project with its whole history
statusshow untracked, modified and staged files
addstage changes into the index (also marks merge conflicts as resolved)
diffdifferences between a commit and the working tree, or between the working tree and the index

A simple workflow. Clone, pick a branch, change files, stage, commit; merge into the main branch (resolve conflicts, add, commit); push. If someone pushed first, pull, integrate and push again. In the lab:

Check your understanding

What is the difference between internal and external quality, and why does the course insist on the internal one?

External quality is what stakeholders see: correctness, usability, efficiency, reliability. Internal quality is what lets the team keep going: maintainability, readability, testability. The second is the means to the first. Aiming at external quality while neglecting internal quality is a common cause of failure.

What is technical debt? Point it out in the Configuration example.

The extra future work caused by choosing a quick, sub-optimal solution now. In Configuration, the exception is only printed: a missing file leaves data null, and the failure appears later as a NullPointerException in getData().

Rigidity, fragility, immobility, viscosity: tell them apart.

Rigid: hard to change, because changes cascade. Fragile: easy to break, because a change here causes errors elsewhere. Immobile: hard to reuse, because extracting the code costs too much. Viscous: doing things properly costs more than hacking, often because of the tools or the environment.

Give an example of anticipation of change and one of generality. How do they differ?

AOC: replace a magic number with a constant, or hide object creation behind a factory, to be ready for a likely change. GEN: turn an implementation choice into a parameter, e.g. filteredDevices(Predicate) instead of devicesByName, to solve a more general problem. AOC prepares for a change; GEN widens the problem being solved.

Which SOLID principle does EternalTV violate, and how does AbstractConsole protect against the same kind of problem?

LSP. EternalTV type-checks as a Device but ignores off(), so a controller’s setAllOff() no longer switches everything off. AbstractConsole makes println final and defines it as print followed by a line feed, so no subclass can break that relation.

State the three laws of TDD. Why must the refactoring step leave all tests green?

No production code without a failing test; no more test than is needed to fail (not compiling counts as failing); no more code than is needed to pass. Refactoring must not change behaviour, and green tests are the evidence that it didn’t. The logger’s OCP step, which changed the output, shows what happens without such a test.

Strategy and Template Method solve the same problem. What is the difference?

Strategy uses delegation: the varying algorithm is an object passed in, chosen at run time (e.g. a fee function). Template Method uses inheritance: the varying step is an abstract method implemented by a subclass, fixed at compile time (e.g. feeCalculation in SilverBankAccount).

Stub, fake, spy, mock: what does each one do in the StandardDevice tests?

The stub answers attemptOn() with a fixed value. The fake answers with a realistic sequence (true, true, false). The spy wraps a real RandomChecker and records its calls. The mock checks the collaboration, i.e. exactly how many times attemptOn() was called after each operation. Stubs emulate replies; spies and mocks examine outgoing calls.

When does a test stop being a unit test? And an integration test?

A unit test checks one unit of behaviour, quickly and in isolation; if any of the three fails, it is an integration test. When nothing is isolated or mocked any more and a whole part of the system runs, it has become a system test.

What is the staging area, and what does git pull do that git fetch doesn’t?

The staging area (index) holds the snapshot that the next commit will record; git add fills it. fetch only downloads remote commits and references, while pull also integrates them into the current branch (fetch plus merge).
