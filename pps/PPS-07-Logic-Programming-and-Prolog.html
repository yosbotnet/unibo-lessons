1. The Logic Programming Paradigm

Logic Programming (LP) uses mathematical logic as a declarative representation language and a theorem-prover for problem-solving. It is the third major programming paradigm alongside imperative/OOP and functional programming.

Key idea

Computation is about establishing in how many ways a goal can be solved — producing a stream of solutions through trial-and-error exploration of a search space. A goal is a relation over data elements, which are essentially "untyped trees with holes" (terms with logic variables).

Historical Context

Prolog was created by Alain Colmerauer in 1972, evolving from knowledge representation languages (Planner, QA-4). It started as a theorem prover and is now the reference language for LP. ISO Prolog (1995) remains the standard. After an initial hype cycle, Prolog is now fundamental to "symbolic AI" and specific niches where its search-oriented nature shines.

A Preview: Permutations

Compare imperative, functional, and logic implementations of list permutations:

static boolean nextPerm(int[] a) {
  int i, k;
  for (i = a.length-2; i >= 0 && a[i] > a[i+1]; i--);
  if (i < 0) return false;
  for (k = a.length-1; a[i] > a[k]; k--);
  swap(a, i, k);
  k = 0;
  for (int j = i+1; j < (a.length+i)/2+1; j++) {
    swap(a, j, a.length-k-1);
    k++;
  }
  return true;
}
def member[A](l: List[A]): List[(A,List[A])] = l match
  case a :: Nil => List((a, Nil))
  case a :: t => (a, t) :: (for (a2, l2) <- member(t)
    yield (a2, a :: l2))

def permutations[A](l: List[A]): Iterable[List[A]] = l match
  case Nil => Iterable(List())
  case _ => for (a, l2) <- member(l);
    p <- permutations(l2) yield a :: p
member([H|T], H, T).
member([H|T], E, [H|T2]) :- member(T, E, T2).

permutation([], []).
permutation(L, [H|TP]) :-
    member(L, H, T),
    permutation(T, TP).
Editor's note

The Prolog version is the most concise and directly captures the relational essence: "permutation(L, [H|TP]) holds if H is any element of L, T is the rest, and TP is any permutation of T". The member/3 predicate intrinsically generates multiple solutions through backtracking.

2. Resolution (Without Unification)

We start with a simplified resolution system using propositional (0-ary) goals, then extend it with unification. This core abstract syntax is the foundation:

Clause ::= Goal :- Goal1, ..., Goaln    (n >= 0)
Program ::= Clause1 ... Clausek          (k > 0)
  • A clause with empty body is a fact, written simply as G.
  • A clause with non-empty body is a rule, written G :- G1,..,Gn.
  • A list of goals is called a resolvent.

Resolution Step

Given initial resolvent R0 = G1, G2, ..., Gn, a valid computation step is:

G1, G2, ..., Gn  ->  G'1, ..., G'm, G2, ..., Gn

...if there exists a clause G' :- G'1, ..., G'm in the Program and G' = G1. Given a resolvent there may be many valid next resolvents. With clauses a. and a :- b, c. and resolvent a, c, d there are exactly two steps: a, c, d → c, d (the list of goals shrinks) and a, c, d → b, c, c, d (it grows).

Resolution Tree

For each resolvent, its first goal may match the head of many clauses (considered top to bottom), so many child resolvents may exist. A resolution succeeds if there is a leaf with an empty resolvent. The tree is possibly infinite and is explored depth-first, left to right; going up the tree to find a new solution is called backtracking.

a.           % a clause with empty body is called a "fact"
b.           % multiple copies of rules/facts can occur
b.
b :- z.      % b is the rule "head", z is the "body"
c.           % different clauses can have same "head"
c :- a, c.   % a sort of recursive rule
c :- b.
d :- d.      % .. recall the order of clauses is relevant

With this program ?- a. has one solution; ?- b. has two (the third clause leads to z, which has no clause: failure); ?- c. has infinitely many solutions, and the branch c :- b. is never reached by the depth-first search; ?- d. loops forever without any solution.

Worked example

Follow ?- b. by hand before looking at the tree. The resolvent is b. Prolog scans the program from the top for a clause whose head is b: clause 2 is a fact, so the resolvent becomes empty and that is the first solution. Prolog does not stop there; it remembers that clauses 3 and 4 also have head b and were not tried. Ask for another answer and it goes back to that choice, takes clause 3, and reports a second solution. Ask again and it takes clause 4: the resolvent becomes z, no clause has head z, so this branch fails and there are no more answers. Two solutions, one failure, and every step was either "replace the first goal with a clause body" or "go back to the last untried clause".

Now ?- c.. Clause 5 is a fact: first solution, immediately. Going back, clause 6 rewrites c into a, c. The first goal is now a, clause 1 proves it, and the resolvent is c again, exactly where we started. So clause 5 gives a second solution, clause 6 opens the same branch a third time, and so on without end. Clause 7 (c :- b) would also give solutions, but depth-first search only reaches it after the branch through clause 6 is exhausted, and that branch is never exhausted. This is why the order of clauses matters in Prolog: the set of logical consequences is the same whatever the order, but which answers you actually see, and whether the search terminates, depends on it.

What can we ask of a resolution? Whether it has one solution (predicative use), how many solutions it has (stream-like use), whether it terminates (undecidable in general), and what the output of a solution is — which, without unification, is not yet defined.

The examiner will ask

Given a small program with facts and rules, draw the resolution tree and identify which branches lead to success and which to failure. What happens when a rule recursively calls itself (like c :- a, c.)?

3. Terms and Unification

To make resolution practical, goals need structure. Prolog introduces terms as the data values and unification as the matching mechanism.

Prolog Terms

Term ::= Variable | Number | Functor | Functor(Term1, ..., Termn)
  • Predicate and functor names start with a lowercase letter.
  • Variable names start with an uppercase letter or underscore _.
  • A term with no variables is called ground.

Terms are trees: cons(10, cons(20, cons(30, nil))) is a compound ground term, while student(X, Y, Z) is a compound non-ground term.

Substitution

A substitution θ = {X1/T1, ..., Xn/Tn} maps variables to terms; the terms Tj must not contain any of the variables Xk (so {X/a(1,Z), Z/W} is invalid and must be rewritten as {X/a(1,Z), W/Z}). For example: {X/10, Y/hello}. Applying it to a term replaces variables: p(X, a, Y){X/10, Y/hello} = p(10, a, hello).

  • Equivalence: {X/Y, Z/10} ≡ {Y/X, Z/10}.
  • Generality: {X/10} is more general than {X/10, Y/2}.
  • Composition: {X/10}{Y/X} ≡ {X/10, Y/10}; {X/10}{X/5} is impossible.
  • Instance: p(10, b) is an instance of p(X, b).
  • Cloning: clone(p(10,X,X,Y)) = p(10,X2,X2,Y2) with X2, Y2 fresh variables — this is what happens to a clause each time it is used in a resolution step.

Most General Unifier (MGU)

Worked example

Unify a(X, Y, A, b(W)) with a(Z, Z, B, b(1)) by hand. Both are compound terms with the same functor a and the same arity, so unification proceeds argument by argument; had the functors or arities differed, it would fail at once. First arguments: X and Z are two variables, so bind one to the other, {X/Z}. Second arguments: Y and Z, another variable pair, {Y/Z}; note that X, Y and Z are now one variable in three names. Third arguments: A and B, {A/B}. Fourth arguments: b(W) and b(1), same functor, so descend: W against 1 gives {W/1}. The result {X/Z, Y/Z, A/B, W/1} makes both terms a(Z, Z, B, b(1)).

The second row of the table is the instructive failure: a(1, 2) against a(X, X). The first argument gives {X/1}. The second argument is then 2 against X, but X is already 1, and 1 and 2 are different constants. There is no substitution that makes the two terms equal, so the unifier is ⊥. Bindings accumulate as you go, and a later argument must respect the ones already made.

The MGU of two terms T1 and T2 is a substitution θ such that θT1 = θT2 (they become identical) and it is the most general such substitution.

T1T2MGU
a(1, 2)a(X, Y){X/1, Y/2}
a(1, 2)a(X, X)⊥ (no unifier)
a(1, b(X))a(Y, b(Z)){X/Z, Y/1}
a(X, Y, A, b(W))a(Z, Z, B, b(1)){X/Z, Y/Z, W/1, A/B}
Unification is symmetric pattern matching

Unlike pattern matching in FP (which is directional), unification works both ways. It binds variables to non-variable terms, and groups some variables together (in the last row above: W/1, and groups (X, Y, Z) and (A, B)). This enables Prolog's distinctive "multiple modes" for the same predicate. The mgu can be tested directly in Prolog: ?- p(X,1) = p(2,Y). gives X/2, Y/1, and ?- p(X,1) \= p(2,Y). fails. The algorithm computing the mgu is due to Martelli and Montanari (1982).

4. Full Prolog Resolution

Combining resolution with unification gives us the full Prolog computation model. The computation state is a pair of resolvent + substitution:

State = <Resolvent : Substitution>

Resolution Step (with Unification)

If G' :- G'1, ..., G'm is a clone of a clause in the program (with fresh variables), and θ' = mgu(G', G1) exists, then:

<G1, G2, ..., Gn : θ> → <(G'1, ..., G'm, G2, ..., Gn)θ' : θθ'>

A solution is the substitution θ at a leaf with an empty resolvent. For simplicity, of the θ in a configuration only the part mentioning variables of the current resolvent and of the input resolvent needs to be kept: bindings of clone variables that no longer occur anywhere can be dropped.

father(abraham, isaac).
father(terach, abraham).
grandfather(GF, GS) :- father(GF, F), father(F, GS).

% Example 1: fact match, empty resolvent
<father(terach, X) : {}>  -->  <yes : {X/abraham}>
% Example 2: theta' must be kept, X is used in the remaining goal
<father(terach, X), father(X, Y) : {}>  -->  <father(abraham, Y) : {X/abraham}>
% Example 3: cloned rule grandfather(GF', GS') :- father(GF', F'), father(F', GS')
% theta' = {GF'/terach, GS'/X}, nothing of it needs to be recalled afterwards
<grandfather(terach, X) : {}>  -->  <father(terach, F'), father(F', X) : {}>

5. Basic Programming: Facts, Rules, Queries

Program as Database

A Prolog program with ground facts acts like a database. A single ground goal queries for a specific tuple:

male(isaac).
plus(2, 3, 5).
plus(1, 6, 7).
plus(0, 0, 5).
?- plus(2, 3, 5).              % Yes : {}
?- plus(0, 0, 0).              % No
?- plus(2, 3, 5), plus(1, 6, 7). % Yes : {}

All facts of a given predicate (name + arity) form a "table"; a ground goal asks whether a tuple is in it. In resolution trees "yes" denotes the empty resolvent and "no" a node with no children.

Existential Queries

If the goal has variables, Prolog finds instantiations (substitutions) making it true:

?- plus(0, X, Y).          % {X/0, Y/5}
?- plus(X, Y, 5).           % {X/2, Y/3}; {X/0, Y/0}
?- plus(X, Y, Y).           % No

Each fact unifying with the goal opens one branch, and the unifier is the solution. When multiple goals are combined, Prolog inherently explores combinations, similar to a for-comprehension with several generators:

?- plus(X, Y, Z), plus(W, K, Z).
% {X/2, Y/3, Z/5, W/2, K/3}; {X/2, Y/3, Z/5, W/0, K/0}; {X/1, Y/6, Z/7, W/1, K/6}; ...

Universal Facts

Variables in facts are universally quantified. A fact like plus(0, X, X). means "0 plus X equals X for all X":

plus(0, X, X).     % universal fact
plus(X, 0, X).     % another one: variable names are local to the clause
?- plus(0, 3, 3).  % Yes
?- plus(0, 5, R).  % {R/5}   (internally {R/5, X'/5}: X' is a clone variable, not shown)
?- plus(3, 0, X).  % {X/3}   (no clash: the clause's X is renamed when cloned)
?- plus(0, 0, X).  % {X/0}; {X/0}  (one solution per matching clause)

Wildcard Variables

The anonymous variable _ matches anything and each occurrence is independent. It is good practice to use _ for variables used only once in a clause, avoiding copy-paste errors.

p(_, 1).
p(1, 2).
q(_, a(1, _)).     % the two _ are different variables
r(X, a(1, X)).     % the two X are the same variable

?- p(X, 1).        % Yes (uses first clause, X unbound)
?- p(1, Y).        % {Y/1}; {Y/2}
?- p(1, _).        % Yes; Yes  (in a goal, _ is a variable we do not want in the solution)
?- q(1, a(1, 2)).  % Yes
?- r(1, a(1, 2)).  % No

Working with Records

Facts can relate structured terms (records), combining predicate names with functors:

manager(person(john, smith, 1283)).
clerk(person(jim, white, 3475)).
chief(person(john, smith, 1283), person(george, red, 8765)).

?- chief(X, person(Y, Z, 8765)).
% X/person(john, smith, 1283), Y/george, Z/red

6. Algebraic Data Types in Prolog

Prolog has no type system, but we model data types using functors (constructors) and predicates (functions converted to relations). A function f: I1,...,In → O becomes predicate p(I1,...,In, O).

Booleans

b_not(b_true, b_false).
b_not(b_false, b_true).
b_and(B, b_true, B).
b_and(B, b_false, b_false).

b_or(B1, B2, B) :- b_not(B1, NB1), b_not(B2, NB2), b_and(NB1, NB2, NB), b_not(NB, B).
b_implies(B1, B2, B) :- b_not(B1, NB1), b_or(NB1, B2, B).

Peano Numbers

Natural numbers encoded as zero, s(zero), s(s(zero)), ... using functors s/1 and zero/0:

succ(X, s(X)).
sum(X, zero, X).
sum(X, s(Y), s(Z)) :- sum(X, Y, Z).

mul(X, zero, zero).
mul(X, s(Y), Z) :- mul(X, Y, W), sum(W, X, Z).

factorial(zero, s(zero)).
factorial(s(X), Y) :- factorial(X, Z), mul(s(X), Z, Y).

greater(s(_), zero).
greater(s(N), s(M)) :- greater(N, M).
?- sum(s(s(s(zero))), s(s(zero)), N).  % N / s(s(s(s(s(zero)))))
?- mul(s(s(zero)), s(s(zero)), N).     % N / s(s(s(s(zero))))
?- factorial(s(s(s(zero))), N).        % N / s(s(s(s(s(s(zero))))))
?- sum(s(s(s(zero))), s(s(zero)), N).
   sum(s(s(s(zero))), s(zero), Z') : {N/s(Z')}
   sum(s(s(s(zero))), zero, Z'') : {N/s(Z'), Z'/s(Z'')} = {N/s(s(Z''))}
   yes : {N/s(s(s(s(s(zero)))))}
Relational interpretation

"The sum of X and successor of Y is the successor of Z provided the sum of X and Y is Z." This reads as a logical statement, not an algorithm — the same predicate can compute sum, check sum, or find decompositions (?- sum(N, M, s(s(s(zero)))). enumerates all pairs).

Three Idioms for Mapping Functions to Predicates

  • Functions returning a boolean: f: I1,...,In → bool becomes p(I1,...,In); the result is whether the call succeeds or fails, so only the positive cases are programmed (see greater/2 above: ?- greater(s(zero), s(zero)). → No).
  • Multiple outputs: no pairs; f: I → O1 × O2 becomes p(I, O1, O2): nextprev(s(N), N, s(s(N))). — ?- nextprev(s(s(zero)), P, N). → {P/s(zero), N/s(s(s(zero)))}; ?- nextprev(zero, P, N). → No.
  • Multiple results: no lazy list; a function returning a stream becomes a predicate with many solutions: 
    range(N1, N2, N1).
range(N1, N2, N) :- greater(N2, N1), range(s(N1), N2, N).
% ?- range(zero, s(s(s(zero))), N).  -->  N/zero; N/s(zero); N/s(s(zero))

Lists with cons/nil

% Find element in list
find(cons(E, _), E).
find(cons(_, T), E) :- find(T, E).

% Position of element (Peano)
position(cons(E, _), zero, E).
position(cons(H, T), s(N), E) :- position(T, N, E).

% Concatenation
concat(nil, L, L).
concat(cons(H, T), L, cons(H, M)) :- concat(T, L, M).

% Count occurrences
count(nil, E, zero).
count(cons(E, L), E, s(N)) :- count(L, E, N).
count(cons(E, L), E2, N) :- E \= E2, count(L, E2, N).

7. Built-in Predicates and List Syntax

Standard List Notation

Instead of cons/nil, Prolog uses built-in list syntax with [] for empty list and [H|T] for list construction:

[H1, H2, ..., Hn | T]   % instead of '.'(H1, '.'(H2, ..., '.'(Hn, T)...))
[H1, H2, ..., Hn]       % instead of [H1, H2, ..., Hn | []]
% special cases: [H|T], [], [E1,E2], [_|T], [E1,_|_]

Library predicates assume these functors: append/3, member/2 (like our find/element), reverse/2, and many others. This is the standard syntax to always use.

?- append([a,b], [c], L).            % L/[a,b,c]
?- append([a,b], [c], [H|T]).        % H/a, T/[b,c]
?- append([a,b], [c], [_,_,_]).      % Yes
?- append([a,b], [c], [_,_,_,_]).    % No
?- append([a,b], [c], [_,_,E]).      % E/c
?- append([a,b], [c], [_,_|T]).      % T/[c]
find([E|_], E).
find([_|T], E) :- find(T, E).

position([E|_], zero, E).
position([H|T], s(N), E) :- position(T, N, E).

join([], L, L).
join([H|T], L, [H|M]) :- join(T, L, M).

Full Relationality

A predicate is fully relational if all arguments can be either input or output. find/2 can: check membership, enumerate elements, or generate lists containing an element:

?- find([a,b,c], E).       % E/a; E/b; E/c (enumerate)
?- find(L, a).              % L/[a|_]; L/[_,a|_]; ... (generate, infinitely many)
?- join(L, M, [a,b,c]).     % L/[], M/[a,b,c]; L/[a], M/[b,c]; L/[a,b], M/[c]; L/[a,b,c], M/[]

Full relationality is often achievable for simple predicates but not for complex algorithms, especially when enumeration is not "directional" (checking that a list contains 10, 20 and 30 is easy; enumerating all such lists is not). A typical pitfall: ?- permutation(L, [a,b]). with the permutation/2 of Section 1 gives L/[a,b] and then loops forever looking for more, because member/3 called with an unbound list keeps generating longer lists. In principle a breadth-first visit of the resolution tree would find all solutions, at a very high cost.

I/O Notation (Documentation Only)

Not Prolog syntax, but a convention used in comments to document the intended mode of each argument: + input, - output, ? input or output, @ input that must be ground. Examples: member(?E, ?L), permutation(+LI, -LO), append(?L1, ?L2, ?L), is(-O, @Expression).

Math Operators

OperatorMeaningExample
=/2Unification?- p(1,2) = p(X,Y). % X/1, Y/2
\=/2Non-unification?- a(1,2) \= a(1,3). % Yes
=:=/2Numeric equality?- 10 =:= 5+5. % Yes
=\=/2Numeric inequality?- 10 =\= 20. % Yes
is/2Evaluate arithmetic expression?- X is 10+20. % X/30
>/2, </2, >=/2, =</2Numeric comparisons (note =<, not <=)Both args must be ground numbers/expressions (not relational)

An operator is just a predicate or functor that can be written in infix (binary) or prefix (unary) notation: '='(p(1,2), p(X,Y)) and p(1,2) = p(X,Y) are the same goal. Numbers such as 10, -20.1, 1.3e-4 are ground terms, and + - * / are ordinary binary functors, so 10+20 is the term '+'(10,20), an abstract syntax tree of a math expression.

?- X = 10 + 20.       % X/'+'(10,20)   (= only unifies: + is just a functor)
?- X is 10 + 20.      % X/30           (is evaluates)
?- 30 is 10 + 20.     % Yes
?- 10 is p(20).       % error: not an arithmetic expression
?- 10 is X + 5.       % error: the expression contains an unbound variable
Warning

is/2 evaluates the right argument as an arithmetic expression (which must be ground) and unifies the result with the left argument. It does not perform unification of terms: do not use it to unify. Predicates doing math are very often not relational.

sum([], 0).
sum([H|T], S) :- sum(T, N), S is H + N.

% ?- sum([10,20,30], S).  -->  S/60
% ?- sum([10,20,30], 60). -->  Yes
% resolution: sum([20,30], S'), S is 10+S'  ...  S'' is 30+0, S' is 20+S'', S is 10+S'  ...  {S/60}

Console I/O for Debugging

write/1 and nl/0 print a term and a newline on the console; the course uses them only for "debugging by logging". Note that they succeed as side effects, outside the relational reading of the program:

sum([], 0).
sum([H|T], N) :- sum(T, N2), write(N2), nl, N is H + N2.
% ?- write('start'), nl, sum([10,20,30], N).   prints: start 0 30 50

8. Building Algorithms: Tail Recursion, Combinations

Performance

Prolog is traditionally "not as fast as C" (professional implementations are rather fast; tuProlog is not, being a JVM layer whose goal is not speed). The performance of a predicate is characterised first of all by the number of resolution steps; each step searches a matching clause, computes an mgu and updates the resolvent, which we may assume to be constant-time although it actually depends on the number of clauses, variables and goals.

Tail Recursion in Prolog

A recursion is tail if the recursive call is the last goal in the body. Prolog, like FP, can optimise tail calls, but with an important difference: Prolog supports tail-recursive foldright-like list construction (using [H|T] unification), which is not possible in FP with immutable structures.

Non-tail recursiveTail recursive
sum/2 sum([],0).
sum([H|T],N) :- sum(T,N2), N is H+N2.
Idiomatic; the resolvent grows with pending is goals and computation happens as the recursion unwinds (~2n resolution steps)		 sum(L,S) :- sum(L,0,S).
sum([],S,S).
sum([H|T],N,S) :- N2 is H+N, sum(T,N2,S).
Less direct (accumulator argument), but computes during recursion and keeps resolvents small
join/3 Not shown (less idiomatic) join([],L,L).
join([H|T],L,[H|T2]) :- join(T,L,T2).
Constructs output while recurring (foldright-like but tail!)
Prolog's unique advantage

Foldright-like construction in join/3 is tail recursive because the output list is built incrementally through [H|T2] unification — the variable T2 becomes bound to the tail as the recursion depth increases. This is impossible in pure FP.

Immutability and Sharing

Prolog terms are immutable: they never change. The only declarative "side effect" is unifying a variable (binding it to a term). Structure sharing means the output list in update/4 shares unchanged suffixes with the input:

update([], _, _, []).
update([E1|T], E1, E2, [E2|T]).         % found it
update([H1|T1], E1, E2, [H1|T2]) :- 
    update(T1, E1, E2, T2).

After ?- update([10,20,30,40], 20, 21, L). → L/[10,21,30,40], the output list's tail [30,40] is shared with the input list.

Generating Combinations

The combination of multiple goals inherently generates Cartesian products of solutions:

?- member(X,[10,20,30]), member(Y,[1,2]), Res is X+Y.
% Res/11; Res/12; Res/21; Res/22; Res/31; Res/32

In general, if goal Gi of a resolvent has ki solutions and they do not constrain the following goals, the resolvent has ∏ki solutions. 9. The Cut Predicate

The pervasive branching and backtracking of Prolog is a feature, but sometimes it creates spurious solutions or unnecessary computation. The cut (!) is a zero-ary predicate that prunes the search tree.

Motivation: Merge

% Without cut: spurious solutions
merge(Xs, [], Xs).
merge([], Ys, Ys).
merge([X|Xs], [Y|Ys], [X|Zs]) :- X < Y, merge(Xs, [Y|Ys], Zs).
merge([X|Xs], [Y|Ys], [Y|Zs]) :- X >= Y, merge([X|Xs], Ys, Zs).

?- merge([], [], L).         % L/[]; L/[] (two identical solutions!)
?- merge([10,20], [5,35], L). % L/[5,10,20,35]; No (spurious failure)
Worked example

Take the query merge([], [], L). The first clause matches with Xs = [], so Prolog answers L = [] and, as always, remembers that clause 2 is still untried. If you ask for another solution it goes back, tries clause 2, which also matches with Ys = [], and answers L = [] a second time. Nothing is wrong with either answer; the problem is that the program describes the empty case twice, and Prolog dutifully reports both.

Now merge([10,20], [5,35], L). Clauses 1 and 2 do not match, because neither list is empty. Clause 3 matches with X = 10, Y = 5, tests 10 < 5, fails. Clause 4 matches, tests 10 >= 5, succeeds, and recurses on merge([10,20], [35], Zs). This continues correctly down to L = [5,10,20,35]. But the calls left pending alternatives behind: at every level where clause 3 succeeded, clause 4 was still untried (where clause 4 was chosen, clause 3 had already failed, so nothing is pending there), and at the base case clauses 3 and 4 were never tried. When you ask for a second solution, Prolog revisits all of them. Each one fails, either because X >= Y is false where X < Y held or because a non-empty pattern cannot match the empty list, but only after doing the work. That is the No after the first answer: not a wrong result, a search that carries on when there is nothing left to find.

Both symptoms have the same cause. Once a clause has been chosen and its test has passed, the alternatives for that call can never succeed, yet Prolog keeps them. The cut is the way to say so. Read merge(Xs, [], Xs) :- !. as "if the second list is empty, this is the answer, do not try the other clauses for this call". Read the ! after X < Y in clause 3 as "the comparison held, so commit to this clause: forget clause 4 for this call". With that commitment, clause 4 no longer needs its own test X >= Y, because it is only ever reached when X < Y has already failed. Compare the two programs line by line: the cut version is the same program with the redundant search removed.

% With cut: clean solutions
merge(Xs, [], Xs) :- !.
merge([], Ys, Ys).
merge([X|Xs], [Y|Ys], [X|Zs]) :- X < Y, !, merge(Xs, [Y|Ys], Zs).
merge([X|Xs], [Y|Ys], [Y|Zs]) :- merge([X|Xs], Ys, Zs).

What Cut Prunes

The cut is a 0-ary predicate used as a goal in the body of a rule. It always succeeds, and as a side effect it discards local pending branches:

  • the successive matching clauses of the predicate (alternatives for the head that generated the cut);
  • the pending alternative solutions of the goals to the left of ! in the current body.

Precise semantics: when the cut is executed, all pending branches below the node that first generated that cut (i.e. the node where the clause containing ! was selected) are pruned.

go :- p, a.
go :- ...
r.
r.
p :- q.
p :- r, !, t, u.
p :- v.
p :- z.
% ?- go.   resolvent p, a  selects p :- r, !, t, u  giving  r, !, t, u, a
% r has two clauses: two branches  !, t, u, a  (the second one is pending)
% executing ! moves to  t, u, a  and prunes: the second branch of r (left of !)
% and the branches for p :- v and p :- z (successive clauses of p).
% The alternative go :- ... is NOT pruned: it belongs to a node above.

In the merge/3 with cut above, the first cut prunes the pending branch of the second fact (so merge([],[],L) gives one solution) and the cut in the third clause prunes the fourth clause, which therefore no longer needs to test X >= Y.

Applications

% Computing first index of an element
first_index_of([E|_], E, 0) :- !.
first_index_of([_|T], E, N) :-
    first_index_of(T, E, N2), N is N2 + 1.
% ?- first_index_of([a,b,b,c], b, N).
%    first_index_of([b,b,c], b, N2'), N is N2'+1
%    !, N is 0+1        (second clause for [b,b,c] is pruned here)
%    N is 0+1  -->  {N/1}   and no further solutions

% Alternative: a relational index_of/3 plus a wrapper with cut
index_of([E|_], E, 0).
index_of([_|T], E, N) :- index_of(T, E, N2), N is N2 + 1.

% here the cut prunes the pending solutions of index_of (goal to its left)
% Quicksort

    partition(Xs, X, Ls, Bs),
    quicksort(Ls, LOs),
    quicksort(Bs, BOs),

partition([X|Xs], Y, Ls, [X|Bs]) :- partition(Xs, Y, Ls, Bs).

% ?- partition([10,3,20,5,30,9,40], 10, L1, L2).  -->  L1/[3,5,9], L2/[10,20,30,40]
% ?- quicksort([60,10,20,50,30,40], L).           -->  L/[10,20,30,40,50,60]

Cut is also the standard way to make a predicate fully relational by dispatching on the shape of the input (var/1 is presented in the next section):

% fully-relational size: computes the length, or generates a list of N variables

generate([], 0) :- !.
generate([_|T], N) :- N2 is N-1, generate(T, N2).

length([], 0).
length([_|T], N) :- length(T, N2), N is N2 + 1.
% ?- size([10,20,30], N).  -->  N/3
% ?- size(L, 3).           -->  L/[_,_,_]
The examiner will ask

Given a program with cuts, identify exactly which branches are pruned when a goal is executed, and which node "generated" the cut. In classic Prolog terminology (not used in the slides) a cut is green if removing it does not change the set of solutions (it only avoids useless work) and red if it does (e.g. first_index_of/3, or the last clause of merge/3, which relies on the cut to avoid re-testing X >= Y).

Bidirectional lists: a list with a cursor can be modelled as bilist(Left, Right), where Left holds the elements before the cursor in reverse order, so that moving the cursor left/right and adding on either side take constant time: bilist([1],[2,3,4,5,6]) → move right → bilist([2,1],[3,4,5,6]).

Partially Instantiated Structures as Lazy Data

A non-ground compound term is a data structure that is partially completed: [1,2,3|_] is a list starting with 1,2,3 that can still be extended by binding its tail. This gives a form of lazy, expanding structure. Example: a cache of factorials that is both input and output of the predicate:

% factorial(+N, -Out, ?Cache), Cache is a partial list of factorials [1,1,2,6,24|_]
factorial(N, Out, Cache) :- factorial(N, Out, Cache, 0).

factorial(N, Res, [Res|_], N) :- !, nonvar(Res).        % reached position N: Res must be known
factorial(N, Out, [H, V|T], I) :-                         % next cell is a hole: fill it
    var(V), !, I2 is I + 1, V is H * I2,
    factorial(N, Out, [V|T], I2).
factorial(N, Out, [_, V|T], I) :-                         % next cell known: move on
    I2 is I + 1, factorial(N, Out, [V|T], I2).

% ?- C = [1,1,2,6|_], factorial(5, Res, C).  -->  Res/120, C/[1,1,2,6,24,120|_]

11. Metaprogramming and Metainterpretation

Metaprogramming is the technique by which programs treat other programs as data: reading and reasoning about them, updating or synthesising them, executing them under different conditions. Java has reflection, Scala has macros and inline metaprogramming; in Prolog it is exceptionally simple and direct because everything is a term — clauses, goals, and data all share the same representation, even syntactically. This is what makes Prolog a component of symbolic-AI systems. Ingredients: everything is a term; predicates to "call" terms; dynamic theories; metainterpretation.

Everything is a Term

Prolog syntax is just surface notation for standard terms:

Surface syntaxInternal term
[A, B, C]'.'(A, '.'(B, '.'(C, '[]')))
(A, B, C)','(A, ','(B, C))
X = 1'='(X, 1)
-X'-'(X) (unary prefix operator)
[A, B, C | T]'.'(A, '.'(B, '.'(C, T)))

{ A, B }'{}'(','(A, B))
?- {0, 1, 2+3} = '{}'(A), A =.. L.
% A/(0, 1, '+'(2,3))     L/[',', 0, (1, '+'(2,3))]

Operators and DSLs

An operator is a predicate or functor declared to have a special syntax: infix if binary, prefix if unary; it can also be a symbol used without quotes. It must be declared with op(Priority, Type, Name) before use: the priority is a number giving precedence with respect to other operators, the type is xfx, xfy, yfx (infix: non-associative, right-, left-associative) or fx/fy (prefix). Operators can be used as predicates, as functors, or to build domain-specific notations (they work in tuProlog 3.3; tuProlog 4 has bugs here):

% use as predicate
:- op(100, xfx, '~').
N1 ~ N2 :- N1 > N2, !, Delta is N1 - N2, Delta < 0.1.
N1 ~ N2 :- N2 ~ N1.
% ?- 10 ~ 10.01.  -->  Yes

% use as functor
:- op(100, xfy, '::').
to_list(A :: B, [A | B2]) :- to_list(B, B2).
to_list(nil, []).
% ?- to_list(10 :: 20 :: 30 :: nil, L).  -->  L/[10,20,30]

% use as DSL
:- op(100, fx, [person, name, age, nationality, married]).
person {
    name 'Rossi Marco',
    age 30,
    nationality italy,
    married false
}.
% ?- person { name NM, age A, nationality N, married M }.
% -->  NM/'Rossi Marco'  A/30  N/italy  M/false

Predicates for Solving Goals

Since a goal is a term, the library can "call" terms. In all of the following G is a term with any of the syntax above; if it is (G1, ..., Gn) it is handled as a resolvent:

PredicateMeaning
call(+G)solves the goal (all solutions, by backtracking)
once(+G)solves the goal with at most one solution (like call(G), !)
not(+G)succeeds iff G has no solution; never binds variables (negation as failure)
true, failalways succeeds / always fails
findall(+Res, +Goal, -List)solves Goal in all ways, collecting an instance of Res for each solution in List (empty list if none)
bagof/3, setof/3variations of findall (grouping by free variables; setof sorts and removes duplicates) — less used
(G ; G')disjunction: either G or G' (or both) should be solvable; it introduces a branch

Together with =.. this gives "higher-order" predicates, by passing a predicate name or a goal as an argument (the pair X, P in filter/4 plays the role of a lambda):

% map(+L, +P, -LO): apply binary predicate P to each element
map([], _, []).
map([H|T], P, [H2|T2]) :- G =.. [P, H, H2], once(G), map(T, P, T2).
inc(N, N2) :- N2 is N + 1.
% ?- map([10,20,30], inc, L).  -->  L/[11,21,31]

% ?- findall([X,Y], (member(X,[1,2,3]), member(Y,[1,2,3])), L).
% -->  L/[[1,1],[1,2],[1,3],[2,1],...,[3,3]]

% filter(+L, X, P, -LO): X is the "parameter" of the goal P
filter(L, X, P, LO) :- findall(X, (member(X, L), once(P)), LO).
% ?- filter([10,21,30,40,50], X, X > 25, LO).  -->  LO/[30,40,50]

% lab variant: a mapper term cloned with copy_term before each call
% map(+L, +mapper(I,O,Op), -LO)
map2([], _, []).
map2([H|T], M, [H2|T2]) :- map2(T, M, T2), copy_term(M, mapper(H, H2, OP)), call(OP).
% ?- map2([10,20,30], mapper(X, Y, Y is X+1), L).  -->  L/[11,21,31]

The semantics of ; in a body H :- ..., (G ; G'), ... is that of two extra clauses c(X1..Xn) :- G. and c(X1..Xn) :- G'. (X1..Xn the variables of G and G') replacing the disjunction with the goal c(X1..Xn). Other control predicates (->, repeat, ...) are "a step too far": if you use them at the exam you will be asked their exact semantics.

neighbour(X, Y1, X, Y2) :- Y1 is Y2+1 ; Y1 is Y2-1.
neighbour(X1, Y, X2, Y) :- X1 is X2+1 ; X1 is X2-1.

Dynamic Theories

A Prolog program is made of a static theory (the one written in the IDE) and a dynamic one, initially empty, where clauses can be added or removed at runtime (some Prologs, e.g. tuProlog 3.3/4.0, have a single theory, which is dynamic). Since clauses are terms, the API is straightforward:

assert(+Clause).      % adds a clause: always succeeds, never binds
                      % e.g. assert(p(1)), assert((p(X) :- q(X)))
asserta/assertz       % assert on top / at the bottom
retract(+Clause).     % removes a matching clause if it exists, possibly binding variables
retractall(+Clause).  % removes all matching clauses: always succeeds, never binds
clause(?Head, ?Body). % queries the theory: Body is true for a fact, (G1,...,Gn) in general
factorial(0, 1).
factorial(X, Y) :- Xm is X-1, factorial(Xm, Y2), Y is Y2*X.

withcache(P) :- cached(P), !.
withcache(P) :- once(P), assert(cached(P)).

% ?- cached(X).                     -->  No
% ?- withcache(factorial(3, N)).    -->  N/6      (computed, then cached)
% ?- cached(X).                     -->  X/factorial(3,6)
% ?- clause(cached(X), B).          -->  X/factorial(3,6), B/true
% ?- withcache(factorial(4, N)).    -->  N/24
% ?- findall(C, cached(C), L).      -->  L/[factorial(3,6), factorial(4,24)]

withcache/1 can be understood as a metainterpreter for single-result predicates that adds caching to the standard interpretation.

The Vanilla Metainterpreter

An interpreter reads and executes a program; a metainterpreter is an interpreter written in the same language as the programs it interprets — typically in order to change the interpretation strategy. In Prolog this is easy because programs are terms and "resolution" is just substituting heads with bodies. As a preliminary step, resolution can be simulated with clauses represented as rule(Head, BodyList) facts: unification is done by the call to rule/2, branching by its multiple clauses, and head/body substitution by append/3:

rule(a, []).      % means: a.
rule(b, []).      % means: b.
rule(d, []).      % means: d.
rule(d, []).      % means: d.
rule(c, []).      % means: c.
rule(c, [c]).     % means: c :- c.
rule(search(E, [E|_]), []).
rule(search(E, [_|T]), [search(E, T)]).

solve([]).
solve([Goal|Rest]) :- rule(Goal, Body), append(Body, Rest, NewGoals), solve(NewGoals).

% ?- solve([a]).  -->  yes          ?- solve([d]).  -->  yes; yes
% ?- solve([e]).  -->  no           ?- solve([c]).  -->  yes; yes; yes; ...
% ?- solve([search(X, [10,20,30])]).  -->  X/10; X/20; X/30    (full resolution!)

The Vanilla metainterpreter does the same on standard clauses, read from the theory with clause/2:

solveV(true) :- !.
solveV((A, B)) :- !, solveV(A), solveV(B).
solveV(G) :- clause(G, B), solveV(B).

% search(E, [E|_]).  search(E, [_|T]) :- search(E, T).
% ?- solveV(search(X, [10,20,30])).  -->  X/10; X/20; X/30

It already works for user-defined predicates. Its "defects" are also features: it cannot deal with built-in library predicates (not defined by clauses), and control predicates must be reimplemented in the metainterpreter — which means one explicitly picks what to support:

builtins(['is', '=', '\\=', '==']).

solveB(true) :- !.
solveB((A, B)) :- !, solveB(A), solveB(B).
solveB(G) :- functor(G, F, _), builtins(B), member(F, B), !, call(G).
solveB(once(G)) :- !, once(solveB(G)).
solveB(not(G)) :- !, not(solveB(G)).
solveB(G) :- clause(G, B), solveB(B).

% sum([], 0).  sum([H|T], N) :- sum(T, N2), N is N2 + H.
% ?- solveB(sum([10,20,30], S)).          -->  S/60
% ?- solveB(not(sum([10,20,30], 50))).    -->  Yes
% ?- solveB(not(sum([10,20,30], 60))).    -->  No

The third clause handles built-ins by calling them as such (call(G)); the fourth and fifth handle one control predicate each. Note the cuts, which make the dispatch deterministic.

Why metainterpretation matters

Metainterpreters give us control over the execution strategy. We can reorder solutions (by inverting clause order), add tracing, impose resource bounds, implement debugging, or change the search strategy entirely:

% Metainterpreter that inverts solution order
solveI(true) :- !.
solveI((A, B)) :- !, solveI(A), solveI(B).
solveI(G) :-
    findall(c(G, B), clause(G, B), L),
    reverse(L, L2),
    member(c(G, B), L2),
    solveI(B).

% Metainterpreter that tracks computation trace and bounds depth
solveT(G, T, B) :- solveT(G, T, B, _).
solveT(true, [], N, N) :- !.
solveT((A, B), L, IN, ON) :- !,
    solveT(A, LA, IN, ON1),
    findall((X, B), member(X, LA), LL),
    solveT(B, LB, ON1, ON),
    append(LL, LB, L).
solveT(G, [G|T], I, O) :-
    I > 0, !, clause(G, B), I2 is I-1, solveT(B, T, I2, O).

% ?- solveI(search(X, [10,20,30])).   -->  X/30; X/20; X/10
% ?- solveT(search(X, [10,20,30]), T, 2).
% -->  X/10, T/[search(10,[10,20,30])]
% -->  X/20, T/[search(20,[10,20,30]), search(20,[20,30])]
% -->  no      (X/30 would need 3 steps, beyond the bound)

solveI collects all matching clauses upfront with findall, so branches can be analysed, prioritised or discarded before exploring them. solveT returns, together with the solution, the list of goals resolved along the way (useful for debugging) and decrements a counter at each step, failing when the bound is exhausted (useful to prune long computations).

Check Your Understanding

Explain the difference between resolution with and without unification. Why is unification necessary for practical Prolog programming?

Without unification (propositional resolution), goals are atomic symbols that either match or don't. With unification, goals have structure (terms with variables), and matching produces a substitution that makes the goals identical. Unification is necessary for expressing relationships between data elements, implementing pattern matching, and producing result bindings.

What is the MGU of a(1, b(X)) and a(Y, b(Z))? Walk through the Martelli-Montanari algorithm.

MGU = {X/Z, Y/1}. The algorithm: decompose a(1,b(X)) = a(Y,b(Z)) gives equations 1=Y and b(X)=b(Z). Decompose b(X)=b(Z) gives X=Z. The resulting substitution is {Y/1, X/Z}.

Given the program: a. b. b. b :- z. c. c :- a, c. c :- b. d :- d. Describe the resolution tree of ?- c. and of ?- d.

?- c has three matching clauses, tried top to bottom. c. gives the empty resolvent: first solution. c :- a, c. gives resolvent a, c; a. reduces it to c, which is the same situation as the root: another solution from c., then again c :- a, c., and so on. The tree is infinite with infinitely many solutions, and since the search is depth-first the third branch c :- b. (which would give two more solutions, plus a failure through z) is never reached. ?- d has one clause d :- d., whose body is again d: an infinite branch with no solution (no output at all, the computation never terminates).

What does it mean for a Prolog predicate to be "fully relational"? Give an example where this property holds and one where it does not.

A predicate is fully relational if all arguments can serve as either input or output. Example: join/3 is fully relational — it can concatenate two known lists, split a list into all possible pairs, or verify a concatenation. Counter-example: is/2 is not — the right argument must be a ground arithmetic expression; ?- X is 10+Y. throws an error.

Why is join/3 tail-recursive even though it constructs the output list from head to tail (foldright-style)?

Because the output [H|T2] is built by unification of the head: when the clause is selected, the output argument is immediately bound to [H|T2] with T2 a fresh variable (a "hole"), and the recursive call, which is the last goal of the body, will bind T2. Nothing is left to do after the recursive call. In FP with immutable structures the same foldright-like construction is not tail-recursive, because the cons cell can only be built after the recursive result is available. Resolution trace: join([10,20],[30,40,50],L) → join([20],[30,40,50],T2') with {L/[10|T2']} → join([],[30,40,50],T2'') with {L/[10,20|T2'']} → {L/[10,20,30,40,50]}.

What is the difference between is/2, =/2 and ==/2? What do ?- X = 10+20., ?- X is 10+20. and ?- 10 is X+5. give?

=/2 is unification (it binds variables so that the two terms become identical), is/2 evaluates its right argument as a ground arithmetic expression and unifies the result with the left, ==/2 checks that two terms are identical without binding. ?- X = 10+20. gives X/'+'(10,20) (+ is just a functor); ?- X is 10+20. gives X/30; ?- 10 is X+5. raises an error because the expression contains an unbound variable (is/2 is not relational).

Explain precisely what the cut (!) does to the resolution tree. In merge/3 with cuts, which branches does each cut prune?

The cut always succeeds; as a side effect all pending branches below the node that generated it (the node where the clause containing ! was selected) are pruned: the alternative clauses for that head, and the pending solutions of the goals to the left of ! in the body. Branches above that node are untouched. In merge(Xs,[],Xs) :- !. the cut prunes the second fact merge([],Ys,Ys), so merge([],[],L) has a single solution; in merge([X|Xs],[Y|Ys],[X|Zs]) :- X < Y, !, ... the cut prunes the fourth clause, which therefore does not need to test X >= Y (and would be wrong without the cut, which is what makes it a "red" cut in classic terminology). In first_index_of2(L,E,N) :- index_of(L,E,N), !. the cut prunes the pending solutions of index_of, the goal to its left.

What do call/1, once/1, not/1 and findall/3 do? Write filter/4 with findall.

call(G) solves the term G as a goal, with all its solutions by backtracking; once(G) gives at most the first solution; not(G) succeeds iff G has no solution and never binds variables (negation as failure); findall(R, G, L) solves G in all ways and collects an instance of R per solution into L (possibly []). filter(L, X, P, LO) :- findall(X, (member(X, L), once(P)), LO). where X is the variable of P that acts as the parameter, e.g. filter([10,21,30], X, X > 25, LO) gives LO/[30]. Combining =.. and call gives higher-order predicates: G =.. [P, H, H2], call(G) applies predicate name P to H and H2.

What is the effect of assert/1, retract/1 and clause/2? How does withcache/1 add caching to a predicate?

assert(C) adds clause C (a term, e.g. p(1) or (p(X) :- q(X))) to the dynamic theory, always succeeds and never binds (asserta on top, assertz at the bottom); retract(C) removes one matching clause, possibly binding variables; retractall(C) removes all matching clauses; clause(H, B) queries the theory, with B/true for facts. withcache(P) :- cached(P), !. withcache(P) :- once(P), assert(cached(P)). first looks for a cached instance of P (the cut avoids recomputing); otherwise it solves P once and asserts the instantiated goal, so the next call unifies directly with the stored fact.

Describe the Vanilla metainterpreter and how you would extend it to handle built-in predicates and negation as failure.

solveV(true) succeeds. solveV((A,B)) decomposes conjunctions. solveV(G) looks up a clause with clause(G,B) and recurses. To handle built-ins, we check if the goal's functor is in a list of built-in predicates and use call/1 directly. To handle negation as failure, we use not/1 or implement it as "call the goal, if it fails then succeed (with no bindings)".

What are the three Prolog interpretations (logic, relational, procedural)? Which is the most useful for idiomatic Prolog programming?

Logic interpretation: a program is a logic theory, computing is proving a goal is a theorem. Relational interpretation (most useful): a program is a set of predicates over terms, querying is asking for a relation. Procedural interpretation: a program is a set of procedures, computing is calling predicates. The relational interpretation is most productive because it emphasizes the declarative, multi-directional nature of Prolog predicates.
