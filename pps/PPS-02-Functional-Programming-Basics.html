1. Motivations: Why Functional Programming?

Object-oriented programming treats everything as an object with encapsulated state and behaviour. This works well for many domains, but it has limits:

Key idea

FP offers a declarative style: you describe what the result should be, not how to achieve it step by step. This leads to terser, more composable, and more confidently correct code — especially when concurrency enters the picture.

OO approachFP thinking
Everything is an object — verbose for simple behaviourFunctions are first-class values — pass them around directly
Functional interfaces require boilerplateFunction literals are lightweight and pervasive
Step-by-step instruction focusDeclarative, goal-oriented composition
Mutable state complicates concurrencyImmutability by default simplifies parallelism

What FP offers: a smooth abstraction for computing information, techniques to abstract away "internal execution" (imperative) aspects, techniques to support concurrency orthogonally (see PCD), and higher confidence in code correctness by construction. A possible disadvantage for software engineering: functional code is terser and requires higher competence.

Functional ideas have been brought into OO languages, in translated form: "no side-effects" becomes "prefer immutability"; "everything is a function" becomes "use lambdas, use factories to create objects"; "higher-order functions" becomes "use the Strategy pattern to achieve generality"; "abstract evaluation order" becomes "use lazy APIs" (as with streams). Java 8+ lambdas give a smooth syntax for functional interfaces (Strategy, Iterator, Template Method), and Java streams enable a fully declarative, side-effect-free manipulation of collections that transparently exploits multi-core (l.stream().parallel().reduce(...)). But why is the Stream API so different from List's, if both deal with sequences? Java 8+, C# and Kotlin inherited their FP nature from Scala, the pioneer of OOP+FP on the JVM.

The examiner will ask

Why is declarativity valuable for concurrent and distributed systems? What property of pure functions makes them safe to evaluate in parallel?

2. Scala in a Nutshell

Scala ("Scalable Language") was designed by Martin Odersky at EPFL starting in 2001, with the first public release in 2004. Scala 3 (2021) is the version we use — specifically 3.3.5. It compiles to JVM bytecode (also JavaScript and native).

3. Values, Types, and Primitives

In pure FP, every program entity is a value. Values are immutable — once bound to a name, they never change. This eliminates entire classes of bugs caused by unexpected mutation.

// values can be associated to names — non-modifiable variables
val v = 1
// types are optional (typically inferred)
val w: Int = 1
// right-hand side can be any expression
val z = v + 5
println(z)

val a = 1
println("result is " + a)   // Java-style concatenation
println(s"result is $a")    // string interpolation
println(s"result is ${a+1}") // with expression evaluation

// primitive types mirror JVM
val i: Int = 10 + 5        // as in Java, interpreted as +(10,5)
val l: Long = 100_000_000_000L
val d: Double = 5.4 * 1.3
val f: Float = 3.0f
val b: Boolean = true && false
val s: String = "hello" concat " to all"  // String method as operator
val n: String = null   // null can be passed to "objects"

val u: Unit = ()       // the Unit type has a single value: ()
Style guide

Scala 3 style conventions: never put spaces between function name and parameter list; always put spaces around operators; never after '(' or before ')'; always after a comma, never before; always between different syntactic elements. Or simply, carefully mimic the slides. Note also that Scala has no true difference between primitive and non-primitive types, and that println is not really a function (I/O on the console is a non-FP hack we need just to log).

Key idea

val declares an immutable binding — think of it as naming a value, not declaring a variable. There is no null in pure FP; Scala retains it only for JVM interop.

4. Functions: Types, Literals, and Styles

A function type is written (T1, ..., Tn) => T0. A function literal (also called lambda or anonymous function) is written (x1, ..., xn) => expression.

Do not confuse the two sides of the =: before it is the val declaration (with its type), after it is the function itself. The slides list four styles for expressing a function value:

StyleExampleNotes
1. By a val holding itval f5: (Int,Int)=>Int = f4A function variable is used as a value
2. Typed function literalval f1: (Int,Int)=>Int = (x:Int,y:Int)=>x+y
val f2 = (x:Int,y:Int)=>x+y		Argument types explicit; the val type may be omitted (inferred)
3. Untyped function literalval f3: (Int,Int)=>Int = (x,y)=>x+yArgument types inferred from the val type
4. Expression with underscoresval f4: (Int,Int)=>Int = _ + _Each _ is a successive argument; val f6 = _ + _ does not type-check (no expected type)

A function body can contain multiple expressions; the last one is the return value:

val g: Int => Int =
  (x: Int) =>
    println("hello")  // side-effect
    x + 1             // return value

println(g(10))  // prints "hello", then 11

Special cases: a 0-argument list is written () => e (type () => T); a 1-argument one (x) => e or simply x => e (type T1 => T0). The type form => T without parameters denotes a by-name argument (section 17). Functions are called with the standard value-passing syntax f(5, 10).

5. Higher-Order Functions

A higher-order function (HOF) takes a function as an argument or returns one as a result. This is the FP equivalent of the Strategy pattern — and far more concise.

Key idea

Higher-order functions are the FP way of making code reusable and configurable. Instead of writing many similar functions, you write one function parameterised by the varying behaviour — expressed as a function argument.

When a function returns a function, we enter the territory of currying (see section 8). The function type arrow is right-associative: A => B => C means A => (B => C).

6. Pattern Matching and Case-Based Functions

Pattern matching is the FP alternative to the switch statement, but far more powerful: it can destructure values, bind variables, and apply guards.

The examiner will ask

What is the difference between a total function and a partial function in the context of pattern matching? What happens when you call a partial function outside its domain?

A case block { case p1 => e1; ... } defines a partial unary function. It's "partial" because it can fail on inputs that don't match any case, raising scala.MatchError (which we typically do not throw or catch explicitly). e match in front of a case block applies such a partial function to e; the syntax _ match followed by indented cases is the idiomatic Scala 3 style for a case-based function (an alternative header is (i: Int) => i match). Patterns for now are values, variables, and variables with an if guard; a variable on the left of => is always a fresh one (it never refers to an existing name). Cases are processed top to bottom and only the first that matches is evaluated.

Indentation styles

Scala 3 uses significant indentation (like Python): a very debated transition from Scala 2, but it works very well and the course stance is to definitely use it. Curly braces (the Scala 2 and Java style) are used only for one-liners where needed, e.g. 5 match { case n if n > 0 => "pos"; case 0 => "zero" }. In complicated cases add an end marker (end res2, end Indentation). A single argument can also be passed with a colon and indentation (println: on one line, 5 + 10 indented below), to be used only with imperative-like code.

7. Defined Functions, Nesting, and Tail Recursion

A def defines a method, essentially with a UML-like syntax. It is not very different from a val holding a function (val square2: Double => Double = d => d * d is mostly equivalent to def square(d: Double): Double = d * d), but it allows additional features — currying, generics, annotations, nesting — and is translated into a bytecode method belonging to a class or object. Input types are mandatory; the return type is optional but typically provided. Methods can be defined inside other methods, something Java does not allow.

Tail recursion

Methods can call themselves recursively, but this is optimised to be efficient (a loop, no stack growth) only if the recursion is tail: all the recursive calls, when executed, are the last expression evaluated before returning. n * factorial(n - 1) is not tail (the multiplication happens after the call returns); _fact(n - 1, n * acc) with an accumulator is. If you are not sure, use @annotation.tailrec: it only checks that the optimisation is possible, and makes the code not compile otherwise.

8. Currying and Partial Application

Currying is the technique by which multiple application to arguments is performed by successive evaluation of a function and its results: basically a shorthand for a function returning a function returning a function... In a def it is written with several parameter lists, def f(x1: T1)(x2: T2): T0. When a function is curried you can have partial application — fixing some arguments to produce a more specialised function. Currying is also used just to organise arguments into sub-groups (e.g. configuration/strategy arguments in a separate list), for ease of reading or for technical reasons we will see (type inference across lists).

Why it matters

Currying is not just a syntactic trick. It lets you configure a function once and reuse it many times. In the slides, configuration/strategy arguments are often grouped by currying to enable this pattern.

The function type arrow => is right-associative, so Double => Double => Double is Double => (Double => Double). A curried function literal x => y => x * y has exactly that type.

9. Product Types (Case Classes) and Pattern Matching

A product type represents a value that contains all of its components — a Cartesian product of sets. In Scala, case class defines a product type (also called a record).

Case classes give you: automatic toString (Point2D(10.0,20.0)), structural equals and hashCode, copy, and — most importantly for Scala — destructuring in pattern matching, using values, variables or underscores for the fields; matching works very well with records of records of records. The tuple notation (p1, p2) is actually equivalent to a case class Tuple2(p1, p2): built-in tuples Tuple2...Tuple22 are aliased to (_, _), (_, _, _), and so on.

Reflect

In FP, data (case class fields) and behaviour (functions operating on them) are kept separate. This contrasts with OOP, where data and methods are encapsulated together. Why might separation be a feature rather than a drawback? Think about what happens when you want to add a new operation.

10. Sum Types (Enums) and Algebraic Data Types

While a product type is a value that has all components, a sum type is a value that is exactly one of several alternatives — a disjoint union of sets. Together, products and sums form Algebraic Data Types (ADTs).

Key idea

An enum in Scala 3 defines a new type as the sum of a number of (possibly 0-argument) product types. This gives you the full power of ADTs: enumerate singletons (like Java enums), model hierarchies (a Person is a Student or Teacher), or build recursive structures like linked lists.

Pattern matching is the natural way to consume an ADT — the compiler can even warn you if your match is not exhaustive (a huge safety advantage). Cases of an enum need to be qualified by the enum name (Person.Student), unless imported. Scala enums cannot model every algebraic data type, but they are enough for now: more powerful constructs come later.

Summary of the core FP-Scala constructs

Types T ::= Int | Double | Boolean | String | (T1,...,Tn) => T0 | C | E (primitives, functions, case classes, enums). Declarations D ::= val x: T = v | def f(x1: T1,...,xn: Tn): T0 = e | case class C(x1: T1,...,xn: Tn) | enum E: ...case C(..). Expressions e ::= v | v1 op v2 | ef(e1,...,en) | (x1,...,xn) => e1 ... en | { case p1 => e1; ... } | e match { case ... } | C(e1,...,en). Very few constructs, sticking to a declarative, match-based style; if and blocks can be used too.

11. Subtyping and Function Variance

The subtype relation T <: R means "any value of type T can be used where R is expected." It is reflexive and transitive (a preorder).

For sum types, each case is a subtype of the enum — e.g. Student <: Person. Pattern matching recovers the specific type at the receiving site.

For functions, subtyping follows two rules simultaneously (contravariance on arguments, covariance on return):

// (T1,...,Tn) => T0 <: (R1,...,Rn) => R0 iff:
//   T0 <: R0  (covariant on return)
//   Ri <: Ti  (contravariant on each argument)

val f: Student => Person = (p: Person) => Student("m", 2015)

Intuitively: where a Student => Person is expected, callers will pass Students and expect a Person back. A function accepting any Person can certainly handle a Student (argument type may be more general: contravariance), and a function returning a Student certainly returns a Person (return type may be more specific: covariance). Unlike sum types, no matching is needed at the receiving site.

12. Modules, Imports, and Organization

In FP, modules group related definitions under a namespace: some may be public (to other modules), others private, and public definitions are accessed via module.defname. Modules and types are used together to structure data types and algorithms: the operators on a type are inserted into a module with the same name as the type (in Scala, an object with the same name as the enum). The ModuleName. prefix can be avoided with import ModuleName.*; imports also work in the REPL, where whole modules can be pasted.

The examiner will ask

In FP, why is it idiomatic to define types in an enum and algorithms in a companion object, rather than putting methods inside the type itself? What does this say about the relationship between data and behaviour?

13. Generics and Parametric Polymorphism

Generics (parametric polymorphism, as in Java generics) enhance reusability of code and expressiveness of types by abstracting some code (functions, types, classes) from some type. In Scala types, case classes, methods and enums can all be generic; the syntax uses square brackets [A, B, ...], and type variables can have bounds (e.g. A <: B, or B >: A as in orElse below).

Type inference for generics is very effective: you rarely need to specify type arguments explicitly, especially at the call site (val p = Pair(10, "20") has type Pair[Int, String]). Generic case classes Tup1[A], Tup2[A, B], ... are exactly how the built-in tuples are shaped: (10, true) == Tuple2(10, true).

14. Optional and Sequence Generic Types

The design recipe for powerful ADTs in FP: a product/sum type definition on top (enum or case class), whose structure is typically exposed so that algorithms can be implemented outside (some parts may be private); an object with the algorithmic aspects — operations and construction methods; generics for reusability; higher-order functions for factorisation; configuration/strategy arguments grouped by currying. Key examples: Optional, Sequences (lists), Trees, Streams. The slides start from a non-generic OptionalInt (Just(i: Int), Empty) and then generify it: note that with generics the empty case needs parentheses, Empty().

Optional[A] models a value that may or may not be present — a safer alternative to null.

enum Optional[A]:
  case Just(a: A)
  case Empty()

object Optional:
  def isEmpty[A](opt: Optional[A]): Boolean = opt match
    case Empty() => true
    case _       => false

  def orElse[A, B >: A](opt: Optional[A], orElse: B): B = opt match
    case Just(a) => a
    case _       => orElse

  def map[A, B](opt: Optional[A])(f: A => B): Optional[B] = opt match
    case Just(a) => Just(f(a))
    case _       => Empty()

Sequence[A] is a generic singly-linked list — the fundamental persistent data structure in FP.

enum Sequence[E]:
  case Cons(head: E, tail: Sequence[E])
  case Nil()

object Sequence:
  def sum(l: Sequence[Int]): Int = l match
    case Cons(h, t) => h + sum(t)
    case _          => 0

  def map[A, B](l: Sequence[A])(mapper: A => B): Sequence[B] = l match
    case Cons(h, t) => Cons(mapper(h), map(t)(mapper))
    case Nil()      => Nil()

  def filter[A](l: Sequence[A])(pred: A => Boolean): Sequence[A] = l match
    case Cons(h, t) if pred(h) => Cons(h, filter(t)(pred))
    case Cons(_, t)            => filter(t)(pred)
    case Nil()                 => Nil()

ADTs vs classes: information hiding

Classes introduce types giving constructors and operations while hiding internal state; algebraic data types give constructors and operations but expose the structure of data (the enum and its cases), so anybody can pattern-match on it. To encapsulate state in Scala: declare the cases as private, and add construction operations in the object. From outside, nobody will be able to pattern match (later we will see how this can be circumvented) — and also outside modules cannot implement new algorithms such as filter by matching, which is the price to pay.

object EncapsulatedSequences:
  enum Sequence[E]:
    private case Cons(head: E, tail: Sequence[E])
    private case Nil()

  object Sequence:   // cases are visible only here
    def cons[E](head: E, tail: Sequence[E]): Sequence[E] = Cons(head, tail)
    def nil[E](): Sequence[E] = Nil[E]()
    def sum(l: Sequence[Int]): Int = l match
      case Cons(h, t) => h + sum(t)
      case _          => 0

@main def tryEncapsulatedSequences =
  import EncapsulatedSequences.*, Sequence.*
  val l = cons(10, cons(20, cons(30, nil())))
  println(sum(l))   // 60

Testing ADTs with JUnit

JUnit can be used smoothly in Scala to retain TDD (SBT dependency "com.github.sbt" % "junit-interface" % "0.13.2" % Test); in FP a test function typically only has asserts, and equality of case classes makes assertions natural:

import org.junit.*
import org.junit.Assert.*

class SequenceTest:
  import u03.Sequences.*
  import Sequence.*

  val l: Sequence[Int] = Cons(10, Cons(20, Cons(30, Nil())))

  @Test def testSum() =
    assertEquals(0, sum(Nil()))
    assertEquals(60, sum(l))

  @Test def testMap() =
    assertEquals(Cons(11, Cons(21, Cons(31, Nil()))), map(l)(_ + 1))
    assertEquals(Cons("10", Cons("20", Cons("30", Nil()))), map(l)(_ + ""))

  @Test def testFilter() =
    assertEquals(Cons(20, Cons(30, Nil())), filter(l)(_ >= 20))
    assertEquals(Cons(10, Cons(30, Nil())), filter(l)(_ != 20))
Architecture

The combination of product types (case classes), sum types (enums), generics, and higher-order functions is remarkably expressive. It lets you define the structure of data once, and then compose operations over it using map, filter, fold — without ever resorting to mutable state or iteration.

15. Lambda Calculus Foundations

Which functional programs are independent of evaluation order, and how can we control evaluation order when needed? The formal approach: define a fully-expressive subset of FP, the λ-calculus (Alonzo Church, 1930), derive a result of confluence ("don't care nondeterminism"), and define evaluation orders on it. Historically, the λ-calculus grounded computability, FP, and later OOP: together with Turing machines it is the backbone of the whole of computer science. It is stunningly simple — one-argument functions and function application, just three syntactic forms; everything else (many-argument functions, primitive types, product and sum types, recursion) is a derived concept.

Syntax of lambda expressions

L ::= x | (λx.L) | L1 L2

A lambda is either a variable (any function formal argument), an abstraction (function) binding a variable, or an application (calling a function with an argument). Conventions: application is left-associative (L1 L2 L3 ≡ (L1 L2) L3), abstraction is right-associative (λx.λy.L ≡ λx.(λy.L)), and application has higher priority than abstraction (λx.L1 L2 ≡ λx.(L1 L2)). L{LP/x} denotes the substitution of every occurrence of x in L with LP.

Lambda calculusScala equivalent
xx (a variable / parameter name)
λx.Lx => L (function literal)
L1 L2L1(L2) (function application)

Beta-reduction is the single computational rule:

(λx.LB) LP  -->  LB{LP/x}

"Calling a function gives the body LB after substituting formal parameter x with actual LP"

The rule is applicable at any level of nesting: it is the semantics of "passing an argument". In Scala terms, an untyped subset L ::= V | V => L | L1(L2) is exactly the λ-calculus: val t: L = x => y => x is λx.λy.x, and t("a")("b") reduces as (λx.λy.x) a b → (λy.a) b → a.

The examiner will ask

Given the Church encoding T := λx.λy.x and F := λx.λy.y, derive the reduction steps for Not F where Not := λx.x F T. (Answer: Not F ≡ (λx.x F T) F → F F T ≡ (λx.λy.y) F T → (λy.y) T → T.)

Church Encoding of Booleans

Building a data type means defining some lambdas as constructors and others as functions manipulating them. Booleans: T := λx.λy.x (choose the first), F := λx.λy.y (choose the second); Not := λx.x F T, And := λx.λy.x y F, Or := λx.λy.x T y. Any sequence of reductions leads to the same result:

The same encoding can be written in Scala, with a self-referencing function type (one of Scala's many magic tricks):

object Lambda:
  trait Lambda extends (Lambda => Lambda)   // a Lambda is a function from Lambda to Lambda

  val True: Lambda  = x => y => x
  val False: Lambda = x => y => y
  val Not: Lambda   = b => b(False)(True)
  val And: Lambda   = b1 => b2 => b1(b2)(False)
  val Or: Lambda    = b1 => b2 => b1(True)(b2)

// test: Not(False) == True, And(True)(False) applied to two distinct lambdas selects the second

Expressiveness

Multi-argument lambdas are encoded by currying: (λx1.λx2....λxn.L) L1 L2 ... Ln →* L{L1/x1,...,Ln/xn}, i.e. Scala's ((x1,..,xn) => L)(L1,..,Ln). Naturals (Church numerals): 0 := λs.λz.z, 1 := λs.λz.s z, 2 := λs.λz.s (s z), ...; inc := λn.λs.λz.s (n s z), add := λn.λm.λs.λz.n s (m s z). Recursion via the Y combinator Y := λg.(λx.g (x x)) (λx.g (x x)), for which Y F →* F (Y F) →* F (F (Y F)) →* ...: it can implement factorial as f(x) = x == 0 ? 1 : x * f(x - 1).

The lambda calculus is Turing-complete: for any computable function f, with an encoding of its input and output domains (e.g. as naturals), there exists a lambda that mimics f. A proof strategy shows it generates all general recursive functions, by encoding constant functions, successor, projection/identity, functional composition, recursion, and minimisation (the smallest argument on which a function is 0). Hence successor, sum, product, factorial, the prime-number predicate, ... any Turing-implementable function.

Editor's note

The fact that every other programming construct (multi-argument functions, conditionals, loops, data structures) can be derived from just functions is why the lambda calculus is considered the mathematical foundation of computation — alongside Turing machines.

16. Confluence, Referential Transparency, Declarativity

A lambda can be 1-step reduced to different lambdas (e.g. add (inc 1) (inc 2), or T x (T x y)), can reduce indefinitely (e.g. Y x, or Y itself), or can either terminate or not depending on the choice (e.g. T x (Y): reduce the outer T first and you get x; keep reducing Y and you never stop). The critical property of the lambda calculus is confluence (the Church-Rosser theorem): given any L, if L →* L1 and L →* L2, then there exists L3 such that L1 →* L3 and L2 →* L3.

flowchart TD
  L["L (original expression)"] --> L1["L1"]
  L --> L2["L2"]
  L1 --> L3["L3 (common result)"]
  L2 --> L3
Consequences

No more than one result of a computation can exist: if L →* L1 and L →* L2 with both irreducible, then L1 ≈ L2 (identical modulo non-clashing renaming of variables, e.g. λx.x ≈ λy.y). So if L always terminates the reduction choice is non-influential (don't-care nondeterminism), while if L may not terminate the reduction choice is key to finding the result. This is the basis of referential transparency — the result of evaluating an expression is independent of its context, so an expression can be replaced by its value — which allows equational reasoning on programs and facilitates understandability and refactoring.

Declarativity in FP means you express what result you want, not the step-by-step how: a sort of holy grail of computer science. A composition like sum(map(filter(l)(_ >= 20))(_ + 1)) says nothing about which function application is performed first: it focuses on building a sequence out of other sequences and aggregating it. If f(x, y) = x + x, then f(g(), h()) could be computed by evaluating g() and h() first, or by reducing to g() + g(), or by evaluating g() once and computing a + a — and we expect the order to be irrelevant. A multi-core PC or a distributed system in the cloud can evaluate the same expression very differently "inside" while the result is the same: modern platforms such as Apache Spark and Map-Reduce are essentially FP over the cloud-edge continuum, where the low layers enact optimisation and adaptiveness that look like "magic" but are just engineering. FP and LP are the quintessential declarative paradigms.

17. Evaluation Order: Call-by-Value, Call-by-Name, Call-by-Need

In FP, computation may be independent of evaluation order: this is the case with terminating computations and without side-effects, which is typical. Still, different evaluation orders can impact performance, or even the result if there are side-effects. Three strategies:

StrategyWhen argument is evaluatedScala syntax
Strict, call-by-value (applicative order: Java, Scala, ...)Just before passing it — once, before the function bodydef f(a: A) — the default, you typically do not change it
Non-strict, call-by-name (normal order)When/if used in the body — each time it is useddef f(a: => A), a shorthand for passing a producer a: () => A and calling a() in the body. Choose it when execution has to be delayed, or avoided if not needed

18. Streams: Lazy Infinite Data Structures

A Stream is essentially a lazy list (the name of streams in Scala 3 is LazyList): lazy management of data, up to modelling infinite flows, where streams connect by iterative decoration (iterate, map, filter, take, toList). The main trick is to put lazy vals into lambdas at cons time; the rest of the implementation is the same as for lists.

The key trick: the Cons case holds thunks (0-argument functions) instead of strict values, and cons uses by-name parameters with lazy val to cache results.

@main def tryStreams =
  import Streams.*
  val str1 = Stream.iterate(0)(_ + 1)                       // {0,1,2,3,..}
  val str2 = Stream.map(str1)(_ + 1)                        // {1,2,3,4,..}
  val str3 = Stream.filter(str2)(x => (x < 3 || x > 20))    // {1,2,21,22,..}
  val str4 = Stream.take(str3)(10)                          // {1,2,21,22,..,28}
  println(Stream.toList(str4))                              // [1,2,21,22,..,28]

  lazy val corec: Stream[Int] = Stream.cons(1, corec)       // {1,1,1,..}
  println(Stream.toList(Stream.take(corec)(10)))            // [1,1,..,1]

Note that a strict filter on an infinite stream would never return: here each stage only computes what the next one forces, so take(str3)(10) pulls exactly ten elements through the pipeline. Every intermediate structure is a sequence: "Stream" and "List" are not two unrelated ways of dealing with sequences, as they are in Java, but the same algorithms with lazy vs strict constructors.

Why this matters

Streams decouple description from evaluation. You describe a potentially infinite sequence (Stream.iterate(0)(_ + 1)) and then decide how much of it to realise. This is the engine behind big data frameworks like Apache Spark — which was itself written in Scala.

19. Extension Methods and Method Chaining

An extension method is an alternative way of defining a method, extracting one of its arguments: other than the standard syntax for calling the method, a new one treating that argument as if it were the receiver of the invocation is enabled — but this is just syntax. Implications: OO-like syntax of method calls without any OOP; method calls can be chained, e.g. to define pipelines; a module can now define standard methods (e.g. factories) and extension methods (e.g. operations). Construct: extension (x: T) def m(arg1: T1, ..., argn: Tn): To = ...

With extension methods, you can write fluent pipelines:

object Sequences:
  enum Sequence[E]:
    case Cons(head: E, tail: Sequence[E])
    case Nil()

  object Sequence:
    extension (l: Sequence[Int])
      def sum: Int = l match
        case Cons(h, t) => h + t.sum
        case _          => 0

    extension [A](l: Sequence[A])
      def map[B](mapper: A => B): Sequence[B] = l match
        case Cons(h, t) => Cons(mapper(h), t.map(mapper))
        case Nil()      => Nil()
      def filter(pred: A => Boolean): Sequence[A] = l match
        case Cons(h, t) if pred(h) => Cons(h, t.filter(pred))
        case Cons(_, t)            => t.filter(pred)
        case Nil()                 => Nil()

    def of[A](n: Int, a: A): Sequence[A] =   // a plain factory method
      if n == 0 then Nil[A]() else Cons(a, of(n - 1, a))

@main def trySequences() =
  import Sequences.*, Sequence.*
  val seq = Cons(10, Cons(20, Cons(30, Nil())))
  println(seq.filter(_ >= 20).map(_ + 1).sum)     // 21+31 = 52
  println(sum(map(filter(seq)(_ >= 20))(_ + 1)))  // equally possible
  println(of(10, -1).sum)                          // -10
FP vs OOP

Extension methods are not about adding behaviour to objects in the OOP sense. They are a syntactic convenience that allows module-defined operations to be chained — keeping the FP discipline (data and behaviour separate) while giving the ergonomics of method-call syntax.

Check Your Understanding

1. Explain what referential transparency means and why it follows from the Church-Rosser theorem.

Referential transparency means an expression can be replaced by its value without changing the program's meaning. The Church-Rosser theorem states that if a lambda term reduces to two different forms, there is always a third form reachable from both. This implies a unique normal form (if one exists), so the result of a terminating program is independent of evaluation order — the fundamental enabler of equational reasoning.

2. What is the difference between a `val` holding a function and a `def` method?

A val f: A => B = ... evaluates its right-hand side once and stores the function object. A def f(a: A): B = ... creates a JVM method which can support generics (def f[A](...)), currying in separate parameter lists, annotations like @tailrec, and nesting inside other defs.

3. Given `curriedMult(x: Double)(y: Double): Double = x * y`, what is the result of `curriedMult(2)`?

It returns a function of type Double => Double that doubles its argument — i.e., y => 2 * y. Partial application at work.

4. Why is pattern matching on an enum considered exhaustive-checked by the compiler?

Because Scala's enum cases are known at compile time. The compiler can verify that all cases are covered in a match expression. If a case is missing, it issues a warning (or an error with the right flag). This eliminates a class of runtime bugs.

5. Derive the reduction steps for And (Not F) T using the Church encoding.

Recall: T := λx.λy.x, F := λx.λy.y, Not := λx.x F T, And := λx.λy.x y F.

And (Not F) T
≡ And ((λx.x F T) F) T
→ And (F F T) T
≡ And ((λx.λy.y) F T) T
→ And ((λy.y) T) T → And T T
≡ (λx.λy.x y F) T T
→ (λy.T y F) T → T T F
≡ (λx.λy.x) T F
→ (λy.T) F → T (irreducible)

Result: T — as expected, since (not false) and true = true. By confluence, any other order of reductions gives the same result.

6. What would happen if you called `sPair(10, loop(20))` where `loop[A](a:A):A = loop(a)`?

With call-by-value (default), loop(20) is evaluated before being passed, causing infinite recursion (stack overflow). With call-by-name (=> A), loop(20) is never evaluated because dummy is unused in the body — the result would be (10, 10).

7. Write the type of `compose` that does `f o g` and implement it.

def compose(f: Int => Int, g: Int => Int): Int => Int = x => f(g(x)). Usage: compose(_ - 1, _ * 2)(5) gives 9.

8. How does a `Stream` differ from a `Sequence` at the implementation level?

A Stream stores its head and tail as thunks (by-name / () => A), while a Sequence stores them as strict values. This means Stream can represent infinite sequences; its elements are computed on demand and optionally cached via lazy val.

9. Explain the subtyping rule for function types with an example.

(T1,...,Tn) => T0 <: (R1,...,Rn) => R0 iff Ri <: Ti for each argument (contravariance) and T0 <: R0 (covariance on the return type). Example: since Student <: Person, Person => Student <: Student => Person. Where a Student => Person is expected, the caller will only ever pass Students and only ever use the result as a Person; a function that accepts any Person and returns a Student satisfies both obligations, so it is safe to substitute — subtyping (<:) means exactly "usable wherever the other is expected". Concretely, val f: Student => Person = (p: Person) => Student("m", 2015) compiles.

10. What is the role of the companion object alongside an enum in Scala FP code?

The companion object is the module holding the operations (algorithms) that work on the type, accessed as Sequence.sum(l) or imported with import Sequence.*. This keeps data definitions (the enum with its cases) separate from behaviour (the functions in the object) — a hallmark of the FP organisational style. The object can also contain construction methods (cons, nil, of), which become mandatory when the cases are made private to hide the structure.

11. (Lab) Implement foldLeft on Sequence, and use it to compute foldLeft(Cons(3, Cons(7, Cons(1, Cons(5, Nil())))))(0)(_ - _).

def foldLeft[A, B](l: Sequence[A])(acc: B)(f: (B, A) => B): B = l match
  case Cons(h, t) => foldLeft(t)(f(acc, h))(f)
  case _ => acc

The accumulator type B may differ from the element type A; the recursion is tail-recursive. The example computes (((0 - 3) - 7) - 1) - 5 = -16. Currying puts the accumulator and the operator in separate lists, so that _ - _ can be inferred as (Int, Int) => Int from the earlier lists.

12. (Lab) Define an infinite Stream of Fibonacci numbers using the course's Stream type, and explain why it terminates.

def fibs(a: Int, b: Int): Stream[Int] = Stream.cons(a, fibs(b, a + b)), then val fibonacci = fibs(0, 1); Stream.toList(Stream.take(fibonacci)(5)) gives Cons(0, Cons(1, Cons(1, Cons(2, Cons(3, Nil()))))). It terminates because cons takes its arguments by name and stores them in lazy vals wrapped in thunks: the recursive call fibs(b, a + b) is not evaluated until take forces the tail, and take(...)(0) returns Empty() without forcing anything further. The same idea gives takeWhile(s)(pred), fill(n)(k), and the corecursive lazy val corec = cons(1, corec).

13. (Lab) Write a function neg that takes a predicate on strings and returns its negation, both as a val and as a def. What is the type of neg(empty)?

Type first: (String => Boolean) => (String => Boolean). As a val: val neg: (String => Boolean) => (String => Boolean) = p => s => !p(s). As a method: def neg(p: String => Boolean): String => Boolean = s => !p(s). With val empty: String => Boolean = _ == "", neg(empty) has type String => Boolean, so neg(empty)("foo") is true and neg(empty)("") is false. This is a higher-order function: a function both taking and returning a function. (A generic version: def neg[A](p: A => Boolean): A => Boolean = a => !p(a).)
