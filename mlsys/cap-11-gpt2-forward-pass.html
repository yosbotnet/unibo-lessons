The chapter in one paragraph

This is the milestone of Part II: GPT-2 small runs on your card, in CUDA you can read line by line, and its logits match PyTorch’s. You already have every kernel it needs (lab 5’s elementwise ops and layernorm, lab 7’s GEMM with chapter 9’s epilogues, lab 9’s attention). What is left is everything around the kernels, and it is what separates a kernel collection from an inference engine: getting the weights onto the GPU in the layout the kernels want, fast; planning memory once, so that nothing is allocated while the model runs; and proving the output right, with a test that needs no files and a verification against the real model. 1. What “matches PyTorch” means

The engine’s claim is that for a given prompt it produces the same logits (the 50,257 scores for the next token at every position) as Hugging Face’s GPT-2 in PyTorch. “The same” needs a definition, because bitwise equality is impossible and you should know why before you chase it. Both programs compute in FP32. Both compute the same mathematical function. But a dot product of 768 terms has a result that depends on the order the terms are added (chapter 5’s non-associativity), cuBLAS and PyTorch’s kernels tile the sums differently, tanhf and expf have several implementations with different last bits, and the differences compound across 12 layers. The result: two correct FP32 forward passes disagree in the fourth or fifth significant digit. GPT-2’s logits are of order 100 in magnitude, so a disagreement of 10−3 to 10−2 per logit is what correct code looks like, and a disagreement of 1 is a bug.

So the engine has two tiers of checking, each with a definition of “matches”:

ModeReferencePasses whenNeeds
testa double-precision CPU forward (cpu_ref.h) over random small models: L = 1–2, C = 64–128, random weightsevery logit within 2×10−4 absolute plus 2×10−4 relative; both matmul backends; the full forward, prefill + decode through the cache, and greedy generation with and without the cache giving identical tokensnothing: no files, no Python. This is what cudasim runs
verifylogits from PyTorch (or a numpy forward) for the real weights and a fixed prompt, written by reference.pymax |logit error| below 10−2 and the top-1 token agreeing at every position, for the full forward and for prefill + decodegpt2_124M.bin and ref_logits.bin

The double-precision reference is the stricter of the two: its own rounding is 108 times finer than FP32, so every deviation it reports is the GPU’s, and a tolerance of 2×10−4 on random models with activations of order one is tight enough to catch a wrong epilogue, a masked entry off by one, or a transposed weight, while leaving room for FP32 rounding across a few layers. The real-weight check is looser because its reference is itself FP32, but it tests the one thing the random models cannot: that the file export, the tensor order and the tied embedding are right for the actual checkpoint.

Your move: the test tolerance is 2×10−4. Why not 10−6, and why would 10−2 be dangerous?

FP32 has 24 bits of mantissa, a relative spacing of 1.2×10−7 (chapter 6), and a sum of 768 terms in a different order can move the result by tens of ulp; after a residual stream accumulates twelve layers of that, 10−6 would fail correct code on rounding alone. At 10−2 on activations of order one, a bug that is off by a percent slips through: a GELU with the wrong constant, a layernorm ε of 10−3 instead of 10−5, a softmax missing a single masked entry out of a hundred. The tolerance is set just above what rounding produces, so that anything structural shows. The lab prints the maximum error of every check; after a run, you know your rounding floor and can tighten it.

2. The weights: from safetensors to one flat file

Hugging Face ships GPT-2 small as model.safetensors: 548 MB, a format chosen for being trivial to read. The file is an 8-byte little-endian length N, then N bytes of JSON mapping each tensor name to its dtype, shape and byte range (data_offsets, relative to the end of the header), then the raw bytes, row-major. No parsing of floats is needed: a tensor is a byte range, and copying it is f.seek(); f.read(). The engine does not read safetensors directly, because C++ has no JSON and because the kernels want one thing: every tensor in one buffer, in the order the forward pass reads them. So export.py (Python standard library only) rewrites it once:

gpt2_124M.bin = header (256 int32: magic 20261022, version 1, L, C, H, V, T_max, float count lo, hi; rest zero)
              + wte [50257, 768]                          154.4 MB   embedding, and the LM head (tied)
              + wpe [1024, 768]                             3.1 MB   position embedding
              + for each of 12 layers (28.35 MB each):
                  ln1_g, ln1_b [768]
                  qkv_w [768, 2304], qkv_b [2304]          HF attn.c_attn: columns q | k | v
                  prj_w [768, 768],  prj_b [768]           HF attn.c_proj
                  ln2_g, ln2_b [768]
                  fc_w  [768, 3072], fc_b [3072]           HF mlp.c_fc
                  fc2_w [3072, 768], fc2_b [768]           HF mlp.c_proj
              + lnf_g, lnf_b [768]
total 1 KB + 497.8 MB = 124,439,808 floats

Three facts decide the layout. Conv1D is [in, out]. HF’s GPT-2 stores every linear weight as the original checkpoint did, [K, N], so y = xW + b needs no transpose and the bytes go into the file untouched (chapter 6 warned that this is the cheapest bug to avoid; it is avoided by copying, not by converting). Layer-major order. One layer’s twelve tensors are contiguous, which is what a decode step streams: layer 0’s 28 MB, then layer 1’s, a sequential read of the whole file per token. Tied weights. The checkpoint has no LM head matrix; wte serves twice, so the file has it once and the engine keeps one pointer to it for both uses.

export.py also writes gpt2_tokens.bin: for every token id, the bytes it stands for, so that generate can print text. The real tokenizer (byte-level BPE with its merge rules) is only needed to turn text into ids, and for that prompt.py uses tiktoken if installed; the engine itself never tokenizes. It reads ids from a file, which keeps the C++ side free of string handling and the correctness story about numbers only.

Your move: export.py copies byte ranges without looking at the values. What goes wrong if the checkpoint were stored in BF16 (as most modern models are), and what would the export have to do?

The byte count would be half what the header claims and every float the engine reads would be two BF16 values glued together: garbage from the first kernel. The export would have to widen each BF16 to FP32, which is cheap (BF16 is FP32’s top 16 bits, chapter 6: shift left by 16), but it is a conversion of 124M values in Python, so it should be done with array or struct on whole tensors, not value by value. The dtype field in the safetensors header is there for exactly this check, and export.py refuses anything but F32 rather than guess.

3. Getting 500 MB onto the GPU

Half a gigabyte has to travel from the disk, through the CPU’s memory, over PCIe, into the card’s DRAM. Every program so far did this with one cudaMemcpy (chapter 2) and never timed it; an engine that loads a model in several seconds when it could take one is a bad engine, and the reasons it can be slow are worth knowing. Three concepts, defined here because the engine is the first program in the course that needs them:

  • Pageable and pinned memory. Ordinary host memory from malloc is pageable: the operating system may move a page or swap it out at any moment, so its physical address is not stable. The copy engine (interlude 5b: a DMA unit that moves data over PCIe without an SM) needs stable physical addresses, so cudaMemcpy from pageable memory secretly copies the data first into a driver-owned pinned buffer (page-locked, never moved), chunk by chunk, and then DMAs from there: two copies, and the CPU does the first. cudaMallocHost gives you pinned memory directly, and a copy from it is one DMA at PCIe speed.
  • Streams. A stream is a queue of GPU work (kernels, copies) executed in order. Work in different streams may overlap, and a copy in one stream can run while the CPU is busy with something else. Chapter 5 used a stream to capture a graph; here one is used so that cudaMemcpyAsync returns immediately.
  • Events. A marker recorded into a stream; cudaEventSynchronize waits until the stream has passed it. The labs’ timer (time_gpu in labs/common/bench.h) uses two of them; here one event per buffer says “the copy out of this buffer is done, you may refill it”.

The engine loads the weights three ways and times each (bench), so that the numbers below are yours:

// gpt2.cu, load_weights: the overlap mode. Two pinned 32 MB buffers; while chunk i crosses PCIe,
// the CPU reads chunk i + 1 from the file into the other buffer.
const size_t CH = 32u << 20;
char* buf[2]; cudaEvent_t done[2]; cudaStream_t s;
cudaStreamCreate(&s);
for (int i = 0; i < 2; ++i) { cudaMallocHost(&buf[i], CH); cudaEventCreate(&done[i]); }
for (size_t off = 0, i = 0; off < bytes; off += CH, ++i) {
    const int k = i % 2;
    const size_t n = std::min(CH, bytes - off);
    if (i >= 2) cudaEventSynchronize(done[k]);              // the previous copy has left buf[k]
    fread(buf[k], 1, n, f);                                  // CPU: disk (or page cache) -> pinned buffer
    cudaMemcpyAsync(dev + off, buf[k], n, cudaMemcpyHostToDevice, s);   // DMA: pinned -> GPU, no waiting
    cudaEventRecord(done[k], s);
}
cudaStreamSynchronize(s);

It is chapter 8’s double buffer, one level up: two buffers, a producer (the file read) and a consumer (the DMA), an event instead of a barrier. The numbers to expect, as ranges: a pageable cudaMemcpy of 500 MB at 5–12 GB/s (the hidden staging copy is CPU work); pinned at 20–50 GB/s on a PCIe 5.0 ×16 slot (64 GB/s theoretical, each direction); and the overlap mode at the speed of the slower side, which once the file is in the OS page cache is the fread itself, a memory copy of a few GB/s per core. The first run after a reboot reads from the NVMe at 3–7 GB/s whatever you do. The lesson is not the 50 ms saved on GPT-2; it is that a 70B model is 140 GB in FP16, and engines load it with exactly this loop, with direct I/O and several threads on the producer side.

Your move: in the overlap loop, the fread and the cudaMemcpyAsync of the same chunk are not overlapped, only adjacent chunks are. What is the total time for n chunks in terms of the read time r and the copy time c per chunk, and when does buffer count matter?

About r + max(r, c) · (n − 1) + c, if the slower side never waits: the first read and the last copy are exposed, everything else hides behind the slower of the two. With two buffers that holds as long as each side’s time per chunk is steady; if reads are bursty (page-cache hits and disk misses mixed), the copy engine idles during a slow read and a third buffer would absorb it, which is chapter 8’s “number of stages” argument again. The chunk size trades the exposed ends (smaller is better) against per-call overhead (a few microseconds per cudaMemcpyAsync; 32 MB is far above it).

4. Memory planning: one arena, no allocation in the loop

A forward pass needs buffers for its activations: the stream x, the normalized copy, the QKV output, the attention output, the 3,072-wide MLP activation, the logits, attention’s scratch, and with a cache, the cache. A framework allocates them as it goes and frees them after; an engine plans them once. cudaMalloc is slow (tens to hundreds of microseconds, sometimes a device synchronization), fragments the heap when sizes vary, and makes pointers change between runs, which breaks the one optimization that removes the launch floor: a captured CUDA graph replays fixed pointers (chapter 5). So the engine takes the largest batch Bmax and context Tmax it will serve, computes every buffer’s size for them, does one cudaMalloc, and carves it:

// gpt2.cu, engine_init(E, weights, cfg, opts, Bmax, Tmax, logit_rows, Tpre = Tmax): one arena, carved
// into buffers. Tmax sizes the cache; Tpre, the most new tokens per pass, sizes the activations
// (a decode-only run passes Tpre = 1).
const size_t rows = (size_t)Bmax * Tpre;
size_t act   = rows * C * 3 + rows * 3 * C + rows * 4 * C + (size_t)Bmax * C;   // x, ln, att | qkv | fc | last
size_t scr   = max(Tpre > 1 ? prefill->scratch(Bmax, Tpre, H, D) : 0, decode->scratch(Bmax, Tmax, H, D)) / 4 + 1;
size_t cache = use_cache ? 2 * (size_t)L * Bmax * Tmax * C : 0;                 // k and v, per layer
size_t lg    = (size_t)logit_rows * V;
cudaMalloc(&arena, /* act + scr + cache + lg, each buffer padded */ ...);
float* q = arena;
auto pad  = [](size_t n) { return (n + 63) / 64 * 64; };    // 256-byte boundaries, as cudaMalloc gives:
auto take = [&](size_t n) { float* r = q; q += pad(n); return r; };   // float4 loads need aligned rows
x = take(rows * C); ln = take(rows * C); att = take(rows * C);
qkv = take(rows * 3 * C); fc = take(rows * 4 * C); last = take(Bmax * C);
scratch = take(scr); logits = take(lg);
for (int l = 0; l < L; ++l) { k_cache[l] = take(Bmax * Tmax * C); v_cache[l] = take(Bmax * Tmax * C); }

Buffers are reused across layers (one qkv, one fc, written twelve times per pass) because a layer’s intermediates are dead once the residual stream has absorbed them. Only the stream x and the cache carry state between layers and steps. At B = 1, Tmax = 1,024 the plan is:

Move the sliders and watch which line wins: at B = 1 the weights dominate; raise T and the scratch’s T2 takes over; raise B at full context and the cache does. The three regimes are chapters 10, 14 and 13 respectively, as a memory bill.

Your move: the engine serves B = 8 sequences at Tmax = 1,024 with the naive attention. Which of scratch, cache and weights is the largest, and does it fit in 12 GB?

Scratch: 8 × 12 × 1,0242 × 4 B = 403 MB. Cache: 2 × 12 × 8 × 1,024 × 768 × 4 B = 604 MB. Weights: 498 MB. The cache wins, and all of it together, with the activations (8× the table’s 31 MB) and the logits, is under 2 GB: it fits ten times over. The limit is not memory at this model size; it is the T2 scratch at long contexts (chapter 10’s Your move) and, for the models that matter in Part IV, the cache: Llama-3-8B at FP16 has 131 KB of cache per token, and chapter 13 shows where that runs out.

5. The forward pass as code

Chapter 10’s kernel list, as a loop. This is the engine’s forward() with the profiling hooks and the checks removed; M = B·Tnew rows, pos0 the position of the first new token (0 without a cache):

// gpt2.cu, forward(): B sequences of T_new tokens starting at pos0. use_cache = false in this chapter.
embed<<<M, 256>>>(tok_d, p.wte, p.wpe, x, T_new, pos0, C);                      // x = wte[tok] + wpe[pos]
for (int l = 0; l < L; ++l) {
    const LayerParams& w = p.layer[l];
    layernorm<<<M, LN_THREADS>>>(x, w.ln1_g, w.ln1_b, ln, C);
    linear(be, EPI_BIAS,          ln,  w.qkv_w, w.qkv_b, qkv, M, 3 * C, C);     // qkv = ln W + b
    if (use_cache) kv_append(qkv, k_cache[l], v_cache[l], B, T_new, pos0, H, D, Tmax, 0);
    if (decode) dec->run(qkv, k_cache[l], v_cache[l], att, B, H, D, pos0 + 1, Tmax, scratch, 0);
    else        pre->run(qkv, att, B, T_new, H, D, scratch, 0);                  // lab 9's attention
    linear(be, EPI_BIAS_RESIDUAL, att, w.prj_w, w.prj_b, x,   M, C, C);         // x += att W + b
    layernorm<<<M, LN_THREADS>>>(x, w.ln2_g, w.ln2_b, ln, C);
    linear(be, EPI_BIAS_GELU,     ln,  w.fc_w,  w.fc_b,  fc,  M, 4 * C, C);     // fc = gelu(ln W + b)
    linear(be, EPI_BIAS_RESIDUAL, fc,  w.fc2_w, w.fc2_b, x,   M, C, 4 * C);     // x += fc W + b
}
layernorm<<<M, LN_THREADS>>>(x, p.lnf_g, p.lnf_b, ln, C);
if (all_logits) lm_head(be, ln, p.wte, wteT, logits, M, V, C);                  // verify: every position
else { gather_last_rows<<<B, 256>>>(ln, last, T_new, C); lm_head(be, last, p.wte, wteT, logits, B, V, C); }

Three design choices in it carry the chapter’s weight:

  • One linear() entry point with an epilogue enum (EPI_BIAS, EPI_BIAS_GELU, EPI_BIAS_RESIDUAL) and two backends selected by --linear cublas|own. The own backend is lab 7’s v7 with chapter 9’s epilogue fused into its stores, plus a GEMV-shaped kernel for M ≤ 8 (decode: a 128×128 tile with one live row and six blocks for N = 768 would starve 48 SMs, like chapter 6’s 3-block layer). The cuBLAS backend runs cublasSgemm and then one fused elementwise kernel for the passengers; for the residual it uses β = 1, so that x += … costs nothing extra. The two backends are the engine’s built-in experiment: same model, your kernels against NVIDIA’s, one flag.
  • Attention through a table. pre and dec are entries of PREFILL_IMPLS and DECODE_IMPLS in attention.cuh, chosen by --attn-prefill naive and --attn-decode simple, each with the contract’s signature and a scratch-size function the memory plan calls. Two more lines are already registered, flash (chapter 14, its kernel from lab 13) and split (chapter 15, from lab 14); nothing else in the engine changes.
  • The LM head is the one NT GEMM. logits = ln @ wte^T with wte stored [50,257, 768]. cuBLAS takes the transpose as a flag; the own backend, whose kernel only reads a row-major [K, N] B operand, multiplies by a transposed copy wteT made once at load time with lab 2’s tiled transpose: 154 MB of memory for not writing a second kernel layout, a trade the comment in the code states so that you can disagree with it.

Note what is not in the loop: no allocation, no host synchronization, no copy except the token ids at the start (an ordinary cudaMemcpy of a few bytes, which does synchronize: a known cost, counted in section 8). The whole pass is a sequence of launches into the default stream, which is exactly the shape a CUDA graph can capture later.

Your move: EPI_BIAS_RESIDUAL updates x in place: the GEMM reads att and writes x += result. The MLP’s second GEMM does the same with fc. What would go wrong if an epilogue read and wrote the same buffer as its A operand, and why is that not a problem for the residual?

A GEMM reads tiles of A at every k step and writes C once at the end; if C aliased A, a block that finished early would overwrite rows of A that other blocks (other k ranges of other tiles) still need to read: a write-after-read race across blocks, undetectable by a test on small shapes where all blocks fit in one wave. The residual is safe because x is neither GEMM’s A operand: the attention projection reads att, the MLP projection reads fc, and x is only touched in the epilogue, each element by exactly one thread, read and then written. linear()’s comment says “x must not alias out” for this reason.

6. Checking it, and debugging a mismatch

./gpt2 test runs section 1’s first tier: a handful of random configurations (small L, C, H, V, several B and T, including odd T), each through both backends, each checked three ways: the full forward against the CPU reference at every position; a prefill of half the tokens into the cache followed by one-token decode steps, against the same reference (so the cache path is proven now even though this chapter does not use it for speed); and, for the single-sequence configuration, greedy generation with and without the cache, which must produce identical token ids, because the two paths compute the same function. Then the sampling kernels against a CPU definition on rows of 50,257 random logits. It needs no files and runs on cudasim, which is how it was checked before it ever met a GPU.

./gpt2 verify runs the second tier on the real weights: reference.py writes ref_logits.bin (a header, the prompt’s token ids, and T × 50,257 FP32 logits, from transformers if it is installed and from a plain numpy forward if not). Neither path reads the engine’s file: the numpy forward reads model.safetensors itself, so a mistake in export.py cannot hide by being made on both sides. The engine prints the maximum logit error and the top-1 agreement for the full forward and for prefill + decode.

When it does not match

It will not, the first time; a forward pass has a dozen places to be wrong by a little. The method is bisection by layer: both the reference and the engine compute the residual stream x after every layer, so dump both (python3 reference.py --dump L writes x after layer L to dump_L_ref.bin; ./gpt2 verify --dump L writes its own to dump_L.bin and prints the largest difference) and find the first layer where they diverge. If layer 0’s output is already wrong, the bug is in the embedding, the first layernorm, the QKV GEMM, attention or the two epilogues, and you dump those intermediates next. The classic faults and their fingerprints:

Your move: your engine passes test on every random configuration but verify fails with top-1 agreement at no position and errors of order 10. Which parts of the engine does test exonerate, and where do you look first?

test builds its weights in memory in the engine’s own order, so it proves the kernels, the loop, the epilogues, the attention and the cache path. It never touches export.py, the file header, or the assumption that HF’s tensors are [in, out] and in the expected order. Everything wrong is therefore between the checkpoint and the flat file, or in reference.py’s own prompt: check that the ids in ref_logits.bin are the ids the engine read, then dump the embedding row of token 0 from both sides. Random-model tests are blind to file-format bugs by construction, which is why the lab’s end-to-end test writes a tiny fake safetensors file and runs it through export, reference and verify.

7. Generation: greedy, temperature, top-k on the GPU

A forward pass ends with one row of 50,257 logits per sequence. Greedy decoding takes the largest; sampling draws a token with probability softmax(logits / temperature), where a temperature below 1 sharpens the distribution and above 1 flattens it; top-k sampling first keeps only the k largest logits (40 is the usual default), so that the long tail of implausible tokens can never be drawn. All three are small jobs, 200 KB of logits per sequence, and a first engine would copy the row to the CPU and do them there. Two reasons not to: at B = 64 that is 13 MB per step over PCIe, and worse, it is a round trip per token that puts the CPU on the critical path and prevents the whole step from ever becoming one graph. So the engine picks the token on the GPU, one block of 1,024 threads per row, and the host only fetches the chosen ids. This is where three tools enter the course, each defined by the job it does here.

Greedy: a max with its index

Chapter 5’s reduction, carrying a pair (value, index) and breaking ties toward the smaller index so that the result is deterministic: each thread scans its stride of the row, warps merge by shuffles, warp leaders merge through shared memory. argmax_rows in sample.cuh, forty lines.

Top-k without sorting: radix select

Sorting 50,257 values to keep 40 is wasteful. What top-k really needs is a threshold: the value of the k-th largest logit, after which “keep the top k” is the elementwise test x ≥ threshold. Radix select finds that value in a fixed number of passes by looking at the numbers one byte at a time, from the most significant byte down:

  1. Map each float to a 32-bit unsigned key that sorts the same way as the float (flip the sign bit for positives, flip all bits for negatives; float_key in the code). Now “larger logit” is “larger unsigned integer” and bytes can be compared independently.
  2. Build a histogram of the top byte over all candidates: 256 bins, how many keys have each value there.
  3. Walk the bins from 255 downwards, accumulating counts, until the running total reaches k. That bin is the top byte of the k-th largest key, and the number still to find inside it is k minus the count of the bins above.
  4. Repeat for the next byte, counting only the keys whose top byte matches. Four passes fix all 32 bits, and the key is the threshold.

A toy with 4-bit keys and 2-bit digits, k = 3, keys {13, 7, 12, 2, 9, 14, 5, 11}:

PassCandidatesHistogram of the digit (bin: count)Walk from the topFound
1 (top 2 bits)all 811: 3   10: 2   01: 2   00: 1bin 11 alone holds 3 ≥ k = 3prefix 11, rank 3 inside it
2 (low 2 bits)keys with prefix 11: {13, 12, 14}11: 0   10: 1   01: 1   00: 110 → 1, 01 → 2, 00 → 3 ≥ 3threshold 1100 = 12

Keys ≥ 12 are {14, 13, 12}: the top three, no sort. The real kernel does this over 50,257 keys with 8-bit digits, and each pass is two things you have met in simpler forms:

  • The histogram is built with atomics: an atomic add is a read-modify-write that the hardware performs as one indivisible operation, so that two threads incrementing the same bin at the same moment both count (chapter 5’s atomicAdd into the final sum was one per block; here it is one per element). Atomics on global memory are executed in the L2 (interlude 5b) and serialize per address: 50,257 increments spread over 256 addresses, from 1,024 threads, would queue there. So the histogram is privatized: each block builds its own in shared memory, where atomics are per-SM and far cheaper, and only the finished histogram is read. Chapter 5’s per-block partial sums were privatization too; this is the general form, and PMPP’s name for it.
  • The walk from the top is a scan (a prefix sum): thread t holds bin 255 − t, and after an inclusive scan it knows how many keys lie in its bin and all bins above it. The one thread whose exclusive prefix is below k and inclusive prefix at or above it has found the digit. A scan over 1,024 values is a warp scan with __shfl_up_sync (lane l adds lane l − 1’s running sum, then l − 2, l − 4, …: five steps), one value per warp into shared memory, a scan of those 32, and each lane adds its warp’s offset: chapter 5’s reduction tree, run so that every position keeps its own partial result.

Step through the select, then the sample:

Drawing the token

With the threshold known, the block computes the row max (for a stable softmax, chapter 9), then each thread sums e(x − max)/temp over a contiguous chunk of about 50 logits, skipping those below the threshold. A scan of the 1,024 chunk sums turns them into a cumulative distribution in index order: thread t knows the probability mass before its chunk and after it. The host supplies one uniform random number u per row (so that a run is reproducible from its seed); the thread whose interval contains u · total walks its chunk once more and stops at the token where the running sum passes the target. One block, one row, five barriers, no sort and no copy to the host but the chosen id.

Your move: the histogram has 256 bins and 1,024 threads add into it. Logits of a trained model cluster: most of the 50,257 keys share the same top byte. What does that do to the first pass, and what would a library do about it?

Shared-memory atomics on the same address serialize, so when nearly every key lands in two or three bins, the first pass runs at the rate of one increment per address per clock or worse, not 1,024 per clock: a few hundred microseconds instead of a few. The second pass is better (keys spread over the second byte) and the third and fourth better still. A library privatizes one more level: each warp keeps its own 256 bins (or uses __match_any_sync to count equal keys within the warp first), and the per-warp histograms are summed once; it may also start from the second byte when the first is known to be uniform. Timing the four passes separately would show the skew (the lab does not; a stretch); at B = 1 the whole kernel is still far below the launch floor of the forward pass that precedes it.

8. Where the time goes

Three things to look for, each a prediction until your trace replaces it.

The launch count. Count the loop of section 5 with the cuBLAS backend: per layer, a layernorm, a GEMM plus its bias kernel, three attention kernels, a GEMM plus bias, a layernorm, a GEMM plus bias-GELU, a GEMM plus bias: 13 launches, 156 for twelve layers, plus the embedding, the final layernorm, the gather and the head: about 160 launches per forward pass, and about 110 with the own backend, whose epilogues are inside the GEMMs. Each launch costs a few microseconds of CPU and GPU time whatever it does (chapter 4’s floor; chapter 5’s graphs demo measured yours). At T = 1,024 the pass is 15–25 ms of real kernel time and the floor is a few percent; at T = 64 the kernels are tiny and the floor is a third or more of the pass. Decode with a cache, chapter 13’s regime, is the T = 1 version of this: nearly the same launches (148 with cuBLAS: one attention kernel instead of three, plus the cache append) for 1 ms of DRAM time.

The shape of the timeline. On the nsys row for the GPU, a prefill is a dense band; the generated tokens follow as one band each, with two gaps per token: the synchronous copy of the ids in and the fetch of the chosen id out, each a round trip through the CPU. Between kernels inside a band there should be no white space at T = 256 and visible white space at T = 1, where the GPU finishes each kernel before the CPU has issued the next.

Generation without a cache. Each generated token reruns the forward pass over the whole sequence, so the time per token grows linearly with the length so far, and generating n tokens after a prompt of T costs about n(T + n/2) token-forwards: 64 tokens after a 256-token prompt is 18,000 token-forwards, where the cached engine does 256 + 64. generate prints the time to the first token and the time per token after it; with --no-cache the second number is tens of milliseconds and rising, with the cache it should be close to the 1 ms of chapter 10’s decode column plus the launch floor. Chapter 13 takes that comparison apart.

What to do about the floor is Part IV’s business (graph capture, fewer and fatter kernels, keeping sampling and the id copies on the GPU for many steps). What this chapter asks is that you measure it: the own backend’s 110 launches against cuBLAS’s 160 at T = 64 is the first comparison, and the per-class table at T = 1,024, where the attention kernels of lab 9 should be the largest line after the linear layers, is the second.

Check your understanding

Why can two correct FP32 implementations of the same model never agree bitwise, and how does the engine define “matches” instead?

Floating-point addition is not associative; different kernels sum in different orders and use different implementations of exp and tanh, and the differences compound over layers. The engine checks random small models against a double-precision reference with a tolerance just above FP32 rounding, and the real weights against PyTorch’s FP32 logits with a looser tolerance plus top-1 agreement at every position.

What does export.py change about the checkpoint, and what does it deliberately not change?

It changes the container: from a JSON-indexed safetensors file to one flat buffer with a fixed header and a fixed, layer-major tensor order that the C++ side can map with pointer arithmetic. It does not change a single value or layout inside a tensor: the [in, out] Conv1D weights are copied as bytes, so the GEMMs need no transpose, and the tied embedding is stored once.

Why is a cudaMemcpy from malloc memory slower than from cudaMallocHost memory?

The copy engine needs physical addresses that will not move, and pageable memory can be moved or swapped by the OS. So the driver stages pageable data through its own pinned buffer, chunk by chunk, with the CPU doing that first copy; pinned memory is DMA’d directly at PCIe speed.

Give two reasons an engine allocates all activation memory once, up front.

cudaMalloc is slow and can synchronize the device, and repeated allocation fragments memory; and fixed pointers are required to capture the step as a CUDA graph, which replays exactly the recorded addresses. A single arena carved by a plan also makes the memory bill explicit: which buffer grows with B·T, which with T2, which with B·Tmax.

You have a mismatch against PyTorch. Describe the bisection method and name one fault it would localize to the attention kernel.

Dump the residual stream after every layer from both implementations and find the first layer that diverges, then dump that layer’s intermediates. A fault that shows as “position 0 correct, later positions wrong” is in attention: head column offsets, the key third’s offset, the scale, or the mask boundary, since position 0 attends only to itself and bypasses all of them.

How does radix select find the k-th largest of 50,257 logits without sorting, and why is its histogram kept in shared memory?

It maps floats to order-preserving unsigned keys, histograms one byte at a time from the top, and scans the bins downward to find the byte in which the cumulative count reaches k; four passes fix the threshold. The histogram is built with atomic increments, which serialize per address; in shared memory they are per-SM and cheap, and only the finished 256 counts are read (privatization).

What is a scan, and where does the sampling kernel use one?

A prefix sum: every position receives the sum of all values up to it, computed in log steps with shuffles within a warp and a second level across warps. Sampling uses it twice: over the histogram bins, to find which bin contains the k-th largest; and over the per-thread probability sums, to turn them into a cumulative distribution so that one thread can locate the token where the random target falls.

Why does generation without a KV cache get slower with every token, and what is the total cost of n tokens after a prompt of T?

Each new token reruns the forward pass over every token so far, so the step costs T + i token-forwards at step i: about n(T + n/2) in total, against T + n with a cache. The keys and values of earlier tokens never change under the causal mask, so recomputing them is pure waste.
