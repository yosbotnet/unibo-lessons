Part III — Attention · Chapter 13

Inference arithmetic: FLOPs, bytes, KV cache, prefill vs decode

~55 min read2 interactive widgets4 plateslab 12 · ~45 min on your GPU

The chapter in one paragraph

Chapter 1 estimated decode on a whiteboard: read every weight once per token, so tokens per second is bandwidth over model size. It promised this chapter would make that exact, and the exact version has only one new ingredient. Every step of an inference engine costs max(FLOPs / peak, bytes / bandwidth) plus overhead, and the bytes are of two kinds: the weights, which every sequence in a batch shares, and the KV cache, the stored keys and values of each sequence’s earlier tokens, which is private to the sequence and grows with its length. Prefill pushes a whole prompt through at once, does hundreds of FLOPs per byte and is compute-bound. Decode makes one token per sequence per step, reads all the weights and all the caches to do it, and is memory-bound. From counting alone you get the time to the first token, the time per token after that, the throughput, the largest batch that fits in 12 GB, and the batch size and context length where each bound flips, before writing a line of code. The chapter counts GPT-2 small on your card and Llama-3-8B on an H100, builds the calculator, and ends with what the counting misses and why real engines reach 60–85% of it.

1. Two phases, four numbers

A request to a language model is a prompt of Tp tokens followed by Tout generated tokens, and the engine handles the two parts differently because they offer the GPU different amounts of parallel work (chapter 6’s M). Prefill runs the whole prompt through the model in one forward pass: M = Tp rows, every linear layer a real GEMM, and attention over the full Tp×Tp causal triangle (chapter 10). Its output is one thing: the next token. Decode then runs one forward pass per generated token: M = 1 row per sequence, every linear layer a GEMV, and attention of one query against everything before it. Each decode step appends one token and runs again, Tout times. A generation step is one such pass; with a batch of B sequences, one step produces B tokens.

Four numbers describe the result, and they are the ones every engine benchmark reports:

MetricDefinitionSet by
TTFT, time to first tokenfrom request to the first output token: the prefill pass, plus the sampling that picks the tokenprefill FLOPs, compute peak

The tension between the last two is the latency-throughput trade: a bigger batch makes each step a little longer (more cache bytes, section 5) and a lot more productive (more tokens per step), so throughput rises while every user’s TPOT worsens a little. The whole chapter is about putting numbers on “a little” and “a lot”, and both come from two counts per token: FLOPs and bytes.

2. FLOPs per token, derived

Chapter 6 counted GPT-2 small by hand: 2 FLOPs per weight of every linear layer, including the LM head. Here is the general form, because the calculator needs it for models that are shaped differently. Call Nmm the number of parameters that sit in matrix multiplies: the four linear layers of every block (or seven in a SwiGLU block: Q, K, V, O, gate, up, down), plus the LM head, which is a GEMM over the vocabulary whether or not its weights are tied to the input embedding. Not in Nmm: the input embedding (a gather, 0 FLOPs), position embeddings, and the norms’ scale vectors. Then every token, in prefill or decode, costs

FLOPslinear = 2 · Nmm per token

Attention is the one term that depends on how many tokens came before. For one query at position t, each head computes t scores (a dot product of length D: 2D FLOPs each) and a weighted sum of t value vectors (2D again); over H heads that is 4t·H·D = 4t·C per layer (in GPT-2, H·D = C; in a GQA model the query heads still number H, so the count is unchanged), and over L layers:

FLOPsattention = 4 · L · t · C per token at context length t

So at the context lengths of this course, attention is a small share of the FLOPs even for GPT-2, whose head dimension is small and whose layers are thin. That is worth holding on to, because sections 5 and 7 will show that attention is a large share of the bytes, and chapter 14 will show that it is the dominant share of the time at long context for a third reason again. Three different reasons, three different fixes.

Your move: at what context length do the attention FLOPs per token equal the linear FLOPs, for GPT-2 small and for Llama-3-8B? Set 4LtC = 2Nmm.

t = Nmm / (2LC): 123.6 M / (2 × 12 × 768) ≈ 6,700 tokens for GPT-2 small, and 7.5 G / (2 × 32 × 4,096) ≈ 28,600 for Llama-3-8B. Below those lengths the linear layers own the FLOPs. Wide models push the crossover out because Nmm grows with C2 while attention grows with C. A context of 128K tokens, which Llama 3.1 supports, is well past it: there, and only there, attention dominates even the FLOPs.

3. Bytes per token: the KV cache

Chapter 10 made the observation that decode is built on: the key and value vectors of a token depend only on that token and the layers below it, never on the tokens after it, so once computed they never change. Recomputing them at every step would cost a full prefill per token. Instead the engine caches them: after the QKV projection of every layer, the new token’s k and v (one D-vector per KV head) are appended to a per-sequence, per-layer buffer, and attention reads the buffer instead of recomputing it. The cache is therefore the model’s memory of the conversation, and its size per token is fixed by the architecture:

bytesKV per token = 2 · L · Hkv · D · s

where the 2 is “keys and values”, Hkv is the number of KV heads (equal to H in GPT-2; 8 against 32 query heads in Llama 3’s grouped-query attention, which exists precisely to shrink this number), and s is the bytes per element of the cache’s format, which need not be the weights’ format.

Model, cache formatPer tokenPer 1,024-token sequencePer 1,024-token sequence, as a share of the weights
GPT-2 small, FP32 (the engine)2 · 12 · 12 · 64 · 4 = 73.7 KB75.5 MB15% of 498 MB
GPT-2 small, FP1636.9 KB37.7 MB15% of 249 MB
Llama-3.2-1B, FP162 · 16 · 8 · 64 · 2 = 32.8 KB33.6 MB1.4% of 2.47 GB

The last row is why GQA exists: it divides the cache by the group size (4 here) at a small cost in model quality, and section 7 shows it also multiplies attention’s intensity by the same factor.

Two things follow immediately. The cache is written once per token and read once per step per sequence, so at context t a decode step reads t × bytesKV for each sequence, and the engine’s kv_append is a trivial kernel next to the attention that reads the result. And the cache is allocated for the maximum context in the engine’s plan (Tmax = 1,024 for GPT-2), so memory is reserved by the slot, not by the token: a sequence that has used 100 of 1,024 slots still holds 75.5 MB. Chapter 17’s paged caches fix that; for now the planning rule is simply

memory = weights + B · Tmax · bytesKV + activations (small: a few multiples of B·C·s, plus the B·V logits)

and the largest batch that fits is (VRAM − weights) / (Tmax · bytesKV): for GPT-2 small in FP32 on your card, (12 − 0.5) GB / 75.5 MB ≈ 152 sequences of 1,024 tokens. For Llama-3-8B in FP16 the weights alone are 16 GB and the question does not arise on a 12 GB card until Part IV quantizes them.

Your move: a chat with 300 tokens of system prompt shared by every user. Does the cache for those 300 tokens have to be private to each sequence?

No, and that is prefix caching. The keys and values of a token depend only on it and on the tokens before it (the causal mask), so every sequence that starts with the same 300 tokens computes exactly the same 300 cache entries, and they can be computed once and shared, which also removes 300 tokens of prefill per request. It needs a cache layout in which a sequence’s entries are not one contiguous [Tmax][D] strip, since the shared part lives elsewhere: that is one more reason for the paged layout of chapter 17. The arithmetic stays the same: the step still reads the 300 entries for each sequence that attends to them.

4. Prefill: the time to the first token

A prefill of Tp tokens runs every linear layer with M = Tp rows and attention over the causal triangle, so the useful FLOPs are the per-token counts of section 2 summed over positions 0 to Tp − 1, with one exception: the LM head runs once, on the last position, because prefill needs only the logits of the next token (chapter 11’s engine computes just that row). So the head’s 2VC (V the vocabulary) is not in prefill’s per-token term; decode still pays it every step, since its one position is always the last:

FLOPsprefill = Tp · 2(Nmm − VC) + 2VC + 2 · L · Tp2 · C

(the attention term is 4LtC summed over t, which gives 2LTp2C; a naive kernel that computes the masked half too does twice that, chapter 10’s causal waste). The bytes are the weights once, the cache written once, and the activations passing between kernels, which chapter 11’s timeline measured and which are small next to either with a fused attention kernel; chapter 10’s naive attention, which the engine runs, moves about 2.6 GB of score traffic per prefill at Tp = 1,024, more than the weights and the cache together, and that is part of why a measured prefill lands above the roof (chapter 14 removes it). For GPT-2 small at Tp = 1,024 in FP32 on your card:

That is chapter 6’s “about 9 ms” guess, now itemized and without the head at the 1,023 positions whose logits nobody reads, and the TTFT for a 1,024-token prompt is this plus one sampling pass, at the roof. Two readings of the table matter later. First, prefill time grows linearly with Tp through the linear term and quadratically through attention, but the quadratic term is small until the crossover of section 2’s guess, so TTFT is nearly proportional to prompt length at these sizes: 1,024 tokens cost about 6.3 ms, twice the 3.0 ms of 512 tokens, not four times. Second, the bound is set by the FP32 peak because the engine is FP32; in FP16 on the tensor cores the same prompt would take 3.1 ms at the roof, and the bytes would halve too, so it would stay compute-bound. Prefill is where chapters 7, 8 and 12 pay off, and where a single H100 is 16 times your card (989 against 61.7 TFLOPS in FP16).

Your move: an engine prefills a batch of 8 prompts of 1,024 tokens together rather than one after the other. How does the total prefill time change, and the TTFT of the first prompt?

The total barely changes: prefill is compute-bound, and 8 prompts together are 8 times the FLOPs for the same peak, so about 8 × 6.3 = 50 ms either way (slightly less together, because the weights are read once instead of 8 times and the GEMMs are larger and closer to the roof). But the first prompt’s TTFT grows from 6.3 to 50 ms, because its token is only produced when the whole batch finishes. Batching prefill buys throughput only through the small kernel-efficiency gain, at a real latency cost; batching decode, next section, is a different story. Engines therefore schedule the two phases differently, and chunk long prefills so that decode steps of other users can run between the chunks.

5. Decode: shared weights, private caches

A decode step for a batch of B sequences at context t does B × (2Nmm + 4LtC) FLOPs, and moves two kinds of bytes:

bytesstep = W + B · t · bytesKV

The weights W are read once for the whole batch: that is chapter 4’s batch dial, every weight used B times per trip from DRAM. The caches are read once each: B sequences, B private caches, no sharing. The step time is the larger of the two roof times, and the table shows it for GPT-2 small in FP32 at t = 1,024 on your card, at the spec bandwidth (lab 0’s 88% makes every memory time 14% longer):

Read it row by row and the shape of decode appears. At B = 1 the step is the weights plus a little: chapter 1’s 0.74 ms becomes 0.85 ms once the cache is counted, and the ceiling is 1,170 tokens/s instead of 1,350. The compute time is a hundred times smaller: the math units are idle 99% of the step. Going to B = 4 costs 40% more time for 4 times the tokens, the batch dial working as chapter 4 said. But the cache column grows with B while the weight column does not, and by B = 16 the caches are more bytes than the weights; from there each doubling of the batch nearly doubles the step, and throughput saturates near 8,500 tokens/s. The batch where the two columns cross is

B · t = W / bytesKV  =  498 MB / 73.7 KB ≈ 6,750 token-slots, i.e. B ≈ 6.6 at t = 1,024

and it is a count of cached tokens across the batch, not of sequences: 8 sequences of 1,024 and 64 of 128 cost the same. Compute never catches up in this table: the batch at which it would (chapter 1’s 92, and it is 92 in FP32 too: the peak halves and the bytes per weight double) was computed without a cache, and the cache adds bytes faster than the batch adds FLOPs. Section 6 says exactly when that is so.

Same batch, same weights, same FLOPs per token; only the private bytes changed. This is why serving throughput is quoted at a context length, and why short-context benchmarks flatter every engine.

6. Both phases on the roofline

Put each phase’s FLOPs over its bytes and the two phases land in chapter 4’s two corners. Prefill: hundreds of FLOP/B, on the roof. Decode at B = 1: 0.28 GFLOP over 573 MB, 0.5 FLOP/B, the bottom of the slope. The batch dial moves decode right, but not the way it moved a bare GEMV, because the cache bytes grow with B too:

intensitydecode(B) = B (2Nmm + 4LtC) / (W + B t bytesKV)  →  (2Nmm + 4LtC) / (t bytesKV) as B → ∞

So there is a ceiling on how far right decode can go, set by the context length alone: at t = 1,024 for GPT-2 small in FP32 it is 285 M / 75.5 MB ≈ 3.8 FLOP/B, a twelfth of the FP32 ridge. Compute catches up only if the limit exceeds the ridge, i.e. if t · bytesKV < 2Nmm · (bandwidth / peak), ignoring the attention FLOPs, which only help a little. The right-hand side is the per-sequence weight work expressed as bytes: 5.4 MB for GPT-2 small in FP32 on your card, 51 MB for Llama-3-8B in FP16 on an H100. The left-hand side is one sequence’s cache: 75.5 MB and 268 MB (at 2,048) respectively. Both fail, by an order of magnitude. In the language of chapter 4’s roofline widget: the linear layers batch, attention does not, and once the cache is the larger part of the bytes the whole step inherits attention’s behaviour.

There are three ways to move the dashed line, and Parts III and IV are organized around them: make bytesKV smaller (fewer KV heads: GQA and MQA; narrower cache formats: FP8 and INT4 caches with per-block scales, chapter 16), make W smaller so the cache matters sooner but the step is shorter (weight quantization, chapter 16), and make the cache bytes that are read actually arrive at full bandwidth (the decode-attention kernels of chapter 15, which is the next section’s problem).

7. Attention at decode: the intensity that does not move

Inside the decode step, the attention kernel is the one that reads the cache, and its own intensity is fixed by the architecture, not the batch. For one query head against one cached position: 2D FLOPs for the score and 2D for the value, against 2D·s bytes of key and value read: 2 / s FLOP per byte, 0.5 in FP32, 1 in FP16, 2 in FP8. A batch does not change it (chapter 4’s guess: each sequence reads its own cache), and more heads do not either, because each head reads its own keys. The one thing that does is GQA: when g = H / Hkv query heads share one KV head, the kernel can load each key and value once and use it for g dot products, so the intensity becomes 2g / s: 4 FLOP/B for Llama 3 in FP16. Still a twenty-third of your card’s tensor-core ridge of 92. Decode attention is a GEMV over the cache, memory-bound at any batch, and a kernel for it has one job: read the cache at the full 672 GB/s.

That job is harder than it sounds, and it is chapter 15. The shape is one query row per (sequence, head) against t keys: at B = 1 and H = 12 there are 12 such rows, one block each in a naive kernel, on a card with 48 SMs; chapter 3’s Little’s law says 12 blocks cannot keep enough bytes in flight to pull more than a fraction of the bandwidth. The arithmetic of this chapter assumes the cache streams at full speed; the lab’s bench-decode will show the engine’s simple decode kernel does not, and the gap is what split-K (FlashDecoding) closes.

Your move: switch the engine’s cache from FP32 to FP16 while the weights stay FP32. For GPT-2 small at B = 64, t = 1,024, what happens to the step time, from the table in section 5?

The cache bytes halve: 4.83 GB → 2.42 GB, so the step moves 498 + 2,416 MB = 2.9 GB instead of 5.3: 4.3 ms instead of 7.9, 1.8 times the throughput, with the weights untouched and no change to any matmul. At B = 1 the same change saves 38 of 573 MB, 7%. The cache format is a decode-throughput lever that only matters at scale, which is why serving engines quantize the cache before they worry about anything else at large batch, and why single-user tools do not bother.

Two lessons from the table. For a small model, the overheads are the story: a 0.44 ms launch floor against 0.85 ms of real work means that without fusion or graphs, GPT-2 small on your card is overhead-bound at B = 1, as chapter 1 suspected, and no kernel improvement shows until the floor is lowered. For a large model, the floor grows only with the layer count (about 1.2 ms for Llama-3-8B’s 32 layers) against a step of 5 to 25 ms, a fifth at most and a few percent once captured in a graph, and the losses that remain are kernel efficiency: achieved bandwidth in the GEMVs and in decode attention. That is why the serving literature’s 60–85% is quoted for large models, and why the same engines look much worse on small ones.

9. The whiteboard estimate, and the calculator

The question as an interviewer asks it: “Llama-3-8B in FP16 on one H100. 64 concurrent users, 2,048-token prompts, 256 output tokens each. What are TTFT, time per token, and throughput, and does it fit?” The answer, in the order you now have the pieces:

  1. Weights. 8.03 G × 2 B = 16.1 GB. The H100 has 80 GB and 3.35 TB/s, 989 TFLOPS dense FP16.
  2. Cache. 131 KB per token; each sequence ends at 2,304 tokens: 302 MB. 64 of them: 19.3 GB. Total 35.4 GB plus activations: fits, with room for about 3 times the batch at this length.
  3. Prefill. 2,048 × 14.0 G (the blocks; the head runs once, 1 GFLOP) + 2 × 32 × 2,048² × 4,096 = 28.6 + 1.1 = 29.7 TFLOP per prompt: 30 ms at peak, call it 38–46 ms as TTFT at 65–80% efficiency if prompts are prefilled one at a time; 64 together would be 1.9 s, so an engine chunks and interleaves them.
  4. Decode step. Bytes: 16.1 GB + 64 × 2,048 × 131 KB = 16.1 + 17.2 = 33.3 GB at the start, 35.4 GB at the end: 9.9 to 10.6 ms at spec bandwidth. FLOPs: 64 × (15.0 G + 1.07 G) = 1.03 TFLOP, 1.0 ms. Memory-bound by 10 to 1. TPOT ≈ 10 ms, more like 12–15 ms in practice.
  5. Throughput. 64 tokens per 10 ms: 6,250 tokens/s at the roof, 3,750–5,310 tokens/s at 60–85%. Per user, 59–98 tokens/s.
  6. Where it could go. The cache is already more bytes than the weights at this batch and length, so doubling the batch adds about 31% throughput for a 53% worse TPOT; an FP8 cache would take 8.6 GB off every step; and the tensor cores are idle 90% of the time, which is the argument for speculative decoding (Part IV), which spends those FLOPs on guesses.

The calculator does these steps for five models and two cards, and is the full version of chapter 1’s w-decode: it adds the cache, the attention FLOPs, the prefill, the memory check and the efficiency and launch-floor corrections of section 8. Set it to the interview question first, then to your engine (GPT-2 small, RTX 5070, FP32, B = 1, 896 and 128, which fill its 1,024 positions), and keep that second readout: lab 12 measures it.

Your move: in the calculator, set Llama-3.2-1B in FP16 on your card and raise the batch from 1 to 64 at a 4,096-token context. Before you do: which column will stop the batch first, memory or time?

Memory. The weights are 2.5 GB, so 9.5 GB is left for caches at 32.8 KB per token: 9.5 GB / (4,096 × 32.8 KB) ≈ 70 sequences, and the calculator refuses B = 71 before the step time has done anything dramatic (at B = 64 the step is 16 ms, 3,900 tokens/s, still memory-bound at 17 FLOP/B against a ridge of 92). On a 12 GB card the KV cache is the budget, not the time, and it is the first thing a serving engine runs out of.

Check your understanding

Why is prefill compute-bound and decode memory-bound, for the same model on the same card?

Prefill runs every linear layer with M = prompt-length rows, so each weight read from DRAM is used that many times: intensity in the hundreds, above the ridge. Decode runs them with one row per sequence, each weight used once per sequence per trip, and additionally reads every sequence’s private cache: intensity of order 1, far below the ridge.

What does a decode step read that a prefill of the same number of tokens does not, and what does it write that prefill writes too?

It reads the entire KV cache of every sequence in the batch (prefill reads none: it has nothing cached yet). Both write one cache entry per processed token. A decode step also reads all the weights, as does prefill, but per token produced rather than per prompt.

A batch of B sequences at context t. Write the bytes of one decode step and say which term batching amortizes and which it does not.

W + B·t·bytesKV. The weights W are read once for the whole batch, so their cost per token falls as 1/B; the caches are private, one per sequence, so their cost per token is constant in B and grows with t.

Why does the cache-versus-weights crossover depend on B·t rather than on B alone?

Because the cache bytes read per step are the total number of cached tokens across the batch times the bytes per token; a batch of many short sequences and a batch of few long ones read the same cache bytes. The crossover is at B·t = W / bytesKV.

Chapter 1 said compute catches up with memory at a batch of about 92 for an FP16 model. Under what condition is that still true once the KV cache is counted, and what is the condition in words?

Only if one sequence’s cache, t·bytesKV, is smaller than the weight work per sequence expressed in bytes, 2Nmm·(bandwidth / peak); otherwise the intensity has a ceiling below the ridge and decode stays memory-bound at any batch. In words: the context must be short enough that each sequence adds less private-byte cost than it adds FLOPs-worth of shared work.

What is the arithmetic intensity of decode attention, and why does batching not raise it while GQA does?

Per cached position and head: 4D FLOPs for 2D·s bytes, i.e. 2/s FLOP per byte. Batching adds sequences that each read their own cache, so FLOPs and bytes grow together. GQA lets g query heads use one loaded key and value, so FLOPs grow by g for the same bytes.

Two engines run the same model at B = 1; one is a small model, one is large. Why does the launch floor hurt them so differently?

The floor is a fixed cost per step (kernel count times a few microseconds), independent of the model’s width and growing only with its layer count, while the useful memory time grows with the weights. For a small model the floor is comparable to the whole step; for a large model it is a much smaller fraction. Fusion and CUDA graphs matter most where the model is small or the step is short.

What decides the largest batch an engine can serve at a given context length, and why is it reserved by slot rather than by token in the engine of chapter 11?

(VRAM − weights − activations) / (Tmax × bytesKV). The contract allocates each sequence’s cache as a contiguous [H][Tmax][D] strip, so the memory is taken when the slot is assigned, whatever the sequence’s actual length. Paged caches (chapter 17) allocate by block of tokens instead.
