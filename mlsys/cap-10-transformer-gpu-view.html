Part II — Kernels that matter · Chapter 10

The transformer from the GPU’s point of view

~65 min read2 interactive widgets4 plateslab 9 · ~50 min on your GPU

The chapter in one paragraph

Chapter 6 drew the transformer block as a list of operations and left one box closed: attention. This chapter opens it, from the side the GPU sees. A block is two sublayers, each “normalize, mix, add back”; the MLP mixes the channels within a token, and attention mixes across tokens, the only operation in the model that does. Attention is a content-based lookup: every token asks a question (its query), every token advertises what it holds (its key) and what it would hand over (its value), and each token’s output is the average of the values, weighted by how well its query matches each key. To the GPU that is two matrix multiplies whose operands are both activations, around a softmax (chapter 9) over a matrix of scores that has T2 entries per head: at 1,024 tokens, 50 MB per layer, larger than every weight matrix in the block, and growing with the square of the context while everything else grows linearly. The chapter counts what that costs, shows that the causal mask wastes half of it, and then takes the step that makes generation affordable: because a token can only look backwards, the keys and values of earlier tokens never change, so they can be computed once and kept. That is the KV cache, and it splits inference into prefill and decode, the two regimes the rest of the course is organized around.

1. The block in five lines, and the two mixing directions

Chapter 6’s Fig. 4 is the whole model; here is one block of it as five lines, for a stream x of shape [B·T, C], one row per token:

h = x + attention(layernorm_1(x))      # sublayer 1: normalize, mix across tokens, add back
y = h + mlp(layernorm_2(h))            # sublayer 2: normalize, mix across channels, add back
# mlp(u) = gelu(u @ W_fc + b_fc) @ W_proj + b_proj

The two sublayers have the same skeleton: normalize the row (chapter 9), mix, add the result back to the stream (the residual, so that each sublayer contributes a correction instead of replacing the signal). What differs is the direction of the mixing. The MLP takes one token’s 768 channels and produces that token’s new 768 channels; it never looks at another row. If the model were only MLPs, each token would be processed in complete isolation and the output for “bank” could not depend on whether “river” came before it. Attention is the one operation that mixes rows: a token’s output is built from other tokens’ values. Everything the model knows about context passes through it.

From the GPU’s side, the block is therefore: four GEMMs against weights (QKV projection, output projection, MLP up, MLP down; chapters 7 and 8), two GEMMs whose operands are both activations (the two inside attention; new in this chapter), one softmax whose rows are as long as the sequence (chapter 9), and the small operations fused into the rest. The next sections open the attention box.

2. Attention as a lookup

In goes a sequence of T vectors (one per token, C = 768 channels each, already layer-normalized); out comes a sequence of T vectors of the same shape, where each output vector is a mixture of information from the tokens before it. The mechanism, defined term by term:

  • Three linear projections turn each token’s vector xi into a query qi = xiWq, a key ki = xiWk and a value vi = xiWv, each a vector of D numbers. The names are a database metaphor that happens to be exact: the query is what token i is looking for, the key is what token j offers to be matched against, the value is what token j hands over if matched.
  • The score sij = qi · kj / √D says how well token i’s question matches token j’s key. A dot product of D numbers of unit variance has variance D, so without the 1/√D the scores would grow with the head size and the softmax below would saturate into a one-hot pick; the scale keeps them of order one whatever D is.
  • The causal mask: in a model that generates left to right, token i may only look at tokens 0 to i. Scores sij with j > i are set to −∞ (chapter 9’s convention) so that they vanish in the softmax. This is a training-time rule (the model must not see the answer), but it is also what makes section 7 possible.
  • A softmax over each row of scores turns them into weights pij ≥ 0 that sum to 1 over j: how much of its attention token i pays to each earlier token.
  • The output oi = ∑j pij vj: the weighted average of the values of the tokens it attended to. A vector of D numbers per token.

For all tokens at once, with Q, K, V the [T, D] matrices whose rows are the qi, ki, vi:

S = QKT / √D  [T, T];   P = softmaxrows(mask(S));   O = PV  [T, D]

Two matrix multiplies and a row softmax. Play with it at toy size, T = 8 tokens and D = 4: click a query row and follow what it reads.

Your move: with the causal mask on, what is the output of token 0, before you look at any number?

Its own value, v0, exactly. Row 0 of the masked scores has one finite entry, s00, and −∞ everywhere else, so the softmax gives p00 = 1 and zero for the rest. Token 0 has nobody to look at. Token 1 mixes two values, and the last token mixes all T: the amount of work per row grows down the matrix, which is section 6’s point.

3. Heads, the fused QKV GEMM, and the layout the kernels want

One lookup per token is one kind of relation (say, “the noun this adjective modifies”). The model wants several at once, so it runs H independent lookups, called heads, each with its own Wq, Wk, Wv and its own score matrix. To keep the cost fixed, the heads split the channels: GPT-2 small has H = 12 heads of D = 64, so 12 × 64 = 768 = C. The outputs of the heads are concatenated back into one [T, C] matrix and passed through the output projection Wo [C, C], which mixes the heads’ findings.

One GEMM, not thirty-six

Thirty-six small projections (3 per head, 12 heads) would be thirty-six launches of [T, 768] × [768, 64] GEMMs with N = 64, too narrow to tile well (chapter 7). So the weights are stored side by side as one matrix Wqkv of shape [768, 2,304] = [C, 3C], and one GEMM produces everything: qkv = x @ W_qkv + b_qkv, shape [B·T, 3C]. The column order is the one Hugging Face’s GPT-2 checkpoint uses and the one the engine contract fixes: columns [0, C) are the queries, [C, 2C) the keys, [2C, 3C) the values, and within each third, head h owns the 64 columns h·D to h·D + 63.

The head split is indexing, not copying

Chapter 6 warned that [B, T, H, D] → [B, H, T, D] is a transpose, and a copy if you materialize it. Nobody materializes it. Head h’s Q for sequence b is a [T, D] matrix whose rows are 64 consecutive floats, spaced 3C = 2,304 floats apart: a matrix with a leading dimension (the stride between rows) of 3C instead of D. Every GEMM routine takes a leading dimension, so the kernel reads the heads in place:

// where head h of sequence b lives inside qkv[B*T, 3C]; row stride (leading dimension) is 3C everywhere
const float* Q = qkv + (size_t)b * T * 3 * C + 0 * C + h * D;   // Q[i][d] = Q[i * 3C + d]
const float* K = qkv + (size_t)b * T * 3 * C + 1 * C + h * D;
const float* V = qkv + (size_t)b * T * 3 * C + 2 * C + h * D;
float*       O = att + (size_t)b * T * C + h * D;              // O[i][d] = O[i * C + d]: heads merged by the same trick

The output buffer att[B*T, C] receives head h’s [T, 64] result at columns h·D, with leading dimension C, so “concatenate the heads” is also just where each head writes. The output projection then reads att as an ordinary [B·T, C] matrix.

Batched GEMM

Attention’s matmuls are small (T × T × 64 per head) and there are B·H of them, all the same shape, at regular distances in memory. That is a batched GEMM: one launch, grid dimension z = the batch index, and each block adds z * stride to its pointers. cuBLAS calls it cublasSgemmStridedBatched; the stride between heads is D floats and between sequences T·3C. Lab 9 writes both a hand-made batched kernel and the cuBLAS call.

Your move: why is the head size a round D = 64 (or 128) in nearly every model from GPT-2 to Llama 3, rather than 32 or 256?

A guess from this course’s material: the per-head matmuls have inner dimension D for QKT and output width D for PV, so D sets the arithmetic intensity of attention’s matmuls and the width of the fragments a warp holds; 64 FP16 values is 128 bytes, one full memory transaction and a round number of m16n8k16 fragments, and a 64-wide tile of K or V fits shared memory comfortably. Smaller heads make the matmuls thin and memory-bound; bigger heads cost registers in the fused kernels of chapter 14 and give the model fewer relations to learn. Nobody proved 64 optimal; it is where the hardware’s round numbers and the model’s preferences met, and it has stuck (Llama 3 uses 128, which is the same argument one size up).

4. Naive attention as kernels

The straightforward implementation, which is lab 9 and the engine’s first attention, runs the formula as four launches per layer:

  1. Scores, batched over B·H: S = QKT · 1/√D, each [T, T]. An ordinary GEMM with M = N = T, K = 64, except that the B operand is transposed (chapter 6’s NT case) and that the output goes to a scratch buffer of B·H·T2 floats. The mask can be applied here (write −∞ where j > i) or in the softmax.
  2. Masked row softmax: chapter 9’s warp-per-row kernel over the B·H·T rows of S, in place. Rows are never fully masked under a causal mask (the diagonal is always allowed), but the guard stays.
  3. Weighted sum, batched: O = PV, [T, T] × [T, 64], written into att with the head’s column offset.
  4. Output projection: att @ W_o + b_o, one GEMM of [B·T, 768] × [768, 768], then the residual add (chapter 9’s epilogue).

The simplest scores kernel is chapter 7’s naive matmul with the batch index on blockIdx.z and the mask folded in:

// lab 9, attn_scores_naive: one thread per score. grid = (ceil(T/16), ceil(T/16), B*H), block = (16, 16)
__global__ void attn_scores_naive(const float* __restrict__ qkv, float* __restrict__ S,
                                  int B, int T, int H, int D, float scale)
{
    int bh = blockIdx.z, b = bh / H, h = bh % H;
    int i = blockIdx.y * 16 + threadIdx.y;            // query row
    int j = blockIdx.x * 16 + threadIdx.x;            // key column
    if (i >= T || j >= T) return;
    int C3 = 3 * H * D;
    float* Srow = S + ((size_t)bh * T + i) * T;
    if (j > i) { Srow[j] = -INFINITY; return; }      // the causal mask
    const float* q = qkv + ((size_t)b * T + i) * C3 + h * D;
    const float* k = qkv + ((size_t)b * T + j) * C3 + H * D + h * D;
    float s = 0.0f;
    for (int d = 0; d < D; ++d) s += q[d] * k[d];
    Srow[j] = s * scale;
}

It is lab 5’s matmul in a new costume, with the same flaw: every thread walks its own 64-long dot product from global memory and nothing is reused on chip. Lab 9’s second version tiles it with chapter 7’s shared-memory tiles, and the third hands both matmuls to cuBLAS. The cuBLAS call needs the row-major trick of lab 6’s harness (compute ST = KQT in column-major terms) with the head stride as the batch stride; the lab’s README spells it out, because getting a transpose flag wrong is the classic attention bug and the CPU reference catches it.

Read the first row twice. A matrix multiply, memory-bound: with an inner dimension of only 64, QKT does 128 FLOPs per output element and then writes 4 bytes of it, and the writes of S dominate. Chapter 7’s tiling cannot fix it, because the problem is not reuse of the inputs but the size of the output. The attention matmuls hold 18% of the block’s FLOPs and, in this naive form, about 43% of its roofline time, all of it spent moving S. Slide T and B and watch the shares:

This is the problem chapter 14 solves. Chapter 9’s fusion limit said a row reduction cannot ride in a GEMM epilogue unless the block sees the whole row; for attention, the “row” is one query against all keys, and a block can own a few queries and stream through all the keys, carrying (m, d) and a running output. Then S is never written at all: the four vermilion passes disappear and attention’s cost drops to its FLOPs plus the reads of Q, K, V. That is FlashAttention, and the reason this chapter makes you measure the naive version first is so that the number it removes is your own.

Your move: the engine of chapter 11 allocates S once as scratch, sized for its largest B and T. In FP32 with H = 12, what is the largest T at B = 8 for which S fits in 4 GB of scratch, and what does that say about naive attention as the engine’s long-term design?

B·H·T2 × 4 B ≤ 4 GB gives T2 ≤ 4×109 / (8 × 12 × 4) ≈ 10.4×106, so T ≈ 3,200: about three times GPT-2’s own 1,024 context at a batch of 8, and the scratch is bigger than the model. Scratch that scales with B·T2 is the clearest sign that the naive design is temporary: the engine’s contract keeps the scratch behind a function (attn_prefill_*_scratch_bytes) precisely so that chapter 14’s kernel can report a size that scales with B·T instead.

6. The masked half

Under the causal mask, row i of S has i + 1 live entries and T − i − 1 that will be −∞ whatever the data. Over the whole matrix that is T(T − 1)/2 entries, just under half, whose values are known before the kernel runs. The naive scores kernel computes the dot product for every one of them (or at least visits the thread and writes the −∞), the softmax exponentiates them to zero, and the weighted sum multiplies the zeros by V. Half of naive attention’s FLOPs and half of its bytes are spent on entries that are known to be zero.

The waste is easy to see and awkward to remove in the naive design: a GEMM kernel computes rectangular tiles, and the diagonal cuts through them. Skipping whole tiles that lie entirely above the diagonal recovers most of it (a 16×16 tile at i0, j0 is dead if j0 > i0 + 15); the tiles on the diagonal still do their masked half. Lab 9’s waste mode measures three things: the full kernels, the tile-skipping versions, and the softmax over rows truncated at the diagonal, and reports what fraction of the time the mask was worth. (The engine’s own attn_prefill_naive in attention.cuh already ships with the tile skip and with softmax rows that stop at the diagonal: when you read its if (j0 > i0 + AT - 1) return;, this is where it comes from.) For FlashAttention the same skip is the difference between a kernel that costs T2 and one that costs T2/2, which at long contexts is the single largest optimization it has.

Your move: the tile-skipping scores kernel launches the same grid as the full one and returns immediately from dead tiles. Is the saving in time the same as the saving in FLOPs?

Nearly, but not quite: a dead block still costs its launch slot on the SM (chapter 2’s block scheduling) and the softmax rows were full length. For the scores and PV kernels, the bytes of S that are never written or read are the real saving (the kernels were memory-bound), and dead blocks cost microseconds in total. Expect a saving a little under the 50% of the entries: the diagonal tiles are full-cost, so at T = 1,024 with 16×16 tiles, 64 of the 2,080 live tiles are diagonal and the dead ones are 2,016 of 4,096: a 49% saving in tiles, a little less in time.

7. Generation: the KV cache, prefill and decode

A language model generates by running the forward pass, taking the logits of the last position, picking a token, appending it, and running the forward pass again. Done naively, generating the 101st token means a forward pass over 101 tokens, the 102nd over 102, and generating N tokens costs N2/2 token-forwards. The fix comes from the causal mask, and it is worth stating precisely.

Look at what the model computes for token j at layer ℓ: its key kj and value vj are projections of xj, the stream at position j, and xj depends, through the attention of layers below, only on tokens 0 to j. Tokens appended later cannot change it. So when token T arrives, every kj and vj for j < T, at every layer, is exactly what it was last step. Recomputing them is recomputing a known answer. Keep them instead: that is the KV cache, one buffer of keys and one of values per layer, with room for Tmax positions per sequence per head. Generating the next token then means:

  1. run the new token alone through the block (M = B, one row per sequence): layernorm, the QKV GEMM with M = B, giving one q, k, v per head;
  2. append k and v at position T of the cache;
  3. attention for one query row: scores against the T + 1 cached keys, a softmax over one row, the weighted sum of T + 1 cached values;
  4. the rest of the block as before, at M = B.

The queries of earlier tokens are not needed at all: nobody asks their question again. Only keys and values are cached, hence the name.

Two regimes come out of this, and the course names them now because the next five chapters are about them:

  • Prefill: the prompt’s T tokens go through the model together, M = B·T rows per GEMM, attention as in section 4, and the cache is filled from the k and v thirds of qkv. Compute-bound at useful lengths (chapter 6’s intensity table at M = 512).
  • Decode: one new token per sequence per step, M = B rows per GEMM, attention of one query against the cache. Every weight is read once per step for B tokens of output, and every sequence’s cache is read once for one token: memory-bound, as chapter 4’s “attention does not batch” said.

What the cache costs: per token, per layer, one key and one value of C floats each, so 2 · L · C · 4 bytes = 2 × 12 × 768 × 4 = 73.7 KB per token in FP32 for GPT-2 small; a full 1,024-token context is 75 MB per sequence, a batch of 16 is 1.2 GB. Chapter 13 does this arithmetic for real models and shows where the cache overtakes the weights; chapter 15 writes the decode attention kernel, which is nothing like section 4’s: a single query row against a long slab of keys is a matrix-vector product, memory-bound, and the game is reading the cache at full bandwidth. Chapter 11’s engine starts without a cache (generation by recomputation, so that correctness is simple) and the cache arrives with the measurements in chapter 13.

Your move: a decode step for one sequence with a 1,024-token context. Roughly how many bytes of weights and how many bytes of cache does it read, and which dominates for GPT-2 small?

Weights: all of them, 498 MB (chapter 6). Cache: 73.7 KB per token × 1,024 = 75 MB. The weights dominate by nearly 7× at B = 1, so the step is bounded by the weight stream, about 0.85 ms at 590 GB/s, and the cache adds 15%. With a batch of 8, the weights are still read once (498 MB) while the caches are read once each (600 MB): the cache now dominates. That crossover, and its dependence on context length and head count, is chapter 13’s central table.

Three things to read off it. In prefill, the LM head is the single biggest kernel, a fifth of the time, scoring all 50,257 words for all 1,024 positions when only the last position’s logits are needed to generate: the engine computes the head for the last position only when generating, and for all positions only when verifying. In decode, the total is 570 MB of reads, nearly all weights, for 0.28 GFLOP: intensity 0.5, about a hundred times left of the ridge (52 FLOP/B at 590 GB/s; 46 at the rated 672), and about 1 ms per token at the DRAM ceiling before the launch floor, which with about 150 launches of a few microseconds each is of the same size (chapter 11 measures it). And the two regimes never meet on the roofline: prefill is where chapters 7 and 8 earn their keep, decode is where bytes are everything, and the same kernel list serves both with the shape M as the only difference.

Embeddings and the LM head

The two ends of the model are both the same [50,257, 768] table wte (chapter 6’s weight tying). At the input it is a gather: token t at position p becomes the row wte[t] + wpe[p], one warp per token, each row 3 KB and contiguous, chapter 3’s friendly kind of random access. At the output it is a GEMM, logits = x @ wte^T: [M, 768] × [768, 50,257], and because wte is stored [50,257, 768] row-major, this is the NT case, B transposed. At decode it is a [1, 768] × [768, 50,257] matrix-vector product that reads 154 MB for 77 MFLOPs: the largest single read of the step, a third of the weights, for one word.

9. What changed since GPT-2, from the GPU’s side

GPT-2 is the course’s model because it is small, its weights are public, and its block is the one every later model is a variation of. The variations matter to the kernels, and here they are in one table, to be met again in Parts III and IV. The model side of each is covered in the Modern Transformer page; this is the kernel side.

None of these changes the list of kernel kinds: GEMMs, a fused attention, row norms, gathers, and epilogue passengers. That is why the engine you build around GPT-2 carries over.

Check your understanding

Which operations in a transformer block mix information across tokens, and why does it matter for how the kernels see the batch?

Only attention. Every other operation acts on one token’s row, so the kernels treat the batch as B·T independent rows. Attention mixes rows within one sequence, so it needs the sequence boundaries, the mask, and a per-sequence (and per-head) batch of matmuls.

Why do the scores get divided by √D, and what would happen to the softmax without it?

A dot product of D unit-variance numbers has variance D, so scores would grow with the head size; the softmax of large scores is nearly one-hot, and its gradients vanish. Dividing by √D keeps scores of order one regardless of D.

The head split [B, T, H, D] → [B, H, T, D] is a transpose. Why does a good kernel never execute it?

Because head h’s matrix is readable in place: rows of D consecutive floats spaced 3C apart, which is a matrix with leading dimension 3C. Batched GEMMs take a leading dimension and a batch stride, so the heads are selected by pointer arithmetic, and the merge of heads on the output side is the same trick with leading dimension C.

QKT is a matrix multiply, yet in naive attention it is memory-bound. Why, and why does tiling not fix it?

Its inner dimension is only D = 64, so each output element costs 128 FLOPs and 4 bytes of output: 28 FLOP/B including the inputs, below the FP32 ridge. The traffic is the write of S itself, not re-reads of the inputs, and tiling only reduces re-reads. The fix is to not write S (chapter 14).

How does the cost of naive attention scale with the sequence length, compared with the rest of the block, and what is the first practical limit you hit?

Quadratically: S has B·H·T2 entries and is written and read four times; everything else scales linearly with T. The first limit is memory: S in FP32 for one GPT-2 layer is 3.2 GB at T = 8,192, before the time.

State precisely why keys and values of earlier tokens can be cached during generation.

Under the causal mask, the stream at position j depends only on tokens 0 to j at every layer, so appending tokens never changes it, and neither its key nor its value (projections of it) ever change. They are computed once, when token j is processed, and reused by every later query. Queries are not cached because no later step asks token j’s question again.

Prefill and decode: what is M for the GEMMs in each, and which roof applies?

Prefill: M = B·T, hundreds or thousands of rows, intensity in the hundreds, compute-bound. Decode: M = B, one row per sequence, every weight read once for a few FLOPs each, memory-bound; attention reads each sequence’s cache once for one query, also memory-bound and not helped by batching.

RoPE, GQA and SwiGLU: say in one line each what they change in the kernel list.

RoPE: an elementwise rotation of q and k that rides in the QKV epilogue and the cache append. GQA: fewer key/value heads, so narrower k and v columns, a smaller cache, and a decode kernel that serves several queries per cached key. SwiGLU: a third MLP matrix, with gate and up fused into one GEMM and the elementwise product in its epilogue.
